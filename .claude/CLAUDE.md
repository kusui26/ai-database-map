## 1. プロジェクトの本質

- **What**：オープンデータ（乗降客数・人口・地価・バス・事業所…）を **駅 × 半径** で集約し、**地図 ＋ AI** で誰でも使えるようにする **AIネイティブな Web アプリ**。
- **想定ユーザー / ユースケース**：鉄道会社の輸送計画、店舗出店の商圏分析、個人の住宅購入検討など
- **到達点**：個人開発した MVP「Station Area Database Map」を **AIネイティブ**に進化させる
- **Step1**：データセットを刷新（現在地）し、アプリを公開する
- **Step2**：LLMを連携し AIネイティブ化する
- **鉄則**：Step1 の実装は **常に Step2 を見据える**（後付けにしない）

---

## 2. 最重要原則：AIネイティブ＝「**API こそがプロダクト**」

従来の SaaS は UI が特権的で、API は二級の副産物だった。本プロジェクトはこれを**反転**させる。

```
      [ LLM (Gemini) ]        [ 構造化UI (Next.js / MapLibre) ]
              \                         /
               \                       /
                ────────── 共通API ──────────
                             │
                     ドメインロジック（不変条件・意味・単位・計算）
                             │
                     Supabase / PostgreSQL + PostGIS
```

- **人間UIとAIは、同じ共通APIを対等に叩く**。UIはこのAPIを直接（または薄いラッパで）呼ぶだけの薄い層にする。
- **ドメインロジックをUIに埋めない**：メトリクスの定義・ラベル・単位・フォーマット・半径変換・ランキング・クラスタリング等は**すべてサーバの共通APIが持つ**。UI専用ロジックと AI/API専用ロジックを二重に作らない（＝仕様のズレとバグの温床を断つ）。
- **APIは自己記述的にする**：利用可能な指標・半径・年・単位・ラベルを機械可読で返す**メトリクス・カタログ**を用意し、各エンドポイントを LLM の **function calling ツール**として設計する。
- **通信契約**：フロントとAIが従う標準インターフェース「**GUI Chat Protocol (Map Edition)**」の型（Type）に、APIレスポンスを合致させる。
- ⚠️ **避けるべきアンチパターン**：意味づけ（ラベル・単位・半径変換・クラスタリング）をフロントに埋め、APIを生カラムのCRUDにすると **AIから消費不能**になる。新設計は **意味を持つ共通API** を核にする。

## 3. コーディング規約（アプリ / Step2 実装時）

**哲学：人間が一目で理解できるコードを書く。** コードは物語のように読め、命名はストーリーを語る。

- **小さく純粋に**：1 関数は**20 行未満**・単一責務。副作用を分離し、純粋なデータ変換関数は専用ファイルへ（テスト容易化）。関数間の依存を減らし**疎結合**に。
- **不変・関数型**：`let` より **`const`**（`var` 禁止）、変数は極力上書きしない。`for` より **map/filter/reduce**、`.then()` より **async/await**。文字列組立は `let +=` でなく **array + push + join**。
- **型を厳格に**：明示的型を必ず付ける。**`any` 禁止**。**`as` キャスト禁止 → 型ガード**（`(x: unknown): x is T`）。Zod からは **`z.infer`** で導出（重複型を作らない）。
- **DRY（Don't Repeat Yourself）・定数・単位**：マジックナンバー禁止 → 名前付き定数。**変数名に単位**を（`timeout_ms`, `distance_km`, `radius_m`）。重複を作らない（メトリクス定義は**単一のカタログ**をUI/APIで共有）。
- **堅牢性**：失敗しうる処理に try/catch ＋**文脈付きエラー**（URL・パス等）。fetch/API は **`AbortController` タイムアウト**必須。
- **AIと人間で別APIを作らない**：必ず共通API（またはその薄いラッパ）経由。UIから直接 DB / ドメインロジックを叩かない。
- **品質ゲート**：**lint / typecheck / unit test を必ず回す**。**境界値・エッジケース**のテストを厚く書く。
- **import**：npm パッケージはトップレベル import（条件付き依存のみ動的 import）。正当な理由なく再エクスポートしない。ライブラリ既存ユーティリティを自作より優先。バージョン移行時は対象バージョンのAPIシグネチャを検証。

> AIにロジックを書かせる箇所は、汎用インターフェース／**DSL**を介す方が安定する。

## 4. Git / 変更範囲 / デバッグ（ガードレール）

**Git（ユーザーの明示的許可なしに書き込み系gitを実行しない）**
- 作業前に必ず `git status` / `git branch` で現在地を確認。想定と違えば確認する。
- **`main` に直接 push しない** → フィーチャーブランチを切って **PR**。実装開始前にブランチ作成。
- `git commit` / `push` / `merge` / `rebase` 前に必ず確認を取る。読み取り系（status/diff/log）は自由。
- **`git add .` 禁止**（ファイルは個別に add）。**未追跡ファイルを削除しない**。
- **`push --force` 禁止・`rebase` 禁止**。マージは **merge commit**（`--merge`）で、**squash 禁止**。
- コミットメッセージのプレフィックス：`feat:` / `fix:` / `refactor:` / `docs:` / `chore:`。
- 「PR を作って」＝**PR 作成**（マージではない）。作成前にターゲットブランチを確認。

**変更範囲**
- **明示的に依頼された変更のみ**行う。機能・ツール・パッケージ・コンテンツを**自律的に追加しない**。必要そうならまず確認。ドキュメント・コミットメッセージは簡潔に。

**デバッグ**
- 修正前に**根本原因を診断**。クイックフィックス（値のハードコード・JSONワークアラウンド）**禁止**。リグレッションは git 履歴 / diff を確認。

**日付**
- 今日の日付が必要なら**必ず `date` コマンドで取得**する（モデル内部知識に依存しない）。

## 5. セキュリティ / 機密

- **`.env`（gitignore）** に `ESTAT_APP_ID` 等の鍵。**APIキーや完全なリクエストURLを出力・ログに出さない**。
- **`data/` と `slide/` は gitignore**（大容量・機密）。派生データは `data/derived/` に置く。
- Supabase 化では **RLS 有効化・SSL 正常化・CORS 制限・シークレットは環境変数**
