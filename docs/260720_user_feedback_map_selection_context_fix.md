# 改善プラン：地図の選択を会話の文脈にする（＋サジェスト強化）

2026-07-20 のユーザーフィードバックに対する改善プラン。**実装はまだ行わない**。設計の正は `architecture.md` §4/§10・`plan_fable.md`（本件は **P8e** として追加想定）・`feat_llm.md`。

## 1. フィードバック（原文）と要点

> ① 入力しないでサジェストをポチポチ押せるのが良いですね。
> ② マップで駅を選択して、「この地価の推移は」のサジェストを押すと、前の会話に引っ張られてしまって選択しているのが無視されてしまいますね。
> ③ 地図で駅を選択したらその後のチャットもそれについての話しにすると良さそうですね。

| # | 種別 | 要点 |
|---|---|---|
| ① | 良かった点（維持・強化） | **入力せずサジェスト連打で探索できる**体験が良い → もっと使えるようにしたい |
| ② | バグ | 駅を地図で選択 → 「この駅の地価の推移は？」を押すと、**選択駅が無視され前の会話に引っ張られる** |
| ③ | 要望 | **地図で駅を選択したら、以後のチャットはその駅の話にする**（選択＝会話の主題） |

**②と③は同一の根本原因**（地図選択が会話に伝わっていない）。①はその文脈が効くようになれば価値が上がる。

## 2. 現状の実装と再現（コード根拠）

- **サジェスト**（`src/components/chat/SuggestionChips.tsx`）：`grp !== null`（駅選択中）かつ会話ありのとき `AFTER_STATION = ['この駅の地価の推移は？', '半径5kmで詳しく', '近くの駅と比べて']` を出す。**駅名を含まない「この駅」という汎用表現**で送る（`onPick(chip)` → 本文だけ送信）。
- **送信**（`src/components/chat/ChatPanel.tsx` `ChatBody`）：`send(text)` は `sendMessage({ text })` を呼ぶだけ。**地図の選択（`useMapUrlState` の `grp` / `radiusM`）は一切送っていない**。
- **API**（`src/app/api/chat/route.ts`）：`inboundSchema = z.object({ messages })` で **`messages` のみ**受理（Zod が未知キーを破棄）。`ToolLoopAgent` の `instructions` は `buildSystemPrompt()`（会話に依らない固定文）。→ **LLM は会話履歴しか見えず、今どの駅が選択されているかを知らない**。

**再現の流れ**：「新宿の人口は？」等で会話が始まる（履歴に新宿）→ 地図で東京を選択 → 「この駅の地価の推移は？」を押す → LLM には本文＋履歴だけが渡り、**「この駅」を解決できず**、履歴に出た新宿や直近の話題に引っ張られる（＝選択した東京が無視される）。

---

## 3. 根本原因

> **地図の選択状態（`?grp`・`?r`）が、チャット（LLM）の文脈に渡っていない。**

チャットと地図は 2 つの独立した状態チャネル（会話履歴 ／ URL の選択）で、**両者が繋がっていない**。「この駅」「ここ」「（この駅の）地価の推移は？」のような**指示語・カテゴリのみの追随質問**は、選択駅を知らなければ解決できない。加えて `AFTER_STATION` サジェストは `hasMessages` のときしか出ないため、「駅を選んですぐ聞く」動線も弱い。

これは本プロジェクトの思想「**クリックと会話は同じ**」（`architecture.md` §4）の裏返し：これまで「会話 → 地図」（mapActions で地図を操作）は繋がっていたが、**「地図 → 会話」（クリック選択を会話の前提にする）が欠けていた**。本改善はこの一方向を補完する。

---

## 4. 設計方針（AIネイティブ・純加算との整合）

1. **地図の現在の選択を、リクエストごとに LLM の文脈として渡す**（会話 ↔ 地図の双方向化）。
2. **選択駅は指示語・追随質問の解決に使うが、明示された別駅名や一般質問には干渉しない**（プロンプトで優先順位を明記）。
3. **純加算**：`src/domain`・`src/shared/protocol`・既存 API・`src/db` は**無改変**。変更は **AI 層（`route.ts`・`system-prompt.ts`）＋チャット UI（`ChatPanel`・`SuggestionChips`）** に限定（P8a–P8d と同じ流儀）。
4. **選択が会話の主題であることをユーザーにも可視化**（「選択が無視される」という不信感の解消＝②のUX面）。

## 5. 改善案（比較と採用）

| 案 | 概要 | 長所 | 短所 | 採否 |
|---|---|---|---|---|
| **A. サーバ側マップ文脈注入** | クライアントが送信時に現在の選択（`selectedGrp`・`radiusM`）を body で送る → route が駅を解決し、`instructions` に「現在の選択駅」文脈を1行注入 | **汎用**（サジェストも自由入力も・「この駅」「ここ」「地価の推移は？」全部効く）。③を素直に実装。選択駅の `grp` を渡せば LLM は `getStationDetail(grp)` を**検索なしで直呼び**でき高速・確実 | route/プロンプトに小変更・grp→駅名の解決に軽い DB 1 クエリ | **採用（中核）** |
| B. クライアント側リライト | 送信時に「この駅」→ 実駅名へ置換して送る | サーバ変更不要 | 駅名の解決が必要・「この駅」限定で脆い（「ここ」「地価は？」等に非対応）・本文が汚れる | 却下（Aで包含） |
| C. サジェスト強化のみ | 選択時のサジェスト拡充・駅名表示 | UI だけで完結 | **②の根本（LLMが選択を知らない）を直さない** | 補助（Aと併用） |

→ **A（サーバ側マップ文脈注入）を中核に、C（サジェスト強化）＋選択の可視化を併せて実施**する。

## 6. 採用案の詳細設計

### 6.1 データフロー（地図 → 会話）

```
[地図で東京を選択] ─ ?grp=東京#0 / ?r=1000（nuqs）
        │  useMapUrlState で ChatBody が現在値を取得
        ▼
sendMessage({ text: 'この駅の地価の推移は？' }, { body: { selectedGrp: '東京#0', radiusM: 1000 } })
        │  POST /api/chat（messages ＋ selectedGrp ＋ radiusM）
        ▼
route：inboundSchema で selectedGrp/radiusM を受理
   → stationByGrp(selectedGrp) で駅名・県を解決（未解決なら文脈スキップ）
   → instructions = buildSystemPrompt() ＋ mapContext(駅, radiusM)
        「# 現在の地図の状態\nユーザーは地図で『東京（東京都・grp=東京#0）』を半径1kmで選択中。
         『この駅』『ここ』や、駅名を省いた追随質問（例『地価の推移は？』）はこの駅を指す。
         ただし別の駅名が明示されたら、また一般的な質問（ランキング等）では選択に縛られない。」
        ▼
LLM は getStationDetail(grp='東京#0', category='land_price', radiusM=1000) を直呼び（検索不要）
        → assemble → 東京の地価パネル＋地図で東京を選択（既存の描画パス）
```

### 6.2 変更点（実装時・ファイル別）

- **`src/components/chat/ChatPanel.tsx`（`ChatBody`）**
  - `useMapUrlState()` から `grp`・`radiusM` を取得。
  - `send(text)` を `sendMessage({ text }, { body: { selectedGrp: grp ?? undefined, radiusM } })` に（**選択があるときだけ** body に載せる。AI SDK の `ChatRequestOptions.body` は追加 JSON をリクエストに合流させる＝確認済み）。
  - transport は `useMemo` で1回生成のまま（body は per-call で常に最新）。
- **`src/app/api/chat/route.ts`**
  - `inboundSchema` に `selectedGrp: z.string().optional()`・`radiusM: z.number().optional()` を追加（現状は未知キーを破棄しているため受理できない）。
  - `selectedGrp` があれば `stationByGrp(selectedGrp)`（既存 db クエリ・**無改変で再利用**）で `StationRow` を取得し、`instructions` に `mapContextPrompt(station, radiusM)` を連結。解決失敗（未存在 grp）や未選択なら注入しない（安全側）。
  - `radiusM` は `RADII_M` で検証（不正は無視）。
- **`src/ai/system-prompt.ts`**
  - `mapContextPrompt(station, radiusM): string` を追加（純関数・上記の文脈文＋優先順位規約）。
  - 既存 `buildSystemPrompt()` の振る舞い規約に「**指示語・カテゴリのみの追随は現在の選択駅を指す。過去の会話より現在の選択を優先。明示の別駅名・一般質問は選択に縛られない**」を追記。
- **`src/components/chat/SuggestionChips.tsx`（①③のUI面）**
  - **駅選択中は会話有無に依らず**「駅の掘り下げ」サジェストを表示（現状は `hasMessages` 必須で、選んですぐ聞けない）。
  - サジェストの**バリエーション拡充**（乗降/人口/地価/バス/事業所/従業者・「半径5kmで」「近くの駅と比べて」「新宿と比較」等）。文言は「この駅の◯◯は？」（サーバ文脈が解決）。
  - 可能なら**選択駅名を表示**（例チップ見出し「東京駅について：」）。駅名はクライアントが持たない（grp のみ）ため、(a) 既存 `/api/stations?q=` 相当や駅サマリの軽量取得で解決、または (b) 文脈はサーバに任せ UI は「この駅」表記に留める、のいずれか（実装時に判断・(b) が最小）。
- **選択の可視化（②の不信感の解消）**
  - チャット上部または入力欄付近に「**現在の対象：東京駅（半径1km）**」の控えめなインジケータ（選択中のみ）。「選択が無視される」という誤解を防ぎ、③の「選択＝主題」を明示。`useMapUrlState` の grp で表示。

### 6.3 プロンプトの肝（②の"引っ張られる"を断つ）

`mapContextPrompt` は次を明確にする：
- **現在の選択駅が『この駅』『ここ』および駅名省略の追随質問の解決対象**。
- **過去の会話に別の駅が出ていても、現在の選択を優先**（＝②を直接是正）。
- **ユーザーが別の駅名を明示したらそちら**、**一般質問（ランキング・散布・カタログ）は選択に縛られない**（＝選択が万能な足枷にならないよう抑制）。
- 選択駅の `grp` を与え、`getStationDetail(grp=…)` を**検索なしで直呼び**してよいと示す（高速・確実）。

## 7. エッジケースと配慮

| ケース | 方針 |
|---|---|
| 駅未選択 | 文脈注入なし（現状どおり） |
| 別駅を明示（「新宿の人口は？」） | 明示駅を優先（プロンプトで規定） |
| 会話途中で選択が変わる | 各送信で最新の選択を body に載せる（per-call＝常に最新） |
| 一般質問（「全国ランキング」） | 選択に縛られない（プロンプトで規定） |
| 履歴内「この駅」の後日曖昧さ | パネル・地図が実体を示すため実害小（履歴の再解釈はしない） |
| 未知/不正 grp | `stationByGrp` が null → 文脈注入をスキップ（安全） |
| トークン/コスト | 文脈は1行・DB は選択時に1クエリのみ（軽微） |
| プライバシー | 選択駅は公開データの grp のみ・鍵はサーバ（既存方針） |

## 8. 受け入れ基準

- 地図で東京を選択 → 「この駅の地価の推移は？」で **東京の地価**が出る（前の会話に引っ張られない）。
- 会話に別駅（新宿）がある状態でも、**選択駅（東京）が優先**される。
- 「新宿の人口は？」と**明示**した場合は新宿（選択に縛られない）。「全国ランキング」等の一般質問も選択に非依存。
- 選択駅を変えると、以後の「この駅…」がその駅に追随。
- **駅選択中は会話が無くても掘り下げサジェストが出る**（入力せず連打で探索できる＝①）。
- チャットに**現在の対象（駅名）**が控えめに表示される。
- `domain`・`protocol`・既存 API・`db` に **diff 0**（純加算）。
- console error 0・typecheck/lint/build 緑・eval 緑（下記拡張含む）。

## 9. 検証方法

- **ヘッドレス（Playwright・LLM 実）**：①地図で駅選択 → ②掘り下げサジェスト表示 → ③「この駅の地価の推移は？」クリック → ④**選択駅の地価パネル**が出る／⑤会話に別駅がある状態でも選択駅が優先、を実測（console error 0）。無料枠のため 1〜2 クエリで実施。
- **eval 拡張**：`tests/chat-eval.test.ts` の runner に `selectedGrp` を body で送るオプションを追加し、**文脈依存ケース**（例「選択＝東京で『地価の推移は？』→ getStationDetail(東京, land_price)」）を `cases.ts` に 1〜2 問追加。`score.ts` は既存の toolCalls 入力照合で判定可能。
- **回帰**：選択なしの既存 20 問は不変であること（body に selectedGrp を載せない経路）。

## 11. リスク・代替

- **リスク：選択に過剰追随**（一般質問まで選択駅に寄る）。→ プロンプトで「明示・一般質問は非依存」を強調＋eval で回帰確認。プロンプト調整で対応。
- **リスク：駅名表示のための追加取得**（UI に駅名を出す場合）。→ 最小案は「この駅」表記＋サーバ文脈で解決（UI に駅名を出さない）。駅名表示は任意拡張。
- **代替：選択時に自動で1メッセージ送る**（「東京駅について教えて」を自動投入）。→ 押しつけがましく却下。文脈注入＋サジェストの受動的提示に留める。
- **将来**：選択だけでなく**表示中の地図範囲（bbox）や開いている詳細タブ**も文脈化すれば、「今見えている範囲で人口が多い駅は？」等に発展可能（本プランのスコープ外・拡張余地として記録）。
