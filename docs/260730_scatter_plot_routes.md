# 散布図に「路線」フィルタを追加する（実装プラン）

作成日: 2026-07-31 ／ 対象: データパイプライン・DB・共通API・散布モーダル・AI ツール ／ 依頼: 「散布図を路線でも絞り込みたい。例：**東海旅客鉄道で新幹線駅のみ**を表示する」

> §1–§8 が調査と設計、**§9 が確定した決定事項、§10 が PR1（データ基盤）の実装結果**（2026-07-31 実装・検証済み）。PR2（UI・AI）は本 PR にスタックして進める。

## 0. エグゼクティブサマリ（結論先出し）

- **路線データは既存の一次データ（国土数値情報 S12-25）に入っている**。`S12_003` が路線名、`S12_005` が事業者種別コード。ただし**派生 CSV にも DB にも取り込まれていない**（notebook は S12_003/S12_005 を読んでいるが出力していない）。→ **パイプラインの追加が必要**。
- **新幹線は名前の当てずっぽうではなく、コードで一意に判定できる**：`S12_005 = 1` が **8 新幹線路線・103 駅**と完全一致（`新幹線` を名前に含む路線は 113 レコードすべてコード 1）。
- **既存の駅グループ（grp）に 100% 貼れることを実験で確認**：S12 の 10,534 レコードすべてが同名の駅グループに一致し、**距離は中央値 55m・最大 706m**（grp のクラスタ半径 1km の内側）。**9,273 グループすべてに路線が付く**。→ **重いノートブック再実行は不要**で、独立スクリプトで安全に生成できる。
- **依頼の例が実データで再現できる**：`会社 = 東海旅客鉄道` × `種別 = 新幹線` → **17 駅**（＝東海道新幹線の駅数）。
- **設計上の要注意点**：**路線名は会社をまたいで重複する**（561 本のうち **28 本**。「本線」は 10 社、「東海道線」は JR 東日本・東海・西日本の 3 社）。→ 路線フィルタは**会社と組で効かせる**（同一行での AND）必要がある。
- 規模感：追加テーブルは **10,424 行（約 196KB）** と小さい。UI は 4 つ目のセレクタ（既存の連動の仕組みを再利用）。

## 2. 既存の駅グループへの対応づけ（実験で検証済み）

`grp` は「**駅名 ＋ 半径 1km の DBSCAN クラスタ**」（[`passenger_aggregation.md`](./passenger_aggregation.md) §3.1）。S12 の各レコードの代表点から、**同名の駅グループのうち最も近いもの**へ対応づける実験を行った。

| 検証 | 結果 |
|---|---|
| 一致したレコード | **10,534 / 10,534（100%）**・駅名が見つからないものは 0 |
| 対応づけの距離 | 中央値 **55m**・95%tile 222m・**最大 706m**（クラスタ半径 1km の内側＝誤対応の余地なし） |
| 路線が付いた駅グループ | **9,273 / 9,273（100%）** |
| 妥当性（東京#0） | 東海道新幹線・東北新幹線・東海道線・東北線・京葉線・総武線・4号線丸ノ内線（**実態と一致**） |
| 妥当性（東海道新幹線） | **17 駅**（東京〜新大阪の実駅数と一致） |
| 妥当性（依頼の例） | **東海旅客鉄道 × 新幹線 = 17 駅** |

→ **ノートブックの再実行は不要**。クラスタ番号（`#0`/`#1`）の再現に依存せず、**距離最小の同名グループ**へ貼るだけで一意に決まる（同名グループ同士は 1km 以上離れているため）。

| 案 | 内容 | 評価 |

  station_id smallint not null references public.stations(id) on delete cascade,
  operator   text     not null,
  route      text     not null,

create index on public.station_routes (route);
create index on public.station_routes (route_type);
alter table public.station_routes enable row level security;
create policy "anon read" on public.station_routes for select to anon, authenticated using (true);

## 4. 絞り込みの意味論（ここが設計の核心）

### 4.1 会社 × 路線は「同じ行」で AND

東京駅は **JR東海の東海道新幹線**と**JR東日本の東北新幹線**の両方を持つ。素朴に「会社フィルタ（`stations.operators`）」と「路線フィルタ（`station_routes`）」を独立に AND すると、
**「東海旅客鉄道 × 東北新幹線」でも東京駅がヒットしてしまう**（会社条件と路線条件が別々の根拠で満たされるため）。

→ **路線・種別が指定されたときは、会社条件も `station_routes` の同一行で判定する**（`exists (select 1 from station_routes sr where sr.station_id = s.id and (ops 未指定 or sr.operator = any(ops)) and (routes 未指定 or sr.route = any(routes)) and (types 未指定 or sr.route_type = any(types)))`）。

会社だけを指定した場合の挙動は**現行と完全一致**であることを、既存のゴールデン値（東日本旅客鉄道 854／東京地下鉄 143／OR 969／京成電鉄 69／新京成電鉄 24／札幌市 46）で確認する（§7）。

### 4.2 種別（新幹線など）は独立したパラメータにする

「新幹線駅のみ」は 8 路線を列挙させるより、**種別コードで 1 発**のほうが明確で、AI からも自然に呼べる（`routeTypes: [1]`）。
複数指定は OR（例：新幹線 ＋ 公営）。`routes` と `routeTypes` を**両方**指定した場合も OR（「東海道線 または 新幹線」）とする。

### 4.3 重複路線名（「本線」）の扱い

- 一覧では **会社名を併記**して表示（例：`本線（京成電鉄）`）。
- **会社を選んでいるときは、その会社の路線だけを候補に出す**（既存の都道府県⇄会社の連動と同じ仕組み）。
- 会社未選択のまま重複路線を選んだ場合は「その名前の路線すべて」＝ 10 社ぶんが対象（**仕様として明示**し、必要なら §9-4 の「会社も自動で選ぶ」を採る）。

## 5. UI 設計

```
現状：  [全国 ▾] [全社 ▾]            [☑ 低分母（⚠）を除外]
変更後：[全国 ▾] [全社 ▾] [全路線 ▾] [☑ 低分母（⚠）を除外]
```

- 幅 896px の 1 段目は現在 3 コントロールで行高 34px。4 つ目を足しても**折返しは発生しない見込み**（実装後にヘッドレスで確認）。
- **路線ポップオーバー**（会社セレクタと同じ骨格＋以下）：
  1. **種別チップ**：`新幹線 / JR在来線 / 公営 / 民営 / 三セク`（トグル＝`routeTypes`）。**「新幹線」を押すだけで依頼のユースケースが完了**。
  2. **検索**（561 本あるため必須）。
  3. **路線一覧**：駅数の多い順、`路線名（会社名）` 表示、重複路線は会社名が識別子になる。
  4. **連動**：会社選択中はその会社の路線のみ（東海旅客鉄道 → 13 本）。逆に路線選択中は会社候補も絞る（既存の `operatorLink.ts` と同じ考え方を拡張）。
- ラベル：未選択は「全路線」、1–2 本は連結、3 本以上は「東海道新幹線 他N件」（既存 `selectionLabel` を再利用）。
- パネルのタイトルにも反映（例：`…（全国・東海旅客鉄道・新幹線）`）＝ ⤢ 昇格やチャット内カードで条件が残る。
