# データ読み込み・表示・遷移の速度を安全に改善する（実装プラン）

作成日: 2026-08-03 ／ 対象: Vercel 設定・地図の初期化・API/RPC・JS バンドル
／ 依頼: 「データの読み込みやページの表示、ページ遷移の**スピード**を**安全に**改善したい」

> 本プランは調査（§1–§3）＋改善案（§4–§6）＋**ご確認いただきたい決定事項（§9）**。
> 数値はすべて **2026-08-03 の実測**（本番 https://ai-database-map.vercel.app ・ローカル本番ビルド・Supabase 直叩き）。

## 0. エグゼクティブサマリ（結論先出し）

- **最大の原因は「関数が米国東部で動いている」こと。** レスポンスヘッダ `x-vercel-id: hnd1::iad1::…` が示すとおり、
  リクエストは東京エッジ（hnd1）に入るが、**関数は iad1（米バージニア）で実行**され、そこから**東京の Supabase** を叩いている。
  DB を 1 回引くだけの `/api/health` が **530〜1,192ms** かかるのはこのため。**`vercel.json` に 1 行**（`"regions": ["hnd1"]`）で直る。
- **2 番目は「駅データを取りに行くのが遅い」こと。** 全駅 geojson の取得は **1,820ms 経ってから開始**される
  （MapLibre の `load` イベントを待っているため）。取得自体は CDN 温で **153ms** しかかからない。
  **並行化するだけで、地図が出た瞬間に駅も出る**ようになる。
- **3 番目はバンドルの無駄。** `catalog.json`（509KB）が**チャンク 2 本に重複**して入っている。chart.js（186KB）も vaul（42KB）も 2 本ずつ。
  初期 JS は **29 ファイル・転送 884KB・展開 3,484KB**。
- 体感の残りは**メインスレッドの詰まり**：ロングタスク合計 **3,074ms**（うち **1,892ms は駅データ到着後**＝1.3MB の JSON を
  メインスレッドで扱っているコスト）。
- **危険な変更は要らない。** 上位 3 つはいずれも「設定 1 行」「取得順の変更」「import 境界の整理」で、
  ドメインロジック・DB・API の契約に触れない。

| 施策 | 期待効果 | リスク |
|---|---|---|
| ① 関数リージョンを東京へ | **全 API が数百 ms 短縮**（health 1,131ms → 100〜200ms 見込み）| 極小（設定 1 行）|
| ② 駅 geojson の取得を並行化 | 駅の表示が **約 1.6 秒** 早まる | 小 |
| ③ チャンク重複の解消 | 転送 −約 100KB／展開 **−約 750KB** | 小〜中 |
| ④ geojson の静的化 | CDN MISS 時 **4.3s → 約 0.1s** | 中（更新手順が 1 段増える）|
| ⑤ 散布 RPC のピボット | 散布の取得 **1.0–1.3s → 0.4–0.6s** 見込み | 中（RPC 変更）|

## 1. 計測方法（再現手順）

| 対象 | 方法 |
|---|---|
| 初期表示 | Playwright（1440×900）＋ Navigation/Resource Timing・PerformanceObserver（LCP・longtask）|
| API | 本番 URL へ 2 回連続（1 回目＝CDN MISS／2 回目＝HIT）。`x-vercel-cache` と `x-vercel-id` を記録 |
| サーバ内訳 | ローカル本番ビルド（東京・DB も東京）で API 実測 ／ Supabase PostgREST を gzip 付きで直叩き |
| バンドル | 初期表示で読まれた `.js` を全取得し、内容の特徴（maplibre / chart.js / ai-sdk / catalog）で分類 |

> アプリは PostgREST の **gzip** 経由なので、そちらで測る（同 795–979ms）。

## 3. ボトルネックの特定

```
[ユーザー] ──東京エッジ(hnd1)── [関数 iad1 米東部] ──太平洋往復── [Supabase 東京]
                                        ↑ ここが往復ぶん丸ごと無駄
```

1. **関数リージョンの不一致**（最大）。DB を 1 回引くだけの `/api/health` が 530〜1,192ms。
   すべての API がこの往復を毎回払っている。CDN HIT の間だけ隠れているが、**MISS と `no-store` 経路（チャット）では常に効く**。
2. **駅データの取得が直列**。`map.on('load')` の中で `fetch` しているため、**1,820ms は取りに行きすらしない**。
   その間ネットワークは空いている。
3. **1.3MB の JSON をメインスレッドで扱っている**。`data: featureCollection`（実体渡し）なので、
   JSON パース → ワーカーへの構造化クローンがメインスレッドに乗る。到着後のロングタスク **1,892ms** の主因。
4. **バンドルの重複**。同じモジュールが「初期グラフ側」と「動的 import 側」の両方に入って複製されている。
5. **散布の RPC が縦持ち**。`values_for_columns` は 1 駅×4 キー＝4 行を返し、`grp` と `station_name` が 4 回重複する
   （展開 3,256KB）。ピボットすれば 1/4 以下。

## 4. 改善案（安全性の高い順）

### ① 関数リージョンを東京に寄せる 〔効果：大／リスク：極小〕

```json
// vercel.json
{ "regions": ["hnd1"] }
```

- DB との往復が国内になる。**すべての API のコールドと `no-store` 経路が短縮**。
- 期待：`/api/health` 1,131ms → **100〜200ms**、`geojson` MISS 4,257ms → **1,000〜1,500ms**。
- 注意：無料/Hobby プランは**リージョン 1 つのみ指定可**（要確認）。日本のユーザー向けなので東京固定で問題ない。
- 検証：`x-vercel-id` が `hnd1::hnd1` になること、§2.2 の表を再測して全項目が改善すること。

### ② 駅 geojson の取得を地図初期化と並行にする 〔効果：大／リスク：小〕

- 現状：`map.on('load')` の**中で** `fetch` → 開始 1,820ms。
- 変更：コンポーネントのマウント時（または module 先頭）で `fetch` を開始し、`load` では**待つだけ**にする。
  あわせて `<link rel="preload" as="fetch">` を `layout.tsx` に置き、HTML パース直後に開始させる。
- 期待：駅の表示が **約 1.6 秒**早まる（地図が描けた瞬間には取得済み）。
- リスク：小（取得の**順序**を変えるだけで、描画経路は不変）。

### ③ チャンクの重複を解消する 〔効果：中／リスク：小〜中〕

- `catalog.json` 509KB×2・chart.js 186KB×2・vaul 42KB×2 が二重に入っている。
- 静的 import の境界を 1 か所へ寄せる／共有チャンクに載るよう整理する。
- 期待：転送 **−約 100KB**、展開 **−約 750KB**、`catalog` の**パースが 1 回ぶん減る**。
- 検証：§2.4 の分類スクリプトを再実行し、重複が 0 になること。

### ④ 全駅 geojson を静的アセットにする 〔**取り下げ（2026-08-04・実測による）**〕

> **取り下げの理由**：①で MISS が 1,727ms → **822ms** に縮み、さらに②で geojson が
> **初期表示のクリティカルパスから外れた**（到着 644ms・地図の load は約 2,500ms）。
> 静的化しても体感は変わらず、**データ更新手順が 1 段増えるコスト**に見合わない。
>
> 以下は当初の検討内容（記録として残す）。

- 現状は毎回 DB を引いている（Supabase 795〜979ms＋Zod 検証）。**駅の集合はデータ更新でしか変わらない**。
- `catalog.json` と同じ「**コードが正・DB はミラー**」の思想で、パイプラインが `public/stations.geojson` を生成する。
- 期待：CDN MISS 時 **4,257ms → 約 100ms**（関数を経由しない）。DB 往復ゼロ。
- リスク：**データ更新時に再生成が必要**。→ `pipeline/` に組み込み、駅数（9,273）の自己検証を内蔵して事故を防ぐ。
- 代替：静的化せず ①だけで済ませる（MISS はリージョンあたり 1 日 1 回なので、影響は限定的）。

### ⑤ 散布の RPC をピボットして軽くする 〔効果：中／リスク：中〕

- `values_for_columns` の展開後 **3,256KB** は、`grp`・`station_name` の重複が主因。
- SQL 側で `(grp, name, x, y, flag)` の形に畳めば **1/4 以下**。
- 期待：散布の取得 1.0–1.3s → **0.4–0.6s** 見込み。API 応答 524KB も縮む。
- リスク：中（RPC 変更）。ただし PR #44 で**ゴールデン照合の手順が確立済み**なので、非回帰は数値で担保できる。

### ⑥ 地図ソースを URL 指定にしてワーカーで処理させる 〔**取り下げ（2026-08-04・前提が誤り）**〕

> **取り下げの理由**：本案は「1.3MB の JSON をメインスレッドで扱っているのが主因」という
> 前提だったが、**実測で否定された**。
>
> | 実測 | 値 |
> |---|---:|
> | `JSON.parse`（1.3MB）| **10ms** |
> | `structuredClone`（ワーカーへ渡す）| **19ms** |
> | 最小化・座標丸めによる削減 | **0%**（応答は既にコンパクト）|
>
> さらに駅の件数を変えて測ると **0 件 2,676ms → 1,000 件 4,333ms → 9,273 件 4,675ms** と、
> **件数にほぼ比例しない**。駅データ由来の負荷（約 2,144ms＝全体の 49%）は
> **レイヤ追加・ラベルの衝突判定など描画側の固定費**であり、ワーカー化では減らない。
>
> 以下は当初の検討内容（記録として残す）。

- `data:` に**実体**ではなく **URL** を渡すと、MapLibre が**ワーカー側で**取得・パース・クラスタリングする。
- 期待：到着後のロングタスク **1,892ms** の相当部分が消える。
- リスク：中。`coordsRef`（grp → 座標）をメインスレッドで持つ必要があるため、**軽量な座標辞書**（grp/lon/lat/name のみ）を
  別に用意する設計が要る。②④の後に、効果を測ってから判断するのが安全。

### ⑦ カタログを小さくする 〔**取り下げ（2026-08-04・実測による）**〕

> **取り下げの理由**：③の後、**駅データ到着前のロングタスクは 63ms** しかない。
> カタログのパースは体感に効いておらず、契約物（`/api/metrics`）を触るリスクに見合わない。
>
> 以下は当初の検討内容（記録として残す）。

- `source`/`license` を id 参照にすれば **−101KB（−32%）**。パース時間に効く。
- ただし `catalog.json` は**契約物**（`/api/metrics` がそのまま返す）。**読み出し時に展開**して互換を保つ設計が要る。
- ③でパース回数が半分になるため、**③の効果を測ってから**判断する。

### 見送りを推奨するもの

| 案 | 理由 |
|---|---|
| 座標精度の丸め | gzip 後の差が小さい見込み。①〜④で足りるなら不要 |
| チャットのデスクトップ既定オープンを止める | AI SDK が初期に載らなくなるが、**P8d で決めた UX を変える**。速度のために体験を削るのは最後の手段 |
| Edge Runtime 化 | Supabase クライアントの動作検証が要り、得られる差は①で大半が回収できる |

## 6. 「安全に」進めるための原則

1. **1 施策＝1 PR**。前後で同じ計測スクリプトを回し、**数値を PR に貼る**。
2. **既存のゴールデンを必ず再実行**：散布（東海旅客鉄道×新幹線＝17 駅）、ランキング 11 ケース、
   信頼性フラグ（除外 99 駅）、AI eval 24 問。**速度のために結果が変わっていないこと**を数値で示す。
3. **性能バジェット**を決め、以後の PR で回帰を検出する（§8）。
4. **契約物（catalog.json・protocol・API の形）を壊さない**。壊す案（⑦）は最後に、互換を保つ設計で。
5. **1 つ直すたびに測り直す**。①で DB 往復が縮むと、④⑤の相対的な価値も変わる。**次の判断は実測後**に行う。

## 13. 実装結果 — ③初期表示で読む JS を減らす（2026-08-04・ブランチ `perf/defer-heavy-chunks`）

### 13.1 調査：原因は「重複」ではなく**不要なマウント**だった

2 本の `catalog` チャンクを取得して調べたところ、**どちらもカタログ単体**（他のモジュールを含まない）で、
ハッシュも別＝別々にコンパイルされていた。追跡すると真因は別にあった：

**`StationDetailPanel` と `ChatCanvas` / `PromotionHost` は、何も表示しない状態でも常にマウントされていた。**
そのため Chart.js とメトリクスカタログが初期表示で **2 本ずつ**読み込まれていた。

- `StationDetailPanel`：`grp` が無ければ何も描かないのに、`MapShell` が常に描画していた
- `ChatCanvas` / `PromotionHost`：`promotion` が無ければ何も描かないのに、チャットを開いた時点で描画していた

### 13.2 対応：必要になるまでマウントしない

既存の `chatSeen`（一度開いたら保持する）と同じパターンで揃えた。

| コンポーネント | 変更前 | 変更後 |
|---|---|---|
| `StationDetailPanel` | 常時 | 駅が選ばれたら（`grp !== null`）|
| `ChatCanvas` / `PromotionHost` | チャットを開いたら | 図の昇格が起きたら（`promotion !== null`）|

Turbopack のチャンク分割を設定で変える案も検討したが、**サポートが薄く安全でない**ため採らなかった。
「重複を消す」より「そもそも読まない」ほうが確実で、初期表示にはより効く。
