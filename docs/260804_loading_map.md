# 「地図を読み込み中…」で画面を持っていかれるのを解消する（実装プラン）

作成日: 2026-08-04 ／ 対象: `Fab` / `AppHeader` / `PromotionHost` の遅延ロード、`page.tsx` の Suspense 境界
／ 依頼: 「散布図・ランキングを押したときに**「地図を読み込み中」で画面を持っていかれる**のが気になる。
**① そもそも出ないようスピードを改善する**、**② 待ちが避けられないなら気にならない UI にする**、の優先順位。
アプリ更新（リロード）時の表示はあまり気にならない。裏が地図の背景なら気にならない気がする」

> §1–§5 が調査、**§6 が推奨**、**§10 がご確認いただきたい決定事項**。
> 数値はすべて 2026-08-04 の実測（本番ビルドをローカル起動、および本番 `ai-database-map.vercel.app`）。

---

## 0. エグゼクティブサマリ（結論先出し）

- **これは「遅い」問題ではなく、バグに近い実装ミスです。** 地図は**再読み込みされていません**。
  MapLibre のインスタンスも canvas もそのまま生きており、React が**アプリ全体を `display:none` で隠して**
  スケルトンに差し替えているだけでした。つまり **300ms のあいだ、見えているものを捨てているだけ**。
- **原因は 1 行で説明できます。** `next/dynamic` は
  **`ssr: false` か `loading` のどちらかを渡したときだけ**自前の Suspense 境界を作ります
  （出荷コードの `hasSuspenseBoundary = !opts.ssr || !!opts.loading`）。
  FAB の 2 つのダイアログは**どちらも渡していない**ため境界が無く、初回に読み込みで中断すると
  React が遡って `page.tsx` の `<Suspense fallback={<MapSkeleton/>}>` を使い、**全画面が奪われます**。
- **同じ穴が 5 か所**あります（FAB のランキング・散布図、ヘッダの ⓘ、AI 昇格用の 2 つ）。
  ⓘ でも再現を確認しました（3/3・約 340ms）。一方 `ssr: false` を渡している駅詳細やチャットでは**起きません**（0/3）。
- **依頼の ① と ② は両方とも実現できます。**
  - ①**先読み**：ダイアログのチャンクは 6 本 166KB。**4G 相当で 1,342ms、3G 相当で 9,193ms** かかります。
    今はこれを**クリックしてから**払っているので、アイドル中に先に取っておけば待ちごと消えます。
  - ②**境界を張る**：`loading: () => null` を足すだけで**全画面スケルトンは 0 回**になりました（実測 3/3 → 0/3）。
    地図は出たままで、依頼の「裏が地図の背景なら気にならない」に一致します。
- **やらなくてよいと分かったこと**：カタログの Zod 検証は **5.7ms**（586 件）で、待ちの原因ではありません。
  ここを削る最適化は**効果がないので採りません**。

## 1. 再現と現象（実測）

### 1.1 どの操作で起きるか（各 3 回）

| 操作 | 全画面スケルトン | 出現まで | 表示時間 |
|---|---:|---:|---:|
| **ランキング（FAB）** | **3/3 回** | 79–165ms | **325–330ms** |
| **散布図（FAB）** | **3/3 回** | 62–104ms | **323–326ms** |
| **ⓘ（ヘッダの About）** | **3/3 回** | — | **339–347ms** |
| 駅を選択（検索から） | 0/3 回 | — | — |
| AI チャットを開く | 0/3 回 | — | — |

本番（`ai-database-map.vercel.app`）でも同じです：ランキング **3/3 回・321–360ms**／散布図 **3/3 回・323–377ms**。

### 1.2 何が起きているか

フラッシュ中の DOM を捕まえたところ、`<main>` が **2 つ**ありました。

```
main.relative.h-dvh[display:none]   ← アプリ本体（地図・チャット・ヘッダ）が隠されている
main.relative.h-dvh                 ← MapSkeleton（「地図を読み込み中…」）
```

- **URL は変わらず、RSC フェッチも発生していません** → ルータ遷移（`app/loading.tsx`）ではなく、
  **`page.tsx` の Suspense フォールバック**です。
- **地図は作り直されていません**：フラッシュ前に印を付けた `canvas.maplibregl-canvas` が
  フラッシュ後もそのまま生きており（`canvasCount` は常に 1）、MapLibre の再初期化は**起きていません**。

→ **実際には何も読み込み直していないのに、「地図を読み込み中」と表示して画面を覆っている**状態です。
依頼の「画面を持っていかれる」という体感は、この挙動そのものです。

### 1.3 初回だけ起きる

同じダイアログを開き直すと、**2 回目以降は一度も出ません**。

| 操作 | 1 回目 | 2 回目 | 3 回目 |
|---|---|---|---|
| ランキング | 全画面スケルトン 330ms | **なし** | **なし** |
| 散布図 | 全画面スケルトン 312ms | **なし** | — |

→ 原因は**初回のチャンク取得で React が中断（suspend）すること**だと確定できます。

## 2. 根本原因

### 2.1 `next/dynamic` は「境界を作らない」ことがある

出荷されている実装（`.next/static/chunks` から復元・`next@16.2.10`）：

```js
// next/dist/shared/lib/lazy-dynamic/loadable.js
const defaultOptions = { loader: …, loading: null, ssr: true }
const opts = { ...defaultOptions, ...options }
const hasSuspenseBoundary = !opts.ssr || !!opts.loading   // ★ここ
const Wrap = hasSuspenseBoundary ? React.Suspense : React.Fragment
```

そして、クライアントに配られる `dynamic()` 本体には**既定の `loading` がありません**：

```js
// next/dist/shared/lib/dynamic.js（クライアントビルド）
function dynamic(loader, options) {
  const n = {}; if (typeof loader === 'function') n.loader = loader
  const l = { ...n, ...options }
  return Loadable({ ...l, modules: l.loadableGenerated?.modules })   // loading は付かない
}
```

したがって：

| 書き方 | `opts.ssr` | `opts.loading` | 境界 | 中断したとき |
|---|---|---|---|---|
| `dynamic(fn)` | `true` | `null` | **Fragment（無し）** | **遡って `page.tsx` の fallback ＝ 全画面スケルトン** |
| `dynamic(fn, { ssr: false })` | `false` | `null` | Suspense | その場で fallback（`null`）＝**見た目に変化なし** |
| `dynamic(fn, { loading: … })` | `true` | 関数 | Suspense | 同上 |

**FAB の 2 つはどちらのオプションも渡していません**：

```ts
// src/components/Fab.tsx（現状）
const RankingDialog = dynamic(() => import('./ranking/RankingDialog').then((m) => m.RankingDialog))
const ScatterDialog = dynamic(() => import('./scatter/ScatterDialog').then((m) => m.ScatterDialog))
```

一方 `MapShell` の 5 つはすべて `ssr: false` 付きです。**§1.1 の「FAB では起きるが駅詳細では起きない」
という非対称は、この違いだけで説明でき、他に説明のつく差はありません。**

### 2.2 実験で裏付け

`Fab.tsx` を一時的に書き換え、同一ビルド内で 2 通りを比較しました（実装後に元へ戻し済み）。

| 変更 | 全画面スケルトン | 地図は見えているか |
|---|---:|---|
| 現状（何もしない） | **3/3 回** | 隠れる |
| ランキングを `<Suspense fallback={null}>` で包む | **0/3 回** | **見えたまま** |
| 散布図のクリックを `startTransition` で包む | **0/3 回** | **見えたまま** |
| 両方に `loading: () => null` を渡す | **0/3 回** | **見えたまま** |

→ **どの方法でも全画面の奪取は消えます。** 以降は「では待ち時間そのものをどうするか」の話になります。

## 4. 待ち時間の内訳（何に時間を使っているか）

### 4.1 クリックしてからダイアログが出るまで

| 内訳 | ランキング | 散布図 | 備考 |
|---|---:|---:|---|
| チャンクのダウンロード（ローカル） | 50ms | 80ms | 転送 94KB / 157KB |
| メインスレッドの実行（longtask） | 80ms | 138ms | JS の評価・Chart.js の初期化 |
| React の初回レンダ〜表示 | 残り | 残り | ダイアログ本体の構築 |
| **合計（クリック→表示・中央値）** | **約 590ms** | **約 240ms** | 実測のばらつきは大きい |

### 4.2 チャンクの中身（6 本・166KB）

| チャンク | 生サイズ | 転送 | 中身 |
|---|---:|---:|---|
| カタログ＋Zod | 591KB | **78KB** | `catalog.json`（586 件）と検証（**両ダイアログ共通**）|
| Chart.js | 186KB | 65KB | 散布図のみ |
| その他 4 本 | 67KB | 23KB | ダイアログ本体・Radix ほか |

**ランキングと散布図は 2 本を共有**しているため、両方を先読みしても合計は **166KB** で済みます。

### 4.3 回線が細いほど致命的（同じ 6 本を回線別に実測）

| 回線 | 6 本 166KB の取得時間 |
|---|---:|
| ローカル（実質無限） | 約 130ms |
| **4G 相当**（4Mbps / RTT 70ms）| **1,342ms** |
| **3G 相当**（400Kbps / RTT 400ms）| **9,193ms** |

**今はこの時間を「クリックしてから」払っています。** つまりモバイル回線では、
**1.3 秒〜9 秒にわたって「地図を読み込み中」が全画面に出続けます**。
ローカルの 325ms は最良ケースであり、依頼者が見ている体感はもっと悪い可能性があります。

### 4.4 やる価値が無いと分かったこと

カタログ（586 件・231KB）の読み込みコストを実測したところ：

| 処理 | 時間 |
|---|---:|
| `JSON.parse` | **2.4ms** |
| Zod の `catalogSchema.parse` | **5.7ms** |

→ **合計 8ms。** 「Zod の検証を省く」「カタログを間引く」といった最適化は**体感に効きません**。
§5 の候補から外します（根拠なく手を広げないため）。

## 5. 対策の候補と検証結果

### ① 先読み（prefetch）— 依頼の優先度 1「そもそも出さない」

地図が落ち着いたあと、**アイドル時間に**ダイアログのチャンクを取得しておく。

```ts
const loadRanking = () => import('./ranking/RankingDialog')
const RankingDialog = dynamic(() => loadRanking().then((m) => m.RankingDialog), { loading: () => null })
// マウント後、アイドル中に loadRanking() / loadScatter() を呼んでおく
```

**実測（試作ビルド）**：クリック後に取得されるチャンクが **4 本 → 0 本**。
§4.3 の **1,342ms（4G）／9,193ms（3G）がクリック時の待ちから消えます**。

- ⚠ **ローカル計測では体感時間は縮みませんでした**（576ms → 561ms）。
  ローカルは回線が速く、待ちの主因が「React の初回レンダ」だからです。
  **効果が出るのは実際の回線**であり、そこが依頼者の環境です。
- 注意点：166KB を余分に落とすので、**初期表示を邪魔しない時機**に限る必要があります
  （`requestIdleCallback`、かつ `navigator.connection.saveData` や `effectiveType` が細いときは見送る）。

### ② 境界を張る（安全網）— 依頼の優先度 2「気にならない UI に」

★の 5 か所に `loading: () => null` を渡す。**1 行 × 5 か所**。

**実測：全画面スケルトン 3/3 → 0/3。地図は出たまま。**
依頼の「裏が地図の背景であれば、まだ気にならない」に**そのまま一致**します。

これは①が効かない場合（回線が極端に遅い・先読みを見送った・キャッシュが切れた）の**保険**でもあり、
**①と②はどちらか一方ではなく両方入れる**べきものです。

### ③ 待っていることを伝える（`useTransition`）

`startTransition` でダイアログを開くと、React は今の画面を保ったまま裏で準備し、
**`isPending` で「準備中」を受け取れます**。FAB のボタン自身にスピナーを出せば、
「押したのに何も起きない数百 ms」が「押したことは伝わっている数百 ms」になります。

- 実測：全画面スケルトンは **0/3**（②と同じく解消）。
- ⚠ **体感時間そのものが縮むかは、今回の計測では判定できませんでした。**
  同一ビルド内で 284ms（`startTransition` あり）と 1,098ms（なし）でしたが、
  比較対象がランキングと散布図で**中身の重さが違い**、かつ計測機のばらつきが ±500ms あります。
  **「速くなる」とは主張しません。**採る理由は**押した手応えを返せること**です。

### ④ 検討したが採らない案

| 案 | 不採用の理由 |
|---|---|
| Zod の検証を省く／カタログを間引く | **8ms しかない**（§4.4）。効果が無い |
| ダイアログを初期バンドルに戻す | 初期表示が重くなる。260803 で意図的に分けた方針の逆行 |
| `MapSkeleton` の文言を変える（「読み込み中」を消す）| 症状が隠れるだけで、**全画面が奪われる事実は変わらない** |
| `page.tsx` の Suspense を外す | 初期表示の実体 HTML（LCP・a11y）を失う。260803 §7a の設計を壊す |
| `<link rel="prefetch">` を手書き | チャンク名はビルド生成。`import()` で書くのが唯一の保守可能な方法 |

## 6. 推奨：**②（境界）＋①（先読み）を入れ、③（手応え）は任意**

理由は 3 つ。

1. **②だけで依頼の②は満たせる。** 「裏が地図の背景なら気にならない」＝境界を張れば達成（実測 0/3）。
   しかも **5 か所 × 1 行**で、挙動の変更が局所的＝安全。
2. **①が無いと、依頼の①（そもそも出さない）は満たせない。** モバイル回線では
   **1.3〜9.2 秒**の取得が残り、②があっても「押しても何も出ない数秒」になる。
3. **③は速度ではなく手応えの改善。** ①②で残る 200〜300ms に対して「押した」ことを返す。
   効果を数値で示せていないので、**入れるかどうかはご判断**（§10 の決定 3）。

**適用後に期待される姿**（ローカル実測ベース）：

| | 現状 | 適用後 |
|---|---|---|
| 全画面スケルトン | ランキング・散布図・ⓘ で毎回 | **出ない** |
| クリック→表示（ローカル） | 240–590ms | 235–300ms（地図は出たまま） |
| クリック→表示（4G 相当） | ＋1,342ms のチャンク取得 | **先読み済みなら 0ms** |
| 地図の見え方 | 全面が白く覆われる | **ずっと見えている** |

## 7. 変更範囲

| レイヤ | ファイル | 変更 |
|---|---|---|
| UI | `components/Fab.tsx` | ダイアログ 2 つに `loading: () => null`。`import()` を名前付き関数に切り出して先読みと共有 |
| UI | `components/AppHeader.tsx` | AboutDialog に `loading: () => null` |
| UI | `components/chat/PromotionHost.tsx` | ダイアログ 2 つに `loading: () => null` |

**無改変**：`page.tsx` の Suspense、`MapSkeleton`、`app/loading.tsx`、API、DB、ダイアログの中身。

### 7.1 再発防止のテスト

今回の穴は「オプションを書き忘れると静かに壊れる」種類なので、**書き忘れを検出**します。

```
src/**/*.tsx の dynamic( を全数走査し、
  ssr: false でも loading でもないものが 1 つでもあれば失敗
```

§3 の表をテストで固定する形です。新しく `dynamic()` を足した人が、
「境界が無いと全画面が奪われる」ことを知らなくても気づけます。

## 8. 検証計画（受け入れ条件）

本番ビルドをローカル起動し、Playwright で実測します（数値は §1・§4 と同じ手順で比較可能）。

1. **全画面スケルトンが出ない**：ランキング・散布図・ⓘ を各 3 回 → **0/3**（現状 3/3）。
2. **地図が隠れない**：クリックから表示まで `main` が `display:none` にならず、
   `canvas.maplibregl-canvas` の可視幅が 0 にならない。
3. **先読みが効いている**：ページ表示から一定時間後にクリックしたとき、
   **クリック後に新規取得されるチャンクが 0 本**。
4. **初期表示を悪化させない**：先読みを入れる前後で、初期表示の転送量とチャンク本数、
   および LCP が悪化していない（先読みはアイドル後に走ること）。
5. **細い回線で見送る**：`saveData` 相当の条件で先読みが走らないこと。
6. 品質ゲート：`typecheck` / `lint` / `test` / `build`。

## 9. リスク

| リスク | 対応 |
|---|---|
| 先読みが初期表示の帯域を奪う | `requestIdleCallback`（＋タイムアウト）で地図の後に回し、細い回線では見送る。§8-4 で検証 |
| `loading: () => null` により「押しても無反応」に見える | ③（`useTransition` で FAB にスピナー）を採るかを §10 で決める |
| `dynamic` の内部仕様（`hasSuspenseBoundary`）が将来変わる | 依存しているのは**公開オプション**（`loading`）であり、内部実装ではない。§7.1 のテストで検出 |
| 先読みしたチャンクが古くなる（デプロイ直後）| Next のチャンクはハッシュ付き。取得失敗は `catch` で握りつぶし、クリック時に再取得される |

## 10. ご確認いただきたい決定事項

| # | 論点 | 選択肢 | 推奨 |
|---|---|---|---|
| 1 | **境界を張る（②）** | 5 か所すべてに入れる／FAB の 2 つだけ | **5 か所すべて**（ⓘ でも再現済み。同じ穴を残す理由がない）|
| 2 | **先読み（①）** | 入れる（アイドル＋細い回線では見送る）／入れない／ホバー時だけ | **入れる**。依頼の優先度 1 に直接効き、4G で 1,342ms・3G で 9,193ms を消せる |

### 11.3 再発防止（`tests/dynamic-suspense-boundary.test.ts`）

### 11.4 残っている制約（正直な注記）

- **先読みは best-effort です。** 完了は読み込み後 2.5–5.9 秒。それより早くクリックすると
  チャンク取得を待ちます（このときも①の境界により**全画面は奪われません**）。
- **クリック→表示の時間そのものは、ローカル計測では縮んでいません。** 待ちの主因は
  React の初回レンダで、先読みが取り除くのは**チャンク取得**（4G 相当で 1,342ms・
  3G 相当で 9,193ms）です。効果が出るのは実回線です。
- `useTransition` による「押した手応え」は**決定 3 により入れていません**。
