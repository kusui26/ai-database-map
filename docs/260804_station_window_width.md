# 駅詳細ドロワーの横幅を広げ、カテゴリのタブを既定でスライド不要にする（実装プラン）

作成日: 2026-08-04 ／ 対象: 駅詳細ドロワー・AI チャットパネル・地図の flyTo 余白・キャンバス
／ 依頼: 「駅をクリックしたときの右側のウィンドウで、**乗降客数・人口・地価などのバーが既定で横スライドになる**のが気になる。もう少し横幅を広げて、既定ではスライド不要にしたい。画面サイズによってスライドが要るのは問題ない。**AI チャットと横幅を合わせている場合は、それも含めて最適な幅**を考えてほしい」

> §1–§5 が調査と設計、**§6 がご確認いただきたい決定事項**。数値はすべて 2026-08-04 の実測（本番）。

---

## 0. エグゼクティブサマリ（結論先出し）

- **原因は単純で、24px 足りないだけ**。タブ帯は **404px** 必要なのに、ドロワーの幅が **380px**。
  実測したすべての画面幅（1280〜1920px）で **24px はみ出し**、常にスライドが必要な状態だった。
- **チャットとは「合っていない」**：チャット **400px** ／ ドロワー **380px** と 20px ずれている。
  依頼の「合わせている場合は…」に対する答えは **「今は合っていないので、この機会に揃える」** を推奨。
- **推奨は両方 420px**。タブが **16px の余裕**をもって収まり、2 枚のサイドパネルが同じ幅で揃う。
  地図の可視幅は現状比 **−60px**（1440px 画面で 636 → 576px）にとどまり、キャンバスは 1440px 以上で影響なし。
  <br>※ 初版はここを「−40px」と書いていたが**算術ミス**（ドロワー +40px に加え、チャットも 400 → 420px と
  +20px 広がる）。§3.1 の表の数値は当初から正しく、**差は全画面幅で 60px**。§4 も同様に訂正した。
- **副次的にコードの重複も解消できる**。パネル幅は現在 **6 か所**にバラバラの数値で埋め込まれており
  （`400` / `380` / `424` / `404` / `420`）、片方だけ直すと **flyTo が駅をパネルの裏に置く**などのズレが起きる。
  **1 か所の定数**に集約する。

## 4. 推奨：**チャットもドロワーも 420px に揃える（案B）**

理由は 3 つ。

1. **タブが 16px の余裕をもって収まる。** 404px ちょうどでは、フォントの微差や文言変更で
   すぐ再発する。16px あれば実用上の変動を吸収できる。
2. **2 枚のサイドパネルが同じ幅になる。** 現状の 400/380 は 20px ずれており、揃えることで
   「意図した設計」に見える。依頼の「チャットと合わせているなら、それも含めて」への答え。
3. **1 つの定数にできる。** §2 の 6 か所を `PANEL_WIDTH_PX = 420` に集約でき、
   flyTo・キャンバス・FAB のズレという**バグの温床を断てる**。

**代償は地図の可視幅 −60px**（1440px で 636 → 576px。内訳はドロワー −40px ＋ チャット −20px）。地図は主役なので軽視できないが、
サイドパネルを 2 枚開いている状態は「データを読んでいる」場面であり、40px の差より
**タブが毎回スライドする煩わしさの解消**が上回ると判断した。

### 4.1 画面が狭いときは従来どおりスライドする

`w-[min(420px, calc(100%-1.5rem))]` の形は維持する。したがって：

- **画面幅 444px 未満**ではドロワーが 420px 未満になり、タブは**スライドする**
- **モバイル（640px 未満）** はボトムシート（全幅）で、375px 端末ならタブはスライドする

依頼の「画面サイズによってスライドが必要な場合はスライドで問題ない」に沿う。

### 4.2 検討したが採らない案

| 案 | 内容 | 不採用の理由 |
|---|---|---|
| タブの余白を詰める（`px-3` → `px-2.5`）| 帯を 404 → 380px に縮め、幅を変えずに収める | 依頼は「幅を広げたい」。**タップ領域が小さくなる**副作用があり、狭い画面では結局スライドする |
| ドロワーだけ 420px（案A）| チャットは 400px のまま | 20px のズレが残り、定数も 1 つに集約できない |
| 両方 440px（案C）| さらに余裕 | 地図が現状比 −100px。タブには 36px も要らない |
| タブを 2 段に折り返す | スライドを無くす | 縦を消費し、`overflow-x-auto` の設計と食い違う |

### 4.3 将来「将来推計人口」タブを足す場合（参考）

`DETAIL_TABS` は 7 カテゴリ中 6 つ。`population_forecast`（**将来推計人口**・7 文字 ≈ 122px）を
足すと帯は **約 526px** 必要になり、420px でも**スライドが復活**する。
その時点で「タブを短い表記にする」「2 段にする」等を別途検討する。**今回は対象外**。

## 7. 実装結果（2026-08-04）

### 7.1 実装した内容

`src/shared/constants.ts` に **3 つの定数**を置き、§2 の 6 か所すべてをそこから算出するようにした。

```ts
export const PANEL_WIDTH_PX = 420
export const PANEL_GAP_PX = 12   // Tailwind の `left-3` / `right-3` と同値
export const PANEL_WIDTH_CSS = `min(420px, calc(100% - 24px))`
```

| ファイル | 変更前 | 変更後 |
|---|---|---|
| `chat/ChatPanel.tsx` | `w-[min(400px,…)]`（クラス）| `style={{ width: PANEL_WIDTH_CSS }}` |
| `detail/StationDetailPanel.tsx` | `w-[min(380px,…)]`（クラス）| `style={{ width: PANEL_WIDTH_CSS }}` |
| `map/MapView.tsx` | `CHAT_PANEL_PX = 400` / `DRAWER_PANEL_PX = 380` | 両方 `PANEL_WIDTH_PX` |
| `canvas/ChatCanvas.tsx` | `424` / `12` / `404` / `12` | すべて `PANEL_GAP_PX` と `PANEL_WIDTH_PX` から算出 |
| `Fab.tsx` | `left: 420`（偶然の一致）| `PANEL_GAP_PX + PANEL_WIDTH_PX + FAB_GAP_PX` |

Tailwind の任意値クラスは**ビルド時に文字列を走査**して CSS を生成するため、実行時の定数からは
組み立てられない。そのため幅だけ `style` に移した（位置・余白のクラスはそのまま）。

| 639px | 639px | 収まる | スライドなし |

### 7.3 再発防止（`tests/panel-layout.test.ts`）

数値がまた 6 か所に散らないよう、**定数そのものに不変条件**を張った。

1. タブ帯の内訳（80＋52＋52＋52＋66＋66 ＋ gap 20 ＋ 余白 16）が **404px** になる
2. `PANEL_WIDTH_PX > 404`（＝既定でスライドしない）
3. 余裕が **16px 以上**（文言やフォントの微差で再発しない）
4. タブに使うカテゴリのラベルが実測時から変わっていない（変われば帯が広がるため）
5. `PANEL_WIDTH_CSS` が `PANEL_WIDTH_PX` と `PANEL_GAP_PX` から導出され、余白が `*-3`（12px）と一致する

4 は「ラベルを変えたら幅を測り直す」ことを強制するための番人。§4.3 の
**将来推計人口タブ**を足すと 2 と 3 が落ちるので、その時点で幅の再検討が必要だと気づける。

### 7.4 依頼との対応

| 依頼 | 結果 |
|---|---|
| バーが既定で横スライドするのが気になる | **解消**（640〜1920px で余裕 16px）|
