## 0. サマリ（結論先出し）

### 0.1 何を作るか

**「今いる場所・気になる場所が、水害でどうなるか」を、地図とAIで誰でも分かるようにする。**
既存アプリの主役は「駅 × 半径の統計」だが、水害は**その一点の話**であり、平均に溶かした瞬間に意味を失う。
そこでご指定のとおり、**メッシュ（＝空間そのまま）で扱う**。駅×半径のカラムは原則作らない。

到達点は 5 段階（§8）で、ご意見の「**少なくとも最初の段階では、アラートが出るような状況になったら危ないところを把握できるだけでも良い**」を Phase 1–3 に正確に対応させた。
**§12 の 8 つの決定は 2026-08-25 に合意済み**で、下表と §8 はその決定を反映した確定版である。

| Phase | 何ができるか | 中心となるデータ |
|---|---|---|
| **0** | 土台（レイヤカタログ・プロトコル拡張） | — |
| **1a** | **ハザードを地図に重ねて見える化**（洪水・内水・高潮・津波・土砂）＋ **地形グループ**（内水の空白を埋める・§3.7） | 重ねるハザードマップの地理院タイル ＋ 治水地形分類図・色別標高図・傾斜量図 |
| **1b** | **自前 250m メッシュ化**（既存の人口メッシュと同じ格子）＋地点の意味づけ | 国土数値情報 **A31a（洪水）・A51（内水）** ＋ 標高 G04-d ＋ 浸水ナビ API |
| **2** | **GPS 連携**（現在地のメッシュ判定・周囲の危険・オフライン動作） | 1b の成果物 ＋ Geolocation API |
| **3** | **アラート**（警報 JSON で「警戒レベル◯相当」を判定・キキクルは面の表示） | 気象庁 警報 JSON（判定）／キキクル タイル（表示） |
| **4** | **AI 連携**（「今どうすべき？」「どこに逃げる？」に答える） | 指定緊急避難場所（skhb01–08）＋ 既存 Gemini ツール |
| **5**（将来） | **移動体の回避**（行ってはいけない面・脱出方向・高台の駐車可能施設） | メッシュ距離変換 ＋ 道の駅 P35 等 |

### 0.2 実測して分かったこと（§4 に詳細）

自分で測った。**2020 年国勢調査の 250m メッシュ（人口>0：1,163,757 メッシュ／合計 126,146,099 人＝公表値と一致）を母集団に一様無作為抽出し、重ねるハザードマップのタイル画素で判定した。**

| ハザード | メッシュの何% | **人口の何%** |
|---|--:|--:|
| **洪水浸水想定区域（想定最大規模 L2）** | **28.7%** | **45.8%** |
| 洪水浸水想定区域（計画規模 L1） | 15.5% | 26.0% |
| 家屋倒壊等氾濫想定区域（氾濫流） | 2.5% | 3.0% |
| 高潮浸水想定区域 | 4.3% | 10.0% |
| 津波浸水想定 | 3.3% | 4.3% |
| 土砂災害警戒区域（土石流） | 7.0% | 2.2% |
| 雨水出水（内水）浸水想定区域 | 0.4% | 1.3% |

- **日本人の 4 割超が、想定最大規模の洪水浸水想定区域に住んでいる。** これがこの機能の存在理由そのものになる。
- 土石流は「メッシュ 7.0% ＞ 人口 2.2%」＝**人の少ないところに広い**。高潮は「メッシュ 4.3% ＜ 人口 10.0%」＝**人の多いところに集中**。同じ「面積」でも意味がまるで違う。この対比は既存アプリの強み（人口メッシュ）と掛け算したときにだけ出せる。
- 先行研究（秦・前田 2020：計画規模・2015 年で 35,391,931 人＝全人口の 27.8%）と、こちらの L1 実測 26.0% がほぼ一致した。**測り方が妥当だという外部検証になっている。**
- **内水の 0.4% は実態ではなく整備状況**。A51 の収録は **47 都道府県中 22**（大阪も京都も丸ごと無い）。一方で**過去 10 年の水害被害額の約 4 割は内水**（東京都では約 7 割）。**被害額 4 割のハザードが、地図としては人口の 1.3% しかない**——この非対称性を地形レイヤで埋める（§3.7）。

### 0.3 いちばん大事な設計判断（3 つ）

1. **メッシュを一級市民にする。** 250m メッシュコードは緯度経度から**純関数**で計算できる。だから「現在地が危ないか」は
   PostGIS も通信も要らず **O(1) の配列参照**で答えられる。これは GPS 連携（Phase 2）と、通信が細る発災時（Phase 3）で決定的に効く。
   既存の人口メッシュと**同じ格子**なので、「浸水域内人口」のような掛け算がタダで手に入る。
2. **判定用データは DB に置かず、静的アーティファクトにする。** 容量（実測 452MB／無料枠 500MB）は入れられない理由だが、
   **入れないほうが良い理由は別にあり、有料プランにしても変わらない**（オフラインで引けない・年 1 回更新の不変データ・アクセスパターンが DB 向きでない）。
   ハザードは **1 次メッシュ単位のバイナリ**として CDN から配り、DB は 1 バイトも増やさない。
   ただし**「DB を使わない」ではなく「ワークロードで分ける」**：任意半径の面積計算や集計クエリは DB が向く（§5.3）。
3. **意味は全部サーバのカタログに置く。** 「この色は何 m か」「この色ならどうすべきか」を**レイヤカタログ**に日本語で持たせ、
   凡例 UI と Gemini が**同じ 1 つのテキスト**を読む。フロントに凡例を直書きした瞬間に AI から消費不能になる（CLAUDE.md §2 のアンチパターン）。

### 0.4 正直に言っておくこと

- 「**路上駐車できる道路**」を判定できる公開データは存在しない（可否は道交法と標識で決まり、GIS 化されていない）。
  災害時の路上駐車は緊急車両の妨げにもなるため、**このアプリは路駐を勧めない**。代わりに Phase 5 では
  「浸水域外」「標高が高い」「指定緊急避難場所・道の駅・都市公園など、駐車できる公共施設」に誘導する（§8.6・§11）。
- **警戒レベル4（避難指示）そのものは無料では取れない**（発令は市町村、配信は L-Alert で一般公開なし）。
  ただし気象庁が出す「**警戒レベル4相当**」（氾濫危険情報・土砂災害警戒情報・キキクル「紫」・高潮警報）は**無料で取れる**。
  アプリはこれを使い、「レベル4相当の情報が出ています／避難情報は市町村の発表を確認してください」と**正直に**表示する（§3.3・§7.5）。
- **リアルタイムの河川水位は有償**（水防災オープンデータ提供サービス・河川情報センター）。無料の範囲では気象庁のキキクルが上限（§3.6）。
- **内水の想定区域図は、まだ全国の半分にも無い。** 指定するのが約 1,700 の市町村で、下水道の管路モデルが要るためである。
  「白いから安全」と読ませないために、**治水地形分類図・色別標高図・低位地帯といった地形レイヤで空白を埋める**（§3.7）。
  ただし地形は「危険の証明」ではないので、**立退き／垂直避難の判定には使わない**。

## 1. ご意見を設計要件に翻訳する

> 「google map がすぐ対応しそうだけど、水害のリスクが有る低地情報を持っておいて、レベル4になった段階で
> カーナビではそこにいかないようにして安全な駐車場、路駐できる道路に誘導するような機能がそろそろ必要になる。
> 少なくとも最初の段階では、アラートがでるような状況になったら危ないところを把握できるだけでも良い。
> そうすればそこを回避して安全なところにいくことができます」

ここから読み取れる要件を分解する。

| # | ご意見の要素 | 要件 | 実装 Phase |
|---|---|---|---|
| R1 | 「水害のリスクが有る低地情報を**持っておいて**」 | ハザードと標高を**自前で保持**し、通信が細っても引ける | 1b |
| R2 | 「レベル4になった段階で」 | **今の警戒度**を取り込み、平時↔警戒でアプリの見え方が変わる | 3 |
| R3 | 「そこに**いかない**ように」 | 危険な面を**避けるべき領域**として明示（点ではなく面） | 1a → 5 |
| R4 | 「安全な駐車場・路駐できる道路に**誘導**」 | 安全な**行き先**を提示（自前ルーティングはしない） | 4 → 5 |
| R5 | 「**危ないところを把握できるだけでも良い**」 | ← **これが MVP の輪郭**。把握 = 見える化 ＋ 現在地 ＋ 警戒度 | 1〜3 |
| R6 | 「回避して安全なところにいく」 | 「どっちに逃げるか」＝**方向**の提示 | 5 |

**MVP は R5。** R3/R4/R6 は R5 の上に素直に積み上がるので、Phase 1 の実装は最初から R6 を見据えた形（＝メッシュ）で作る
（CLAUDE.md「Step1 の実装は常に Step2 を見据える」の同じ思想）。

### 1.1 このアプリがやる意味（Google マップとの差）

Google マップは「今どこにいるか」と「どう行くか」は強いが、**「その場所が将来どうなるか」の統計を持っていない**。
本アプリは既に**人口・所得・売上・地価を同じ格子で持っている**。だから水害を足すと、他にない組み合わせが出る。

- 「この駅の周辺は、想定最大規模で**何人が浸水域に入るか**」
- 「浸水域内の人口が**増えている**駅はどこか」（＝リスクの高い土地の宅地化。秦・前田 2020 の指摘そのもの）
- 「浸水深 3m 以上の区域に、**事業所が何件あるか**」

これは Google マップが持たない資産の上でしか作れない。Phase 1b の副産物として自然に出る（§5.5）。

## 2. なぜ「メッシュのまま」が正しいのか

ご指定の「データはメッシュのまま使う」は、この機能では**単なる好みではなく、設計上ほぼ必然**である。理由を明示しておく。

### 2.1 駅×半径は「平均の道具」で、水害は平均で語れない

既存の 806 列は「半径 1km の人口」のように**面積按分した平均・合計**である。水害でこれをやると：

- 「半径 1km の平均浸水深 0.8m」は、**誰の役にも立たない数字**になる。同じ円の中に浸水 0m の台地と 5m の低地が同居する。
- 駅の代表点が高台にあるだけで、駅の東側全部が 3m 浸水でも「安全」に見えてしまう。**安全側に倒れない**（＝人が死ぬ側に倒れる）。

したがって、**水害だけは既存カラム体系に入れない**。これは既存設計への例外ではなく、`dataset.md` の集約パラダイム表に
「**メッシュ（集約しない）**」という行を 1 つ足すこと、と理解するのが正しい。

### 2.2 メッシュコードは緯度経度の純関数である ＝ 現在地判定が O(1)

標準地域メッシュは緯度経度から四則演算だけでコードが出る（`population_mesh.md` §8.2 の逆変換）。つまり：

```
(lon, lat) ──純関数──> 250m メッシュコード ──配列参照──> 浸水深ランク
```

- **PostGIS も空間インデックスも要らない。** サーバ往復も要らない。
- **オフラインで動く。** 発災時は通信が最も細る。1 次メッシュ 1 枚（南北約 74km ×東西約 91km）ぶんのバイナリ
  （後述 51,200 バイト）を端末に持てば、圏外でも現在地の危険度が出る。これは**ポリゴンでは絶対に真似できない**性質である。
- **バグりにくい。** ポリゴン内外判定は境界条件が地獄だが、格子の添字計算は単体テストで全数近く検証できる（CLAUDE.md §3「境界値を厚く」）。

### 2.3 既存の人口メッシュと同じ格子だから、掛け算が無料になる

既存パイプラインは 2015/2020 年の**250m メッシュ**人口を持ち（`data/国勢調査_人口及び世帯_2020_mesh250`）、
将来推計人口（R6・250m）も同じ格子である。ハザードを同じ 250m 格子に載せれば、**結合キーがメッシュコードだけ**になり、
面積按分も空間結合も不要で「浸水域内人口」「浸水域内の将来人口」が出る。§4 の実測はこれを先取りして手で確かめたものである。

### 2.4 既存ドキュメントの「予定」からの変更点（明示しておく）

`dataset.md` は既に災害リスクを次の候補に挙げており、集約パラダイムを

> **（将来）ポリゴン（災害リスク）＝半径円との重なり面積率** ＝ 新パラダイム
> （`dataset.md` §3「集約パラダイム」・§4「次の候補」）

と予告している。**本プランはこれを主表現から降ろす。** 理由は §2.1 のとおりで、
「半径円との重なり面積率」は**エリアの傾向を比べる**には良いが、**目の前の一点が危ないか**には答えられないからである。

ただし**捨てるわけではない**。予告されていた「重なり面積率」は、
メッシュを持てば `flood_area_ratio_{R}`（半径内メッシュのうち浸水域の割合）として**引き算なしで導ける**（§5.5）。
つまり **メッシュが下位互換の土台になり、面積率はその派生**という関係に整理する。
`dataset.md` §3 の集約パラダイム表は、実装時に

- **メッシュ（災害リスク）＝集約しない**（主表現）
- **半径円との重なり面積率**（派生・任意）

の 2 行に書き換える。

### 2.5 公式タイルだけでは足りない理由と、「ズレ」を起こさない置き方

#### メッシュを持たず公式タイルだけにしたら、何ができないか

タイルは**画像**なので、原理的にできないことが 4 つある。

| できないこと | なぜ困るか |
|---|---|
| **オフラインで引けない** | タイルは「いま見ている範囲」しかキャッシュされない。避難で要るのは自分の周囲数十 km で、それを z14 タイルで持つと **1 次メッシュ相当の範囲で約 1,700 枚**（経度方向 45.5 × 緯度方向 37.4・北緯 35 度）。同じ範囲がメッシュなら **51,200 バイト・1 リクエスト**。通信が細る発災時にここが効く |
| **面の計算ができない** | 脱出方向（格子上の距離変換）・浸水域内人口・駅ごとの集計・ランキング。画像からは 1 つもできない |
| **AI に渡せない** | 「この駅で浸水域に入る人口は？」に答えられない。画像は LLM から消費不能で、CLAUDE.md §2 が禁じるアンチパターンそのもの |
| **複数レイヤの合成判定ができない** | 「3m 以上 **かつ** 家屋倒壊区域 **かつ** 継続 72h 以上」を 3 枚の画像の画素突き合わせでやるのは非現実的（家屋倒壊は minzoom 4、他は 2 で解像度も揃わない） |

「点の値なら浸水ナビ API で取れるのでは」は部分的に正しい。ただし浸水ナビは
① **洪水（河川氾濫）だけ**で内水・高潮・津波・土砂を含まない、② **分間 30 リクエスト**なので 9,273 駅の一括判定に使えない、
③ 外部依存なので発災時に落ちたら終わり。**この 3 つを埋めるのがメッシュ**である。

#### ズレは「見せない」のではなく「起こさない」

250m に丸めると、実際には浸水しない高台の一部まで塗られる（＝**過大表示**）。安全側ではあるが
「うちは浸水しないはずなのに赤い」という不信を生む。**そこで、メッシュは画面に出さない。**

| 役割 | 使うもの | 解像度 |
|---|---|---|
| **表示**（地図の色） | 重ねるハザードマップの**公式タイル** | 原典 |
| **地点の数値**（◯m・◯分後） | **浸水ナビ API**（m 単位）を第一、メッシュはフォールバック | 原典 |
| **判定・集計・方向・オフライン** | 自前 **250m メッシュ**（**画面に出さない**） | 250m |

こうすると表示・数値・計算の 3 つが原典解像度で揃い、**ズレが「見えない」のではなく「起きない」**。
メッシュは**表示レイヤではなくインフラ**という位置づけになる（この整理により、レイヤ制御の「メッシュ表示」トグルは**不要**になった・§7.1）。

**メッシュを画面に出してよいのは 2 つの例外だけ**。
① **統計の面表示**（例「市区町村ごとの浸水域内人口」のコロプレス）——地点の危険判定ではなく統計だと文脈で分かる。
② **Phase 5 の「行ってはいけない範囲」**（§8.6）——警戒時は「何 m か」より「近づくな」が優先で、250m の粗さがむしろ安全側に働く。
どちらも「粗いこと自体が問題にならない」用途である点が共通している。

### 3.7 内水は「地図が薄い」——何が起きていて、地形でどう補うか

**内水（雨水出水）氾濫**＝川が溢れる前に、降った雨が下水道・排水路の処理能力を超えて街に溜まる浸水。
マンホールから噴き出す、地下街・アンダーパスが浸かる、という現象で、**都市部で近年のゲリラ豪雨の主役**である。
実測が 0.4%（人口 1.3%）と極端に低いのは**実態ではなく整備状況**なので、その中身をここに書いておく。

#### なぜ地図が薄いのか（3 つの構造的な理由）

| | 洪水（A31a） | **内水（A51）** |
|---|---|---|
| 指定するのは | **河川管理者**＝国 ＋ 47 都道府県（少数） | **市町村**（下水道管理者）＝約 1,700 |
| 制度 | 2015 年改正で想定最大規模へ。**2021 年改正で全ての一級・二級河川が対象**に | 2015 年に「雨水出水浸水想定区域」創設だが**当初は水位周知下水道のみ**。**2021 年改正でようやく対象拡大**（下水道の浸水対策を行う全団体へ）＝まだ進行中 |
| 計算 | 河道と地形から氾濫解析 | **下水道の管路網モデル**を作らないと計算できない（費用・技術とも重い） |

洪水は「47 都道府県が作れば全国が埋まる」構造だが、内水は「**1,700 市町村がそれぞれ管路モデルを作る**」構造なので、進み方が桁で違う。

**国土交通省の実績値**（社会資本整備審議会 下水道小委資料「近年の降雨及び内水被害の状況、下水道整備の現状について」2019-12）：

- 内水ハザードマップの早期作成が必要な **484 地方公共団体のうち 361 団体**が公表済（ただし「**既往最大規模**」降雨）
- 内水浸水で人命への影響が懸念される**地下街を有する 20 団体のうち、想定最大規模降雨で公表済は 1 団体のみ**

A51 が収録するのは**想定最大規模**のほうなので、出発点がほぼゼロだったことが分かる。

**現在の到達点（A51 2025年度版のダウンロード一覧を数えた）**：**47 都道府県のうち 22 のみ**。

- 収録あり：北海道・青森・宮城・群馬・埼玉・千葉・東京・神奈川・富山・石川・福井・長野・愛知・兵庫・鳥取・島根・岡山・広島・山口・香川・愛媛・福岡
- **丸ごと無い（25 府県）**：**大阪・京都**・静岡・新潟・岐阜・三重・滋賀・奈良・和歌山・岩手・秋田・山形・福島・茨城・栃木・山梨・徳島・高知・佐賀・長崎・熊本・大分・宮崎・鹿児島・沖縄

**大阪府が丸ごと白いのは、大阪に内水氾濫がないという意味ではない。** 国土数値情報の注記も、自らこう書いている。

> ・本データは水防法に基づいて指定された雨水出水浸水想定区域**及び区域指定前であっても既に想定最大規模降雨における
> 　内水浸水想定区域図が作成されておりホームページ等で公表されている範囲**です。
> ・**実際の雨水出水（内水氾濫）浸水区域はこの雨水出水（内水）浸水想定区域よりも広い場合があります。**
> （国土数値情報 A51「その他の情報」）

#### それなのに、被害の 4 割は内水である

| 指標 | 値 | 出典 |
|---|---|---|
| **過去 10 年の全国の水害被害額 約 1.8 兆円のうち内水の割合** | **約 4 割** | 国交省・前掲資料 |
| **東京都では** | **約 7 割** | 同 |
| 都市浸水対策達成率（対策が完了した面積の割合） | 約 59%（平成30年度末） | 同 |
| 内水氾濫等による浸水戸数のうち、下水道整備が途上の地区で発生した割合 | 約 9 割 | 同 |

**被害額の 4 割を占めるハザードが、地図としては人口の 1.3% しかカバーされていない。**
この非対称性が、§7.5「白は『想定なし』であって『安全』ではない」の**最大の実例**である。

#### 地形で補う（新しい設計要素）

内水は**地形が効く**——周囲より低い・水が集まる・排水先が遠い。だから**想定区域図が無い地域でも、
「ここは水が集まりやすい地形です」とは言える**。ハザードの空白を、地形レイヤで埋める。

| 補完レイヤ | 出典 | 形式 | 何が分かるか | 実アクセス |
|---|---|---|---|---|
| **治水地形分類図** | 地理院タイル `lcmfc2` | ラスタタイル | **旧河道・後背湿地・氾濫平野**＝水が集まってきた歴史そのもの。内水の説明力が最も高い | ✅ 200 |
| **土地条件図** | 地理院タイル `lcm25k_2012` | ラスタタイル | 地形分類（台地・低地・盛土・切土） | ✅ 200 |
| **色別標高図** | 地理院タイル `relief` | ラスタタイル | 相対的な低さを面で | ✅ 200 |
| **傾斜量図** | 地理院タイル `slopemap` | ラスタタイル | 平坦＝水が抜けない場所 | ✅ 200 |
| **低位地帯 G08** | 国土数値情報（商用可） | ポリゴン | 「周辺より低く排水が困難」＋想定最大浸水深。**定義そのものが内水の説明** | — |
| **標高 250m メッシュ G04-d** | 国土数値情報（商用可） | メッシュ | 平均／最低標高・海面下フラグ。自前メッシュに同梱（§5.3） | — |

**扱い方（ここを間違えると危ない）**

1. **これらはハザードではない。** 浸水想定ではなく地形である。カタログの `group` を **`terrain`** にして
   洪水・内水と**別グループ**に置き、凡例でも「**参考：地形**」と明示する。根拠の質が違うものを同じ見え方にしない。
2. **`verdict`（立退き／垂直避難の判定・§6.2）には使わない。** 地形は「危険の証明」ではないため。
3. **使うのは「空白を埋める一文」まで**。想定区域図が無い市区町村で、`/api/hazard/point` がこう返す：

   > この市区町村には内水（雨水出水）の浸水想定区域図が**まだありません**。ただしこの地点は**低位地帯**で、
   > 周囲より約 2.1m 低く、**旧河道**にあたるため、大雨時に水が集まりやすい地形です。

   ——「安全」とも「危険」とも言わず、**判断材料を足す**。これが誠実な埋め方である。
4. **Phase 1a でタイルだけで出せる**（治水地形分類図・色別標高図・傾斜量図）。**データ整備ゼロで内水の空白を減らせる**ので、
   Phase 1a のレイヤ一覧に「地形」グループを最初から入れる。

> 地理院タイルは基本測量成果を含め、「**ウェブサイトやソフトウェア、アプリケーション上でリアルタイムに読み込んで利用する場合、
> 出典の明示のみで申請不要**」（地理院タイル一覧「ご利用について」）。出典は「国土地理院」または「地理院タイル」等と記載する。

## 4. 実測：全国の水害曝露を測った（2026-08-24）

**プランに書く数字は、可能な限り自分で測る**（`docs/260816_sales.md` と同じ流儀）。

### 4.1 手法

1. **母集団**：`data/国勢調査_人口及び世帯_2020_mesh250` の全 304 ファイルから、2020 年国勢調査 250m メッシュの
   「人口（総数）」を読み、**人口 > 0 の 1,163,757 メッシュ**を得た。**合計人口 126,146,099 人＝2020 年国勢調査の公表総人口と一致**（検算）。
2. **標本**：固定シードで一様無作為抽出（洪水 L2・内水・高潮・津波は n=1,200、計画規模・家屋倒壊・土石流は n=600）。
3. **判定**：各メッシュの**重心**の緯度経度を Web メルカトルの画素座標に変換し、**重ねるハザードマップの z14 タイルの当該画素**の
   アルファ値 > 0 なら「区域内」とした。
4. **妥当性**：同じ 400 メッシュを **z14 と z16 で二重測定**し、z14 26.25% / z16 27.25%（人口 44.58% / 45.53%）と一致することを確認した。
   → **ズーム由来の描画膨張バイアスは無視できる。**

### 4.2 結果

| レイヤ | n | メッシュ % | 95%CI | 人口 % |
|---|--:|--:|--:|--:|
| 洪水浸水想定区域（**想定最大規模 L2**） | 1,200 | **28.7** | ±2.6pt | **45.8**（±6.8pt） |
| 洪水浸水想定区域（計画規模 L1） | 600 | 15.5 | ±2.9pt | 26.0 |
| 家屋倒壊等氾濫想定区域（氾濫流） | 600 | 2.5 | ±1.3pt | 3.0 |
| 高潮浸水想定区域 | 1,200 | 4.3 | ±1.2pt | 10.0 |
| 津波浸水想定 | 1,200 | 3.3 | ±1.0pt | 4.3 |
| 土砂災害警戒区域（土石流） | 600 | 7.0 | ±2.0pt | 2.2 |
| 雨水出水（内水）浸水想定区域 | 1,200 | 0.4 | ±0.4pt | 1.3 |

人口 % は**比推定量**（Σ人口×該当 ÷ Σ人口）なので信頼区間はメッシュ % より広い。
L2 について線形化法で分散を計算すると **45.8% ± 6.8pt（95%CI・n=1,200）**＝**39〜53%**。
「4 割超」は言えるが、「45.8%」と小数第 1 位まで断言はしない、という精度である。他レイヤの人口 % も同程度の幅を見込む。

### 4.3 読み取れること

- **想定最大規模では、人口の 45.8% が浸水想定区域内**。メッシュ比 28.7% を大きく上回るのは、**人が住む場所ほど低地だから**。
  日本の都市が沖積平野の上に載っているという地理そのものが数字に出ている。
- **計画規模との差が大きい**（26.0% → 45.8%）。「想定最大規模」は 1000 年に一度級であり、
  さらに 2021 年の水防法改正で**全ての一級・二級河川**が対象に拡大された。**「昔のハザードマップは白かった」は今や通用しない**という
  メッセージが、この 2 つの数字だけで言える。
- **土石流はメッシュ 7.0% に対し人口 2.2%**（人が少ないところに広く分布）、**高潮はメッシュ 4.3% に対し人口 10.0%**（人が多いところに集中）。
  **同じ面積でも人口曝露はまるで違う。** これは既存の人口メッシュと掛けないと絶対に出ない。
- **内水が 0.4% と極端に低いのは、実態ではなく整備状況**（A51 の収録は **47 都道府県中 22**・大阪も京都も丸ごと無い）。
  一方で**過去 10 年の全国の水害被害額 約 1.8 兆円のうち約 4 割が内水**（東京都では約 7 割）である。
  → **被害額の 4 割を占めるハザードが、地図としては人口の 1.3% しかカバーされていない。**
  この非対称性は §7.5「白＝安全ではない」の最大の実例で、**地形レイヤで空白を埋める**設計が要る（**§3.7**）。

### 4.4 先行研究との照合（外部検証）

秦康範・前田真孝「全国ならびに都道府県別の洪水浸水想定区域の人口の推移」（災害情報 No.18-1, 2020）は、
500m メッシュ国勢調査 × 国土数値情報浸水想定区域（**計画規模**）で、**2015 年の区域内人口 35,391,931 人**（全人口比 **27.8%**）と算出している。

**こちらの計画規模の実測は 26.0%。** データ年次（2012年度版 vs 2025年度版）と解像度（500m vs 250m）が違うにもかかわらず
1.8pt しか違わない。**測り方が妥当であることの外部検証**として十分である。
同論文は「区域内人口が減っている県でも区域内**世帯数**は 47 都道府県すべてで増加」＝**浸水リスクの高い地域の宅地化が進んでいる**と指摘しており、
これは §1.1 で挙げた「浸水域内人口の推移」機能の裏づけになる。

### 4.5 容量の見積り（この数字から出る）

- 人口 > 0 のメッシュ 1,163,757 のうち L2 浸水域は **約 33.4 万メッシュ**。
- これに人が住んでいない浸水域（河川敷・農地・工業地）を足すと、**全国でおよそ 50〜60 万メッシュ**（≒ 3.1〜3.7 万 km²・国土の 8〜10%）と見込む。
  ※ この外挿だけは実測ではないので、Phase 1b で**実データから確定**する（§10）。
- **Supabase に入れる場合**：ハザード 6 種＋標高を 1 行にまとめても、標高は全メッシュに要るので約 150 万行 × 約 70 バイト ＝ **約 105MB**。
  **現在 452MB／500MB なので不可能**（`docs/260816_sales.md` §12.4）。
- **静的アーティファクトにする場合**（採用案・§5.3）：1 次メッシュ = **320 × 320 の 250m セル**なので、
  ランクを 4 ビットで詰めると **1 レイヤ 51,200 バイト固定**。人口 > 0 のメッシュを含む 1 次メッシュは**実測 151 枚**
  （無人域を含めても 180 枚程度）なので、**全国 1 レイヤ ≒ 7.7MB（raw）**、
  **端末が 1 回に落とすのは 51,200 バイト（gzip 後は浸水域の広がり次第で数 KB〜十数 KB）**。
  → **DB は 1 バイトも増えない。**

## 5. データモデル（メッシュ・ネイティブ）

### 5.1 全体像

```
[原典]                          [パイプライン(Python)]                 [配布]                    [消費]
A31a 洪水(5種)  ─┐                                                  ┌ 1次メッシュ別バイナリ ──→ 現在地判定 / 集計 / 方向計算
A51 内水        ─┤                                                  │  （320×320 nibble）        （ブラウザ・Edge 両方・**画面には出さない**）
A49 高潮        ─┼→ 250m メッシュへ集約 → hazard_mesh.csv ─────────┤
A40 津波        ─┤   （最大ランクを採る）      （derived）           ├ 集計 CSV（市区町村・駅×半径）→ 解析・参考値
A33 土砂        ─┤                                                  │
G04-d 標高      ─┘                                                  └ （Phase 5 で必要になったら PMTiles＝回避領域の描画用）

[別経路・ホスティング不要]
重ねるハザードマップ タイル ──────────────────────────────────────────→ MapLibre（表示の主役）
気象庁 キキクル タイル / 警報 JSON ───────→ /api/hazard/alerts（サーバでキャッシュ）→ UI・AI
浸水ナビ API ───────────────────────────→ /api/hazard/point（サーバでキャッシュ）→ UI・AI
```

**要点：原典 → メッシュ化は 1 回だけ行い、そこから描画用と判定用の 2 表現を派生させる**（＝単一の真実。CLAUDE.md §3 DRY）。

### 5.2 メッシュ格子の定義（純関数・テスト対象）

1 次メッシュは **緯度 40 分 × 経度 1 度**。これを 250m（5 次）メッシュまで割ると、
**1 次メッシュ = 320 行 × 320 列**（2次 8 × 3次 10 × 4次 2 × 5次 2）にちょうど分割される。この「320×320」が全設計の骨になる。

```ts
// src/shared/mesh.ts（新規・純関数のみ・framework 非依存）
export type MeshCode = string                    // 10 桁（250m）
export type MeshCell = { readonly primary: string; readonly row: number; readonly col: number }  // 1次メッシュ + 0..319

export function meshCodeFromLonLat(lon: number, lat: number): MeshCode
export function meshCellFromLonLat(lon: number, lat: number): MeshCell
export function meshCenterOf(code: MeshCode): { lon: number; lat: number }
export function meshBoundsOf(code: MeshCode): { west: number; south: number; east: number; north: number }
export const MESH_SIZE_M = 250
export const CELLS_PER_PRIMARY = 320
```

- **測地系**：既存方針どおり基準は **EPSG:6668（JGD2011）**（`CRS.md`）。標準地域メッシュは日本測地系の定義だが、
  JGD2011 と WGS84 の差は数 cm 級でメッシュ判定に影響しない。ただし **G04-d は JGD2000** なので、
  メッシュコードを鍵に結合する限り再投影は不要（同じコード体系）である点を明記しておく。
- **テスト**（CLAUDE.md §3「境界値を厚く」）：
  1 次メッシュの四隅、2次/3次/4次/5次の境界、日付をまたがない範囲での往復（code → center → code）、
  既存 `population_mesh.md` の実データ（例 `5339452011` → 35.684375, 139.626563 を検算済み）との一致。

### 5.3 配布形式：1 次メッシュ単位のバイナリ（判定用）

| | 内容 |
|---|---|
| 単位 | 1 次メッシュ 1 枚 = 320 × 320 セル |
| 中身 | セルごとに **4 ビット**（0＝該当なし、1–6＝浸水深ランク、7–15＝予約） |
| サイズ | **51,200 バイト固定**（raw）。ほぼ 0 の疎な配列なので gzip がよく効く（圧縮率は Phase 1b で実測して記録する） |
| ファイル名 | `hazard/{layer}/{primaryMesh}.bin`（例 `hazard/flood_l2/5339.bin`） |
| 標高 | `terrain/elev/{primaryMesh}.bin`（平均標高を dm 単位の int16 ＝ 204,800 バイト。必要なら 1 バイト量子化で半減） |
| 索引 | `hazard/index.json`（存在する 1 次メッシュ・レイヤ・生成日・原典年度・ハッシュ） |

- **なぜ固定長密配列か**：オフセット計算 `row * 320 + col` だけで引ける＝**パースが不要**。JSON も CSV も要らない。
  発災時に一番効く性質は「速い」ではなく「**壊れない・要らないものを読まない**」である。
- **なぜ 1 次メッシュ単位か**：**人口 > 0 のメッシュを含む 1 次メッシュは実測 151 枚**（`data/` の 250m メッシュから集計）。
  端末は**自分がいる 1 枚（＋隣接 8 枚）だけ**を落とせばよい。1 次メッシュは**南北約 74km ×東西約 91km（北緯 35 度）**なので、
  **避難行動の距離スケールを完全にカバーする**。
- **ホスティング**（**決定 2：案 A に確定**・§12）：
  - **案 A（採用）**：Next.js の `public/hazard/**` → Vercel の CDN。**帯域が潤沢**（Hobby 100GB/月）。
    リポジトリの増分は **1 レイヤ 7.7MB × メッシュ化するレイヤ数**（洪水 3 種なら約 23MB・raw）。
    **`.bin.gz` を置いて `DecompressionStream('gzip')` で解く**なら数 MB に収まる（配信経路の圧縮設定に依存しないので確実）。
  - 案 B（退避先）：**Supabase Storage**（無料枠 1GB・DB とは別枠）。リポジトリは汚れないが、**egress 5GB/月**が上限で読めない量ではない。
  - **A を採る理由**：帯域が効く・デプロイと版が一致する。B は**リポジトリ増分が許容できなくなったときの退避先**として残す。

#### なぜ DB ではなく静的アーティファクトか（容量以外の理由）

容量（実測 452MB／無料枠 500MB）は「**いま DB に入れられない**」理由だが、「**入れないほうが良い**」理由は別にある。
そして**こちらは有料プランにしても変わらない**。

| 理由 | Supabase Pro（$25/月・8GB）で解決するか |
|---|---|
| **オフラインで引けない**（発災時に圏外で死ぬ） | ❌ しない |
| アクセスパターンが DB 向きでない（1 点 → 1 値を高頻度・低レイテンシ。往復は東京リージョンでも 20–50ms） | ❌ しない |
| **年 1 回更新の不変データ**でトランザクションも整合性制約も使わない＝DB の機能を 1 つも使わない | ❌ しない |
| CDN 配信は帯域内で実質ゼロ。DB は 1 リクエストごとに egress を消費（無料枠 5GB/月） | ❌ しない |

#### ただし「DB を使わない」ではなく「ワークロードで分ける」

有料化が本当に効くのは**解析側**である。ここは DB のほうが明確に向く。

| ワークロード | 置き場所 | 理由 |
|---|---|---|
| 現在地判定・オフライン・脱出方向 | **静的アーティファクト** | 上表のとおり。Pro にしても改善しない |
| **任意半径**の浸水域面積（PostGIS `ST_Intersection`） | **DB** | `architecture.md` §5.2 が将来拡張として挙げている領域 |
| 「浸水域内人口が増えている市区町村」を動的に出す | **DB** | Phase 1b では §5.5 の CSV で手元検証にとどめる |
| `flood_area_ratio_{R}` 等をランキング・散布で使う（**決定 3 により当面やらない**） | **DB** | やるなら既存 RPC にそのまま乗る |

> **正直に言うと、Supabase の容量問題は水害とは独立にいずれ来る。**
> `docs/260816_sales.md` §12.4 の推奨 3 が既に「次のデータ追加の前に **E**（増減率を RPC 計算）・**F**（`float8[]` 化）・**G**（Pro）を判断する」と書いている。
> **水害はこの判断を回避できる数少ないデータ**（DB を 1 バイトも増やさずに作れる）だが、昼間人口・生活利便施設を足すときには逃げられない。
> → **決定 3 により、当面は無料枠のまま静的で作る。** Pro 化は「任意半径の浸水面積」「浸水域内人口の推移」を
> 動的に出したくなった時点で、**水害とは別軸**（昼間人口など次のデータ追加とまとめて）判断する（§12.2）。

### 5.4 レイヤカタログ（＝ハザード版のメトリクス・カタログ）

既存の `metric_catalog` は「(metric, radius, year) → 値」の世界なので、ハザードはそこに入らない。
**同じ思想で形の違う `hazard_catalog` を新設する**。これが UI 凡例・API 検証・AI ツール記述の**単一の真実**になる。

```ts
// src/shared/hazard.ts（Zod・z.infer で型を導出）
export const hazardLevelSchema = z.enum(['safe', 'caution', 'warning', 'danger', 'critical'])

export const hazardRankSchema = z.object({
  code: z.number(),                 // 1..6（原典のコード値そのまま）
  labelJa: z.string(),              // '3.0〜5.0m未満'
  meaningJa: z.string(),            // '2階部分が浸水'      ← 原典の「内容」欄
  actionJa: z.string(),             // '立退き避難が基本'    ← ドメインの判断（§7.5 で監修）
  level: hazardLevelSchema,
  color: z.string(),                // '#FFB7B7'（公式凡例と一致させる）
  minM: z.number().nullable(), maxM: z.number().nullable(),
})

export const hazardLayerSchema = z.object({
  key: z.string(),                  // 'flood_l2'
  group: z.enum(['flood','inland_flood','storm_surge','tsunami','landslide','terrain','realtime']),
  labelJa: z.string(),              // '洪水浸水想定区域（想定最大規模）'
  summaryJa: z.string(),            // 1〜2文。AI がそのまま説明に使える
  ranks: z.array(hazardRankSchema),
  tile: z.object({ url: z.string(), minZoom: z.number(), maxZoom: z.number(), format: z.enum(['png','geojson','pbf']) }).nullable(),
  mesh: z.object({ available: z.boolean(), pathTemplate: z.string() }).nullable(),
  vintage: z.number(),              // 2025
  updateCadence: z.enum(['static','annual','10min']),
  source: z.string(), license: z.string(), attribution: z.string(),
  coverageNoteJa: z.string().nullable(),  // '公表済みの市町村のみ。白い＝安全ではない'
  /** 網羅性が低いレイヤで「空白を埋める」参考レイヤ（内水 → 治水地形分類図・標高・低位地帯・§3.7）。 */
  fallbackLayersJa: z.array(z.string()),
})
```

**網羅性の注記は、レイヤごとに強さを変える。** 内水は特に強い文言にする（§3.7）。

```jsonc
// hazard-catalog.json（抜粋）

  "key": "naisui",
  "group": "inland_flood",
  "labelJa": "雨水出水（内水）浸水想定区域",
```

### 5.5 既存資産との掛け算（解析用・任意）

Phase 1b の副産物として、**メッシュ × 人口**の集計 CSV を出す。これは**駅×半径の DB 列にはしない**（§2.1）が、
ランキングや散布図で使いたくなったときのために、`data/derived/` に置いて手元で検証できるようにする。

- `hazard_pop.csv`：メッシュ × {浸水深ランク, 2020 人口, 2015 人口, R6 推計 2050 人口}
- 例に出せる問い：「浸水域内人口の**増加**が大きい市区町村は？」「2050 年に浸水域内人口が最も残るのは？」
- **もし駅×半径に入れるなら**、列は最小限にする：`flood_area_ratio_{R}`（半径内メッシュのうち浸水域の割合）と
  `flood_pop_ratio_{R}`（半径内人口のうち浸水域内の割合）の 2 系統 × 6 半径 = 12 列 ＝ 約 11 万行 ≒ **8MB**。
  現在の DB 残 48MB なら入る。ただし**決定 3 により当面は作らない**（入れると「平均で語る」誘惑が生まれる）。
  必要になったら §12.2 のタイミングで Pro 化とセットで判断する。

#### プランからの差分（3 点・いずれも実装して分かったこと）

1. **危険度レベルの最も軽い段階を `safe` から `none` に変えた。**
   §5.4 の草案は `['safe', …]` だったが、**§7.5-1「白は『想定なし』であって『安全』ではない」と型の名前が矛盾する**。

2. **浸水深の階級は原典コードの 6 段階ではなく、8 段階にした。**
   配信タイルの画素を 294 タイルぶん集計したところ、**国交省マニュアル（第 4 版）表-7.2 の「詳細版 8 階級」の配色で

3. **階級に `colorSource` を足した**（`official` / `measured` / `null`）。
   浸水深・浸水継続時間は**公式マニュアルの RGB と配信タイルの実測が完全一致**したので `official`。

   という推定で対応づけたので `measured`（地すべりの特別警戒は標本に出現せず `null`）。
   凡例 UI は `measured` に控えめな注記を出す。**どこまで確かかを型に残す**のは `reliabilityFlagKey` と同じ思想。

### 6.2 立退き／垂直避難の判定ルール（純関数・**決定 6 で確定**）

`domain/hazard/verdict.ts`（20 行未満・単一責務）。順に評価し、**最初に当たった条件を採る（安全側）**。

| 優先 | 条件 | 判定 | 根拠 |
|--:|---|---|---|
| 1 | 家屋倒壊等氾濫想定区域（氾濫流 or 河岸浸食）内 | **立退き避難** | 建物ごと倒れるため上階に意味がない |
| 2 | 土砂災害警戒区域（特別警戒区域を含む）内 | **立退き避難** | 同上 |
| 3 | 浸水深ランク ≥ 3（3.0m 以上） | **立退き避難**（3 階以上の堅牢な建物があれば垂直も可） | 2 階が浸水・水没する高さ |
| 4 | 浸水継続時間ランク ≥ 4（72 時間以上） | **立退き避難** | 孤立・ライフライン途絶 |
| 5 | 浸水深ランク 1–2（0〜3.0m 未満） | **垂直避難も選択肢**（上階のある堅牢な建物に限る） | 床上〜1 階浸水 |
| 6 | いずれにも該当しない | **その場に留まる**（ただし土砂・内水の未公表に注意） | — |

> ⚠ **人命に関わる判断なので、この表を「確定版」として扱う（決定 6・§12）。**
> 出典は国土交通省／内閣府の考え方に沿い、**アプリが「避難しなくてよい」と断定しない**書き方に統一する（§7.5）。
> **閾値・文言を変えたくなったら、コードより先に §12 の決定を書き換える。** この表が唯一の合意記録である。
> 専門家による監修は**実装をブロックしない別トラック**で進める（§12.2）。監修結果はカタログの `actionJa` の
> 差し替えだけで反映でき、コード変更が要らない設計になっている（§5.4）。

### 6.3 外部 API の扱い（レート制限・タイムアウト・失敗時）

- **浸水ナビは「分間 30 リクエスト」が明記**されている。→ **必ずサーバ経由**にし、
  **メッシュコード単位でキャッシュ**する（同じ 250m メッシュ内の問い合わせは 1 回に畳む）。
  Route Handler に `CACHE.day` を付ければ Vercel の CDN が吸収し、実リクエストは激減する。
- **`AbortController` によるタイムアウト必須**（CLAUDE.md §3）。浸水ナビ 5s／気象庁 3s を初期値にする。
- **数値の優先順位**：ユーザーに見せる浸水深は **① 浸水ナビ（m 単位・原典解像度）→ ② 自前メッシュ（ランク・250m）** の順で採る（§2.5）。
  応答には**どちらを使ったかを `source` として必ず入れる**（`'suibou-navi'` / `'mesh'`）。
- **失敗時は黙って落とさない**：①が取れなければ `hazards`（自前メッシュ）だけで応答を組み立て、`rivers: []` ＋
  `notesJa: ['河川別の到達時間は取得できませんでした（浸水深は 250m メッシュの区分値です）']` を返す。
  **部分的に答えられるなら答える**のが防災系 UI の正解。
- **キキクルの `targetTimes.json` は `max-age=60`**。サーバ側で 60 秒キャッシュし、クライアントは 5 分間隔でポーリングする
  （更新は 10 分間隔なので、5 分で十分に追随できる）。

### 6.4 GUI Chat Protocol の拡張（純加算）

`src/shared/protocol.ts` に**足すだけ**で、既存の型は 1 つも変えない。

```ts
// mapAction に 2 つ追加
{ type: 'setHazardLayers', layers: string[], opacity?: number }
{ type: 'showPoint', lon: number, lat: number, labelJa?: string }

// panel に 2 つ追加
{ type: 'hazardCard',     // 地点のハザード一覧＋verdict
  placeJa: string, level: HazardLevel, headlineJa: string, evacuation: 'takeaway'|'vertical'|'stay',
  items: { labelJa: string; valueJa: string; level: HazardLevel }[],
  reasonsJa: string[], sources: SourceRef[], disclaimerJa: string, placement, size }

{ type: 'evacuationList', // 避難先候補
  forDisasterJa: string,
  items: { name: string; address: string; distanceM: number; bearingJa: string; outsideFlood: boolean; elevM: number|null }[],
```

**なぜ `statTable` の使い回しで済ませないか**：浸水深は「数値」ではなく「**レベル**」であり、色と行動が紐づく。

### 7.2 駅詳細タブは増やさない（重要な判断）

駅詳細のタブ帯は**すでに 8 タブ＝516px** でパネル幅 420px を超えており、右端フェードで凌いでいる
（`constants.ts` の `PANEL_WIDTH_PX` コメント・`tests/panel-layout.test.ts`）。**9 タブ目は入れない。**

代わりに、**`stationCard` パネルのヘッダに「災害バッジ」を 1 つ足す**。

```

│ 東京都 / 乗降 12.3万人・日            │
│ ⚠ 想定最大規模 3〜5m 浸水  [詳しく見る]│ ← タップで hazardCard（＝地点カード）を開く

```

- バッジは `/api/hazard/point` を駅の代表点で 1 回引くだけ（＝タブ追加ゼロ・レイアウト不変条件を壊さない）。
- 「駅の代表点だけの話であって、駅前広場の反対側は違うかもしれない」という**限界をバッジのツールチップに明記**する。

### 7.3 現在地モード（Phase 2）

```
        ┌────────────────────────┐
        │ 📍 現在地                │
        │ 東京都葛飾区付近          │
        │ ─────────────────────  │
        │ 🔴 想定最大規模 3〜5m     │  ← level に応じた色（safe/caution/warning/danger/critical）
        │    2階部分が浸水          │
        │ ⚫ 家屋倒壊等氾濫（氾濫流）│
        │    → 立退き避難が基本      │
        │ ─────────────────────  │
        │ 標高 3.2m ／ 中川が氾濫   │
        │ すると約30分で浸水開始     │
        │ ─────────────────────  │
        │ [安全な場所を探す]         │
        │ ⓘ 避難は市町村の情報に従う │
        └────────────────────────┘
```

- **`watchPosition` は前面のみ**。バックグラウンド追跡はブラウザではできない（§9.3）。**できないことを UI で約束しない。**
- **精度（`coords.accuracy`）を必ず見る**。250m メッシュに対して精度 300m 超なら「おおよその位置です」と明示し、
  隣接メッシュも併記する（誤った安心を作らないため）。
- **オフライン**：Service Worker で「現在地の 1 次メッシュ＋隣接 8 枚」のバイナリと `hazard-catalog.json` をキャッシュ。
  既存の `OfflineBanner.tsx` を拡張して「オフラインですが、ハザードは表示できます」と出す。

### 7.4 警戒モード（Phase 3）

**平時と同じ画面のままにしない。** レベル4相当が出ている地域を表示しているときは、アプリの見え方を切り替える。

| | 平時 | 警戒（レベル3相当以上） |
|---|---|---|
| 既定レイヤ | 洪水（想定最大規模）OFF | **キキクル ON ＋ 洪水 ON** |
| 上部 | 通常ヘッダ | **警戒バナー**（何が出ているか・いつの情報か・出典） |
| 地点カード | 「もし起きたら」 | 「**今**」＋「もし起きたら」の 2 段 |
| 主 CTA | — | **［安全な場所を探す］** |

- バナーの文言は**必ず「◯◯相当」**：`土砂災害警戒情報（警戒レベル4相当）が発表されています`。
  **「避難指示が出ています」とは絶対に書かない**（それは市町村が出すもので、こちらは知り得ない）。
- **時刻を必ず出す**（`basetime`）。10 分前の情報を「今」と言わない。
- 通知は **決定 7 により画面内バナーのみ**（§12）。登録地点 ＋ Web Push は **Phase 3 のスコープ外**にし、
  「届かないことがある」前提の設計と購読管理ができてから将来のフェーズで扱う（§9.4・§12.2）。

### 7.5 「誤った安心」を作らないための表示規約（最重要）

このアプリで**いちばん危険なのは、赤を出し損ねることではなく、白を「安全」と読ませること**である。

1. **白は「想定なし」であって「安全」ではない。** 凡例の一番下に必ず `未指定・未公表の区域があります` を出す。
2. **網羅性の注記をレイヤごとに出す**（`coverageNoteJa`）。**特に内水**——47 都道府県中 22 しか整備されておらず、
   大阪府・京都府は全域が対象外。ここは「レイヤを OFF にしているのか、地図が無いのか」が見分けられるよう、
   **対象外の都道府県では明示的に「この地域には内水の想定区域図がありません」と出す**（§3.7）。
3. **年度と出典を常時表示**（`vintage`）。ハザードマップは更新で色が変わる。
4. **地図に描く色は常に公式タイル（原典解像度）**。自前 250m メッシュは画面に出さない（§2.5）ので、
   「粗い表示なのに正確なつもりで読まれる」事故が起きない。統計のコロプレスに限って出すときは「250m メッシュ集計」と明記する。
5. **避難の要否を断定しない。** 文言は「〜が基本です」「市町村の避難情報に従ってください」に統一。
6. **AI にも同じ規約を課す**（§6.5 のシステムプロンプト）。UI だけ慎重で AI が断定したら意味がない。

### 7.6 モバイル・アクセシビリティ

- 地点カードは既存の `vaul` ボトムシート（`StationDetailPanel` と同じ作法）で出す。片手で読める高さに収める。
- **色だけで危険度を伝えない**（1 型・2 型色覚）。レベルは **色＋アイコン＋テキスト**の 3 重で示す。
  公式凡例の色は変えられないので、**地点カード側でテキストを担保**する。
- ハザードのラスタは既定 opacity 0.6。**背景地図の地名が読めなくなると避難に使えない**ため、
  0.3–0.9 のスライダを必ず出す。

## 9. 先に潰しておく落とし穴

### 9.1 タイルの画素から意味を読む（色 → ランクの逆引き）

Phase 3 でキキクルの色からレベルを読むには `<canvas>` に描いて `getImageData` する必要がある。

- **CORS が要る**（汚染された canvas は読めない）。→ **気象庁・地理院とも `access-control-allow-origin: *` を実測確認済み**。
- ただし MapLibre のタイルとは**別に fetch する**方が確実（内部キャッシュに手を突っ込まない）。
- **色の完全一致に頼らない**。アンチエイリアスで中間色が出るので、**最近傍色**で判定し、閾値外は「不明」にする。
- **決定 5 でこちらを採った**：キキクルは**面としての表示に留め、レベル判定は警報 JSON（テキスト）から取る**（§12）。
  色の解釈が不要で壊れにくい。**画素の読み出しは実装しない**——上の 3 つの注意点（CORS・別 fetch・最近傍色）は、
  将来どうしても色が要るときのために残しておく。

### 9.2 ハザードタイルは「いつの間にか中身が変わる」

年度更新でタイルの内容が差し替わる（A31a は毎年 5 月に更新）。バージョン固定できない。

- カタログの `vintage` を**手で上げる運用**にし、更新月（5 月）に確認するタスクを残す。
- 自前メッシュ（1b）は生成日とハッシュを `index.json` に記録し、**表示と一致していることを検証できる**ようにする。

### 9.3 ブラウザはバックグラウンドで位置を追えない

- `watchPosition` は**前面のみ**。iOS の PWA は特に背景実行が厳しい。
- したがって **「アプリを閉じていても危険を知らせる」は、位置ベースでは実現できない**。
- 実現できる形は 2 つ：
  1. **前面のとき**に現在地を追い、危険に入ったら画面内で警告する（Phase 2/3）
  2. **登録地点**（自宅・実家・勤務先）を保存し、**サーバが定期監視**して Web Push を送る（**決定 7 により当面やらない**・§12.2）
- **①を②のように見せない。** UI とコピーで区別する。

### 9.4 Web Push の制約

- iOS は 16.4 以降で対応するが、**ホーム画面に追加した PWA のみ**。Android/デスクトップは通常の PWA で可。
- 送信にはサーバ側の VAPID 鍵と購読の保存が要る（Supabase に小さなテーブル 1 つ）。
- **「通知が届かないことがある」を前提に設計する。** 通知はあくまで補助で、正は市町村の防災無線・緊急速報メール。
- **決定 7 により、当面は実装しない**（§12.2）。Phase 3 は画面内バナーで完結させる。

### 9.5 座標系と測地系

- 判定はすべてメッシュコード経由なので再投影不要。
- ただし**面積計算（浸水域面積・人口按分）は Albers 正積**で行う（`CRS.md`）。ここを緯度経度のままやると北で誤差が出る。
- G04-d は JGD2000、A31a は JGD2011。**メッシュコードで結合する限り問題にならない**が、
  ポリゴン同士を重ねる工程（1b の集約）では `to_crs` を明示する。

### 9.6 パイプラインの重さ

- A31a は地方整備局・都道府県ごとの分割で、旧版（2012年度）のページには「北海道・愛知・三重はファイルサイズが大きい」と注意書きがある。
  1 次メッシュ版（A31b）の前身にあたる A31-v4_0 のダウンロード表では、GeoJSON で最大 1,016.7MB のファイルが存在する。
- **対策**：都道府県ループで 1 県ずつ処理して即メッシュ集約し、ポリゴンをメモリに残さない。
  `data/` は gitignore なので容量は問題ないが、**処理時間は数時間規模を見込む**。

### 9.7 Vercel / Next.js まわり

- Route Handler の実行時間上限に注意（浸水ナビ ＋ 気象庁を直列で叩かない。`Promise.all` ＋ 個別タイムアウト）。
- 静的アーティファクトは `public/` に置けば CDN 配信されるが、**リポジトリが数 MB〜20MB 台 増える**（**決定 2 で許容**・§12）。
- `.vercelignore` は `data/ slide/ script/ pipeline/ condminium/ docs/` を除外している（`public/` は対象外）。
  **`public/hazard/` を新設しても除外されない**ので追記は不要だが、誤って `public/` を除外しないこと。

### 9.8 既存の不変条件を壊さない

- **駅詳細タブは 8 のまま**（`tests/panel-layout.test.ts`）。§7.2 の方針を守る。
- `PANEL_WIDTH_PX = 420` を広げない。
- `metric_catalog` に水害を混ぜない（カテゴリは 9 のまま）。ハザードは別カタログ（§5.4）。
- Supabase のサイズを増やさない（§5.3）。増やす場合は `--append` モードで（`docs/sales.md` §10.3 の教訓）。

| 都道府県別の浸水域面積 | 各都道府県の公表値（あれば）と桁が合う |
| 標高 | 海面下フラグ（G04-d コード 5）のメッシュが、東京・大阪・濃尾平野のゼロメートル地帯と一致する |

### 10.3 API・UI

- `/api/hazard/point` を主要 20 地点でスナップショットし、**回帰で `verdict` が変わったら落ちる**ようにする
- 外部 API 障害時（浸水ナビ 500・気象庁タイムアウト）に**部分応答が返る**ことのテスト
- Playwright（既存の検証手順どおりヘッドレス＋スクリーンショット）で、レイヤ ON/OFF・凡例・共有リンク復元・オフライン表示

### 10.4 AI

- `src/ai/eval/cases.ts` に防災ケースを追加し、**禁止応答（避難不要の断定・出典なしの数値・「避難指示が出ています」）を落とす**テストを入れる
