## 2. #3176 カタログ掲載 — not planned（妥当だと考える）

### 言われたこと

1. **HTTP・認証なしの MCP はコード変更なしでユーザー自身が登録できる。** Settings → MCP →
   サーバーを追加で種別 http と URL を入れるだけ。保存される spec は `{ type: "http", url, enabled: true }` で、
   `configSchema: []` のカタログエントリを install した結果と実質同一。つまりカタログ追加は
   「使えるようにする」変更ではなく「**同梱の審査済みリストに載せる**」という編集判断。
2. **現行カタログのスコープと合わない。** 16 エントリはいずれも地域を問わない著名サービスで、
   特定の国のデータセットに限定されるエントリは 1 件もない。この粒度を維持したい。
   `ja` が一級ロケールであることと同梱カタログのスコープは**別の判断軸**。

### 評価

どちらも反論する材料が無い。とくに 1 点目は、**こちらが issue に書いた検証セクション自体が根拠**に
なっている（Settings 経由で実機動作を確認済みと自分で書いた）。掲載は機能ではなく編集判断だ、という
整理は正確で、2 点目のスコープの線引きも 16 エントリを見れば一貫している。

サーバの設計自体は評価していただいた——自己記述カタログ（キー・単位・年次）、出典を返すこと、
レート制限の明示、災害を「想定」と「現況」に分けて断定を避けていること。ここは維持する。

## 3. #3175 スキル走査 — 採用・マージ済み

### 入ったもの（PR #3184）

- `~/.claude/plugins/installed_plugins.json` の `installPath` を読み、`<installPath>/skills/` を
  **3 つ目の走査ルート**に追加
- スキル名は **`<plugin>:<skill>`**（CLI と同じ addressing）。見た目の話ではなく、Run ボタンと
  スケジューラが `/${skill.name}` を送るため、名前を合わせないと押せても動かない
- 優先順位は **project > user > claude-plugin**（プラグインが既存のスキルを奪わない）
- `settings.json` の `enabledPlugins` で明示的に false のプラグインは除外
  （user → workspace → `settings.local.json` の順にマージ）
- `SkillSource` に `claude-plugin` を追加し**読み取り専用**として扱う。サイドバーに専用バッジ（8 ロケール）
- ledger は CLI の内部状態ファイルなので全フィールドを型ガードで読み、壊れていても例外を投げない

### こちらの提案から変わった点

`installPath` は**絶対パスかつ `.` / `..` セグメントを含まないものだけ**を辿る。相対パスはサーバの
カレントディレクトリから解決されてしまい、`..` は CLI が何もインストールしていない場所を指すため。
一方で**プラグインキャッシュ配下への封じ込めはしない**——`claude plugin marketplace add` は path も
受けるので、キャッシュ外の `installPath` は正当な形であり、封じ込めるとローカルでプラグインを
開発している人のプラグインを黙って落とすことになる。

この判断は、こちらが出した素朴な提案より明確に良い。**「壊れた ledger を弾く」と「正当な使い方を
弾く」の線引き**を、実際のインストール経路から引いている。

### 意図的に外した面

- **bridge の `/help` とブリッジのスラッシュコマンド**：先方の実機ではプラグインのスキルが
  **1,116 件（3 プラグイン）**あり、1 行ずつ 1 通に詰めるとどのブリッジのメッセージ上限も超える
- **スキルのスケジューラ**：マーケットプレイスのプラグインを入れただけで frontmatter の `schedule` が
  定期実行として自動登録されるのは、ユーザーが頼んでいない挙動
- **性能**：既定の `discoverSkills()` が毎回全スキャンすると 11–18ms → 179–204ms になったため、
  名前で引く 2 か所は `:` を含まない名前ではプラグインをスキャンしない

> **1,116 という数字はこちらの設計にも効く。** 当プラグインは 11 本だが、スキルは「足せば足すほど
> 良い」ものではない。母艦側の一覧・スケジューラ・ブリッジに載る前提で、**数を抑える**判断は今後も
> 維持する（コマンド版 5 本を MulmoClaude に置かない判断＝PR-15a と同じ方向）。

## 4. 核心：症状の原因は、こちらの説明が間違っていた

### 先方の指摘（これが正しい）

> MulmoClaude はエージェントに渡すスキル一覧を自前で組み立てていません。本物の claude CLI を
> spawn し、`--allowedTools` に裸の `Skill` を渡すだけです。裸の `Skill` は全スキルを許可するので、
> スキルの発見自体は CLI 側で、そこにはプラグインのスキルも含まれます。

`discoverSkills()` が供給しているのは、スキル一覧 UI / `manageSkills`、bridge の `/help`、
スケジューラ、呼び出しイベントへの path・description の後付け（表示用）——**エージェントの挙動には
効かない**。

### こちらが書いていたこと（誤り）

`docs/260912_gui_chat_protocol.md` §4.6.1 ① と プラグイン README にこう書いた。

> **MulmoClaude はプラグインのスキルを読まない。** 走査するのは `~/.claude/skills/` と
> `<workspace>/.claude/skills/` の 2 つだけ。

`discovery.ts` の事実としては正しい。だが**「エージェントがスキルを呼ばない理由」の説明としては誤り**。
症状（作法が届かない）と回避策（相対 symlink）は正しかったので結果的に動いてしまい、
**間違った因果のまま出荷していた**。

### なぜ間違えたか

`Skill` の呼び出しが 0 件という観測から、最も近くにあった「走査ルートが 2 つだけ」という
コード上の事実に飛びついた。**観測（0 件）と機構（なぜ 0 件か）を確かめずに結びつけた**のが原因。
symlink を張ったら直ったことが、誤った説明の裏づけに見えてしまった（実際には CLI 自身が
`<cwd>/.claude/skills/` を読むから直っただけ）。

## 5. 先方の質問への回答（実測）

> Settings でサンドボックスを OFF にした場合、`Skill` の呼び出しは発生しますか？

**発生する。仮説どおり Docker のパス不一致が真因。** 以下すべて 2026-09-15 実測。
回避策の symlink 6 本は**外した状態**で計測している。

### 5.1 同じプロンプトを、同じワークスペースで、環境だけ変えて実行

`claude -p "横浜市で中古マンションを買おうと思っています。おすすめの駅はどこですか？"`
（cwd = `~/mulmoclaude`、`--allowedTools` は MulmoClaude と同じ裸の `Skill` を含む 9 個）

| | プラグイン由来コマンド | `station-data` ツール | SessionStart フック | `Skill` 呼び出し |
| --- | --- | --- | --- | --- |
| **ホスト**（サンドボックス OFF 相当） | 見える | **13 本** | 発火（文脈注入あり） | **`ai-database-map:station-recommendation`** |
| **コンテナ**（`mulmoclaude-sandbox` に MulmoClaude と同じ 3 マウント） | なし | **0 本** | 発火せず | **なし** |

### 5.2 CLI 自身の診断が理由を言っている

`claude plugin list` を同じ 2 環境で実行した。

```
ホスト     : ✔ enabled
コンテナ   : ✘ failed to load
             Error: Marketplace ai-database-map failed to load: cache-miss
```

### 5.3 追加で分かったこと 1 — 効いているファイルは 2 つ

ホストの絶対パスを持つ ledger は `installed_plugins.json` だけではない。

| ファイル | キー | 値の例 |
| --- | --- | --- |
| `installed_plugins.json` | `installPath` | `/Users/<user>/.claude/plugins/cache/<mp>/<plugin>/<ver>` |
| `known_marketplaces.json` | `installLocation` | `/Users/<user>/.claude/plugins/marketplaces/<mp>` |

**どちらか片方だけでは直らない**（投稿後に切り分けた）。同じコンテナで書き換える対象を変えて比較した。

| 書き換えたもの | `claude plugin list` | エージェント（コマンド・スキル・フック） |
| --- | --- | --- |
| `installLocation` だけ | ✔ enabled | **届かない**（コマンド 0・`Skill` 呼び出しなし） |
| `installPath` だけ | ✘ failed to load（`cache-miss` のまま） | 届かない |
| **両方** | ✔ enabled | **届く**（コマンド・`Skill`・フックが復活） |

`plugin list` が `enabled` でもエージェントには届かない段がある。**成功判定に `plugin list` を使えない**。
影響は当プラグインに限らず、`claude-plugins-official` を含む登録済みマーケットプレイス全部に及ぶ。

### 5.4 追加で分かったこと 2 — 書き換えれば直る（実証済み）

2 ファイルの `/Users/<user>/.claude` を `/home/node/.claude` に置換したコピーを、
同じコンテナに**重ねてマウント**して再実行した。

```
✔ enabled
```

つまり先方が想定している「Docker モードでの installPath 書き換え（localhost →
host.docker.internal と同種の処理）」は、**2 ファイルを対象にすれば成立する**。
`HOME=/home/node` は MulmoClaude が明示的に渡している（`server/agent/config.ts`）ので、
読み替え先は一意に決まる。

### 5.5 追加で分かったこと 3 — 失われるのはスキルだけではない

プラグインが丸ごと不活性になる。**スキル・スラッシュコマンド・MCP サーバ（13 → 0）・
SessionStart フック**がすべて落ちる。当プラグインの MCP は Settings に別途登録してあったので
ツールだけは動いており、**それが「スキルだけの問題」に見せていた**。

### 5.6 この計測の限界（正直に）

MulmoClaude 本体を `--disable-sandbox` で起動して UI から会話したわけではない。
**CLI を直接叩いている**。ただし「エージェントのスキル発見は CLI の仕事」というのは先方自身の
指摘であり、MulmoClaude が渡す `--allowedTools` の形も合わせてある。

本体経由の自動確認は見送った。`POST /api/agent` にはブートストラップで配られる bearer token が要り、
リクエストの形と SSE の受けを解析する必要がある——得られるのは既に分かっている yes/no ひとつなので、
手間とリスクに見合わない。**UI から確かめるなら 2 分**で済む（Settings でサンドボックスを OFF →
新しいチャットで横浜の質問 → スキルのバッジが付くか見る）。返信前に一度やっておくと万全。
