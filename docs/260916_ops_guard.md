## 1. 実測（2026-09-16・本番）

推測で設計しないために、先に測った。**このうち 2 つは、こちらの仮説を否定した。**

| 測ったこと | 結果 |
| --- | --- |
| CDN は効くか（同一 URL を 3 回） | `MISS → HIT → HIT`。**効く** |
| 未知のクエリパラメータ | 別のキャッシュキー＝ `MISS` ＝**関数が起動する** |
| `/api/stations/geojson` の大きさ | **227 KB（gzip）／ 1.36 MB（生）**・9,273 features |
| その properties | `grp` / `pax` / `name` だけ（既に最小） |
| **座標を 6 桁に丸めたら** | **gzip で 0.4%（895 B）しか減らない** ← 仮説が外れた |
| クライアントに届く `Cache-Control` | **`public` のみ**（`s-maxage` は CDN が消費して落とす） |
| `ETag` / `Last-Modified` | **どちらも無い** |
| SWR の再試行 | 12 フック中 **11 が既定（無制限リトライ）** ← 想定外 |
| `MAX_TOOL_STEPS` | 6（1 ターンで最大 6 回モデルを呼ぶ） |
| チャットのモデル | `gemini-flash-lite-latest`＝**15 RPM / 500 RPD**（`docs/feat_llm.md` §6 の実測値） |

単価（`docs` 調べ・リージョン幅）：Fast Data Transfer **$0.15〜0.35/GB**、Edge Requests
**$2.00〜3.20/100 万**、Active CPU **$0.108〜0.221/時**、WAF レート制限 **$0.50〜0.80/100 万**。

### 1.1 ここから出てくる 3 つの事実

**① ブラウザ向けの指示が 1 つも無い。** クライアントに届くのは `public` だけで、`max-age` も
`Expires` も `ETag` も `Last-Modified` も無い。**どれだけ持ってよいかを、こちらが何も言っていない。**

> ⚠ **訂正（G1 の実測後）。** ここには当初「だから毎回 227 KB を取り直している」と書いていたが、
> **それは誤りだった**。Chromium は `public` だけでも**ヒューリスティックで**キャッシュしており、
> 2 回目はネットワークに出ない（§3 G1 の完了注記）。問題は「取り直している」ことではなく、
> **期間をブラウザ任せにしている**ことである。

**② WAF では日次の上限が作れない。** WAF の計測窓は **最小 10 秒・最大 10 分**（Pro も同じ）。
`/api/chat` に 10 分 30 件を掛けても 1 IP あたり **4,320 回/日**まで通る。Gemini の **500 RPD** に対して
8 倍以上。**日次枠はコード側でしか守れない。**

**③ 失敗したときにアプリが自分で叩きにいく。** SWR の既定は「エラー時に指数バックオフで
再試行（回数上限なし）」。429 や障害のときに、開いているタブが全エンドポイントを叩き続ける。
**いちばん弱っているときに、こちらから追い打ちをかける。**

## 2. 何を守るのか

優先順に 3 つ。**金額より先に「止まらないこと」が来る**のは、防災の機能を持っているからである。

1. **上流の信頼**（気象庁・国土地理院）——遮断されたら防災機能が死ぬ。金では戻らない
2. **可用性**——Gemini の日次枠を焼かれるとチャットが止まる。費用はゼロだが機能は死ぬ
3. **請求**——Pro では超過が課金される。転送量が最大の項目

## 3. 決定（やること）

### G1. `Cache-Control` に `max-age` を足す

**問題**：§1.1 ①。**どれだけ持ってよいかを、ブラウザに何も言っていない。**

**やること**：`src/lib/http.ts` の `CACHE` に、ブラウザ向けの寿命を足す。

| 段 | 現行 | 案 | 対象 |
| --- | --- | --- | --- |
| `day` | `public, s-maxage=86400, stale-while-revalidate=3600` | ＋ `max-age=3600` | geojson・metrics・operators・routes・hazard/catalog・hazard/point |
| `hour` | `public, s-maxage=3600, stale-while-revalidate=600` | ＋ `max-age=300` | ranking・growth・駅詳細・evacuation・**recommend** |
| `short` | `public, s-maxage=30, stale-while-revalidate=60` | **据え置き** | stations 検索・**hazard/alerts** |
| `none` | `no-store` | 据え置き | health・dataset・map |

⚠ **`short` には足さない。** ここには `hazard/alerts`（いまの警報）がいる。**古い警報を「今」として
見せないこと**のほうが、転送量より重い（`docs/260824_flood.md` §7.4）。

✅ **`max-age` は客まで届く（確認済み）。** Vercel が落とすのは **`s-maxage` と
`stale-while-revalidate` だけ**で、`max-age` は通す（公式の記述）。実測でも
ローカルは `public, max-age=3600, s-maxage=86400, stale-while-revalidate=3600` を返し、
本番ではここから前 2 つが落ちて `public, max-age=3600` になる。

**それでも `ETag` は残る課題**（本文のハッシュ）。`max-age` が切れたあとは検証子が無いので全文を
取り直すしかない。条件付き GET が 304 を返せば本文は流れないが、毎回 1 往復は発生する。

**受け入れ**：
- 本番の `/api/stations/geojson` の応答に `max-age`（または `ETag`）が出ている
- 2 回目のページ表示で geojson の**本文が転送されない**（`curl` の条件付き GET／転送量で測る。目視ではなく数で）
- `hazard/alerts` のヘッダが**変わっていない**
- 既存 API の**本文**がバイト同一（W3 と同じやり方で main と突き合わせる）

> **✅ G1 完了（2026-09-16）。** `day` に `max-age=3600`、`hour` に `max-age=300` を足した。
> `short` と `none` は据え置き。既存 API の**本文は 18 本すべてバイト同一**、スモーク 44/44。
>
> **⚠ 受け入れの 2 番目が、良い意味で外れた。** 「2 回目に本文が転送されない」は、**変更前から
> 満たされていた**。ヘッドレスで測ると main でも 2 回目は `transferSize=0`——Chromium が
> `public` だけでヒューリスティックにキャッシュしている。対照実験（**別の文脈**なら必ず
> 1,360,709 B 転送される）で計測器が壊れていないことも確かめたうえでの結果である。
>
> | | 1 回目 | 同じ文脈の 2 回目 | 別文脈の 1 回目 |
> | --- | --- | --- | --- |
> | 変更前（main） | 1,360,709 B | **0 B** | 1,360,709 B |
> | 変更後 | 1,360,709 B | **0 B** | 1,360,709 B |
>
> **つまり G1 は「227 KB の再転送を止める」変更ではない。** 得たのは**振る舞いを決めたこと**である。
> ヒューリスティック・キャッシュは RFC が「してもよい」と言っているだけで、**期間も条件もブラウザ任せ**
> （`Last-Modified` が無いので、期間を計算する足場すら無い）。`max-age=3600` は「1 時間」を
> こちらが選んだという宣言で、Chromium 以外でも同じになる。**ヒューリスティックが実際に何時間なのかは
> 測れていない**ので、1 時間が従来より長いか短いかは分からない——分からないものを、決まった値に置き換えた。
>
> 副産物のほうが確かかもしれない。**`short` に `max-age` を付けないことをテストで固定した**
> （`tests/http-cache.test.ts`）。`/api/hazard/alerts` がここから `day` へ移ったら落ちる。
> 「いまの警報を配り置きしない」は転送量とは独立に守りたい性質で、これまで**どこにも書かれていなかった**。
>
> **残る本命は `ETag`。** `max-age` が切れたあとは検証子が無いので、結局**全文を取り直す**しかない。
> 304 で本文を流さない形にはできるが、`json()` がリクエストを見ていないので全ルートに手が入る。
> **別ブロックにする**（§7 へ持ち越し）。

### G2. SWR の再試行を抑える

**問題**：§1.1 ③。11 フックが無制限に再試行する。429 のときに再試行するのは、**「待ってください」と
表示しながら裏で叩き続ける**ということで、待ち時間を自分で延ばしている。

**やること**：
1. `src/lib/http-error.ts`（新）に `HttpError extends Error { status: number }` を置く
2. 各フックの fetcher が、失敗時にこれを投げる（いまは `new Error('…HTTP 429')` で**状態が文字列に
   埋まっている**）
3. `SWRConfig` をアプリ全体に 1 つ置き、`onErrorRetry` で
   **4xx は 1 度も再試行しない／それ以外は最大 2 回**にする

置き場所は `src/app/layout.tsx`（`NuqsAdapter` の隣）に client の小さなプロバイダ。`/ai` は SWR を
使わないので影響しない。

**なぜフックごとに書かないか**：12 か所に同じ設定を配ると、次に増えたフックで忘れる。
`useRecommend` だけが `shouldRetryOnError: false` を持っている**現状がまさにそれ**（W5 で 1 つだけ直した）。

**受け入れ**：
- ローカルで `/api/recommend` を叩き切って 429 を出し、**追加リクエストが 2 回で止まる**（ネットワークログの実測）
- 5xx では 2 回まで再試行する
- `useRecommend` の個別設定が消えている（共通に寄せた証拠）

### G3. `clientIp` を `x-vercel-forwarded-for` 優先にする

**調べたこと**：Vercel は `x-forwarded-for` を**上書きし、外部の IP を転送しない**（IP 詐称の防止）。
`x-real-ip` と `x-vercel-forwarded-for` は同じ値で、**`x-forwarded-for` だけは、Vercel の上に別の
プロキシを置いたときに書き換わりうる**。

**つまり現状は安全**（`x-real-ip` を優先している）。ただし
- コメントの「XFF 左端は詐称可能」は**一般論としては正しいが、Vercel 上では前提が違う**
- 将来プロキシを挟んだときに、`x-forwarded-for` へのフォールバックが穴になる

**やること**：`x-vercel-forwarded-for` → `x-real-ip` → `x-forwarded-for` の順にし、**なぜこの順なのかを
コメントに書き直す**（いまのコメントは Vercel の挙動を反映していない）。ローカル（`next start`）では
どれもクライアントが送れる——**アプリ内の制限はローカルでは意味を持たない**ことも書く
（W5 のヘッドレス検査はこれを利用している）。

**受け入れ**：ユニットテストで 3 ヘッダの優先順位を固定。本番で 429 が IP ごとに効いている。

### G4. `/api/chat` に日次の上限（DB）

**問題**：§1.1 ②。WAF は 10 分窓までしか作れないので、**日次枠はここでしか守れない**。
1 IP が 10 分 30 件のペースで回すだけで 4,320 ターン/日＝Gemini の 500 RPD を軽く超える。

**設計**：Supabase に日次カウンタを置く。**アプリのメモリでは持てない**（インスタンスが入れ替わると
消える。`src/ai/rate-limit.ts` 自身がその限界を書いている）。

```
create table public.chat_usage (
  day       date not null,           -- 米国太平洋時間の日付（Gemini の枠と境目を合わせる）
  ip_hash   text not null,           -- 生 IP は保存しない（salt つきハッシュ）
  count     integer not null default 0,
  primary key (day, ip_hash)
);
```

- **2 段の上限**：`ip_hash` ごとに **20 ターン/日**、`ip_hash='ALL'` の行で **全体 150 ターン/日**
- 加算は `security definer` の RPC（anon は select only・`20260816234947_anon_select_only.sql`）。
  引数を SQL に埋めない・`search_path` を固定する
- **日付は `America/Los_Angeles`**。Google の枠がそこで切り替わるので、境目をずらすと数が合わない
- 上限に達したら **429 ＋ 日本語 1 文**（「本日の上限に達しました。明日またお試しください」）。
  Google の 429 を待たず、**こちらの言葉で止める**

**なぜ全体の上限も要るか**：IP ごとだけだと、分散した相手に枠を焼かれて実ユーザーが弾かれる。
全体の上限があれば、**枠を焼き切る前にこちらが止まる**（同じ「止まる」でも、Google の 429 より
説明ができる）。

**目安の根拠**：`MAX_TOOL_STEPS = 6` なので 1 ターンは最大 6 回のモデル呼び出し。典型は 2〜3 回。
150 ターン × 3 ≒ 450 で 500 RPD の内側、最悪 6 回でも Google の 429 に先に当たるだけで害はない。
**正確な上限ではなく、「暴走を止める線」**として置く。

**プライバシー**：IP は個人情報として扱う。**生では保存せず**、サーバ側の salt でハッシュする。
salt は環境変数（`.env`・`CLAUDE.md` §5）。日付が変われば鍵も変わるので、追跡には使えない。

**受け入れ**：
- 上限到達で 429 と日本語が返る（ローカルで上限を 2 に下げて実測）
- 日付が変わるとリセットされる（RPC に日付を渡して検査）
- **生 IP がどこにも保存されていない**（テーブルの中身を見て確認）
- 上限内のときに増える往復は **1 回だけ**

## 5. やらないこと（根拠つき）

- **geojson の座標を丸める**——**実測で否定した**。6 桁に丸めても gzip で **0.4%（895 B）**しか
  減らない。長い座標を持つのは一部の駅（グループの重心）だけで、gzip が既に繰り返しを畳んでいる。
  仮説は「1 割は減る」だった
- **geojson を静的生成する**——CDN が `HIT` を返しているので、関数の起動はもともとほぼ無い。
  効くのは転送量だけで、それは G1 の担当
- **キャッシュ済み GET にアプリ内レート制限を足す**——未知パラメータでキャッシュは割れる（実測）が、
  そこは **WAF がエッジで、関数が起動する前に**止める。アプリ内の制限は関数が起動してから効くので、
  同じ相手に二重の仕組みを置く価値が薄い。**WAF を入れることが前提**
- **`src/ai/rate-limit.ts` を Upstash Redis に差し替える**——前身 §4.4 が seam として想定していた道だが、
  **いまは見送る**。WAF がエッジで粗く止め、G4 が日次を DB で見る。ここに Redis を足すと
  **全リクエストに 1 往復と新しい障害点**が増える。厳密な全体制限が要ると分かってからでよい
- **監視基盤の自作**——Vercel の Observability と Firewall のダッシュボードを使う
- **ページ表示の API 呼び出し回数を減らす**——効果はあるが、これは性能の仕事であって運用ガードではない。混ぜない

## 6. 検証の作法

この案件でこれまで効いたやり方を踏襲する。

- **本番のヘッダと転送量で測る**（DevTools の見た目ではなく `curl -D -` と `%{size_download}`）
- **既存 API の本文がバイト同一**であることを、main と本ブランチをそれぞれビルドして `cmp` で
  突き合わせる（W3 と同じ手順。G1 はヘッダを変えるので、**本文だけ**を比べる）
- **429 は実測する**（ローカルで上限を踏む。`tests/api.smoke.sh` に追加）
- 純関数（ヘッダ組み立て・`onErrorRetry` の判定・日付の境目）は**ユニットで固定**する
