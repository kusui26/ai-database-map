# チャットのモデル検証 — `-latest` の差し替えを受けて（2026-09-26）

関連：`docs/feat_llm.md` §4.1（モデル）・§4.6（失敗の言い分け）・§7（eval）／PR #160

**結論**：既定を **`gemini-3.5-flash-lite`（番号つきの版）に固定**し、**温度は送らない**（＝既定 1.0）。
38/38・災害と拒否 17/17 で、いまの本番（別名 × 0.2）と品質は同じ。3.1 Flash-Lite は関門で落ちた（§4・§5）。

---

## 1. きっかけ

- 2026-09-25、本番のチャットが **31 秒待って失敗**した。調べると、既定モデル
  `gemini-flash-lite-latest`（「最新の Flash-Lite」を指す**別名**）の中身が、7 月に検証した
  **3.1 Flash-Lite から 3.5 Flash-Lite へ、こちらの知らないうちに差し替わっていた**
- **31 秒の正体**（コードから特定）：`src/ai/client.ts` の `createTimedFetch` は、モデルの
  **初回応答が 15 秒以内に来なければ打ち切って 1 回だけ再試行**する。15 秒 ×2 で 31 秒と合う。
  このとき投げられる `FirstChunkTimeoutError` は SDK が再試行も包みもしないので、PR #160 の分類では
  「生成に失敗」に落ちていた（本 PR で「一時的に応答できない」に直す・`tests/chat-first-chunk-timeout.test.ts`）
- **「3.5 は思考型だから遅い」とは言えない**：getModel では 3.1 も 3.5 も `thinking: true` で、
  Google の文書でも**どちらも既定の思考は最小（`minimal`）**である。初回応答の遅れは 7 月の 3.1 でも
  実測されていた（正常 ~1s に対しテール 7〜30s・`docs/260728_chat_scatter_plot_timeout_mitigation.md`）。
  **違いは遅れの頻度にしか出ない**ので、それを測る（§3）
- 加えて、Google は Gemini 3 系で **temperature を既定（1.0）のままにするよう強く推奨**している
  （1.0 未満は「ループや性能低下を招きうる」・[Gemini 3 の手引き](https://ai.google.dev/gemini-api/docs/gemini-3)
  の Temperature 節）。こちらは **0.2** を渡していた

つまり**いま本番で動いているモデルと設定は、一度も eval を通っていない**。

## 2. 決め方（**測る前に固定する**）

### 2.1 比べる組み合わせ

| | モデル | 温度 | 意味 |
|---|---|---|---|
| **A** | `gemini-flash-lite-latest`（＝3.5 Flash-Lite） | 0.2 | **いまの本番** |
| **B** | `gemini-3.5-flash-lite` | 既定（送らない＝1.0） | A と同じモデルで、Google の推奨どおり |
| **C** | `gemini-3.1-flash-lite` | 0.2 | 7 月に検証した系統に戻す |

C が最良だった場合に限り、**D＝3.1 Flash-Lite × 既定温度**も流して温度を決める
（推奨は Gemini 3 全体に対するもので、3.1 にも当てはまるため）。

### 2.2 合否の関門

1. **災害・拒否は 1 問も落とさない**（17/17。人命に関わる言い方の不変条件・eval の既存規則）
2. **全体 36/38 以上**（eval の既存の閾値）

### 2.3 関門を通った組み合わせの順位

1. **合格数**が多いもの
2. 合格数の差が **1 問以内**（＝揺らぎの範囲）なら、**安定性**——初回応答の打ち切り（15 秒超）と、
   再試行に頼った問が少ないもの
3. それも並ぶなら、**所要時間の p95** が短いもの
4. それも並ぶなら、**Google の推奨**（既定温度）に沿うもの

> **補足（A・C を測った後、B を測る前に追記）**：1 の「1 問以内は揺らぎ」と同じ考えを 2・3 にも入れる。
> A で見えたのは、初回応答の打ち切りが**提供元のまれな停滞**で（8〜15 秒の「長考」は 0 回、打ち切って
> 再試行すればすぐ返る・§4）、**温度では変わらない**ことだった。1 回の通し（約 95 回の呼び出し）で
> 0〜数回という出方は偶然の範囲なので、このままでは同じモデルの A と B が偶然の 1〜2 回で決まってしまう。
> そこで **2（打ち切りの回数と、再試行に頼った問の数の合計）は差が 3 以上、3 は差が 20% 以上のときだけ
> 差とみなし**、それ未満は並びとして次へ送る。
> C はこの補足の前に関門で外れており（§4）、補足は C の扱いを変えない。

### 2.4 別名か、版の固定か

**選んだモデルは、番号つきの ID に固定する**（`-latest` を既定にしない）。理由：

- 別名は**断りなく中身が替わる**。今回は替わっても**エラーは出ず**、遅さとして現れた——
  品質の変化は、なおさら気づけない
- 固定した版が退役すれば 404 になるが、PR #160 以降は `model failure kind=rejected status=404
  provider=NOT_FOUND model=…` が 1 行で残るので**すぐ分かる**。Google は退役を事前に告知する
- 次の版が出たら（Google は 2 週間前にメールで告知する）、**この eval を流してから**上げる

### 2.5 どれも関門を通らなかったら

モデルは変えない。落ちた問を分類して報告し、プロンプトかモデルかを切り分けてから決める。

## 3. 測り方

- **runner**：`tests/chat-eval.test.ts`（38 問・実 `/api/chat`）。本 PR で**所要時間・再試行・名札**を
  記録できるようにした（集計は `src/ai/eval/report.ts`・純関数・`tests/ai-eval-report.test.ts`）
- **サーバ**：ローカルの本番ビルド（`pnpm build` → `pnpm start`）。モデルは `GEMINI_MODEL`、温度は
  `CHAT_TEMPERATURE`（コード）を組み合わせごとに切り替えてビルドし直す
- **サーバのログも数える**——`[ai] モデルの初回応答に Nms（テール遅延）`（8 秒以上）と
  `[ai] 初回応答が 15000ms を超えたため 1 回だけ再試行します`（打ち切り）、`model failure` の行
  （PR #160）。遅れや失敗は、合否より先にここに出る
- **間引き**：問間 20 秒（Flash-Lite の無料枠は 15 回/分・1 問あたり 2〜3 回呼ぶ）
- **無料枠の予算**：1 回の通しで約 100〜120 回。3.5 は A・B の 2 回で約 230 回、3.1 は約 115 回
  （1 日 500 回の内側。本番の分を残す）
- **1 組につき 1 回の通し**。温度 1.0 は答えが揺れるので、合格数の 1 問差は揺らぎとみなす（§2.3）

流し方（組み合わせごと・約 16 分）：

```bash
pnpm build                                   # CHAT_TEMPERATURE を切り替えたら必ずビルドし直す
GEMINI_MODEL=gemini-3.5-flash-lite pnpm start -p 3411 > server.log 2>&1 &
EVAL=1 CHAT_BASE_URL=http://localhost:3411 EVAL_THROTTLE_MS=20000 \
  EVAL_REPORT=report.md EVAL_LABEL="B: gemini-3.5-flash-lite / temperature 既定" \
  pnpm exec vitest run tests/chat-eval.test.ts
grep -c '1 回だけ再試行します' server.log     # 初回応答の打ち切り
grep 'model failure' server.log               # 失敗の中身（種類・状態・回数）
```

## 4. 結果

2026-09-26 0:28〜1:50 JST、ローカルの本番ビルドで測った。流した順は A（0:28〜）→ C（0:43〜）→ B（1:17〜）
（B は温度の切り替えにビルドが要るので最後）。D は C が最良でなかったので流していない（§2.1）。

所要時間は、提供元の混み具合（§4.2）と手元の負荷（測った後の 2:31 に負荷平均 45・8 コア。iOS シミュレータ
などが動いていた）で揺れる。**組み合わせの間の速さの比較は、同じ時間帯に交互に流した §4.3 の実験がいちばん確か**である。

### 4.1 まとめ

| | 組み合わせ | 合格 | 災害・拒否 | 再試行に頼った問 | 初回 15 秒超の打ち切り | 提供元のエラー | p50 | p95 | 最大 |
|---|---|---|---|---|---|---|---|---|---|
| **A** | `gemini-flash-lite-latest` × 0.2（いまの本番） | **38/38** | 17/17 | 0 | 2 | 0 | 4.3s | 18.2s | 19.6s |
| **B** | `gemini-3.5-flash-lite` × 既定 | **38/38** | 17/17 | 0 | 0 | 0 | 5.0s | 12.4s | 19.8s |
| **C** | `gemini-3.1-flash-lite` × 0.2 | 33/38 | **15/17** | 6 | 5 | 9（すべて 503） | 14.1s | 50.2s | 50.6s |

- 所要時間は 1 問ぶん（`/api/chat` の 1 ターン）。再試行した問は 2 回目を採点し、その所要を数える
- 無料枠の 429 は、どの組み合わせでも 1 度も出ていない

### 4.2 C（3.1 Flash-Lite）は関門で落ちた——多くは中身ではなく混雑

- 落ちた 5 問のうち 3 問（災害の避難先 2 問を含む）は、**答えそのものが返らなかった**。提供元が
  503「This model is currently experiencing high demand」を返し（SDK の再試行を含めて 2 回とも）、
  あるいは 50 秒の上限に達した
- 残る 2 問（曖昧駅名「尼崎」・地図文脈「新宿」）は、期待した語で `searchStations` を呼ばなかった
- 返った問も 1 問 9〜18 秒かかった（A・B は 3〜5 秒）。初回応答が 8〜13 秒の回が 10 回あった
- この混雑は 3.1 に固有のものとは言えない。**同じ日の 2:33 には 3.5 Flash-Lite も、503 と 25 秒の初回応答を
  返した**（アプリを通さず curl で直接測った・3 回中 2 回が 503）。C の関門落ちの主因は、流した時間帯の混雑である
- それでも 3.1 を選ぶ理由は無い。検索語の違いで落ちた 2 問は混雑と関係がなく、Google の退役表では 3.1 は
  **早ければ 2027-05-07 に退役**し、後継に 3.5 Flash-Lite が指定されている
  （[Deprecations](https://ai.google.dev/gemini-api/docs/deprecations)）

### 4.3 A と B：品質は同じ。B の遅さは温度のせいか

- どちらも 38/38。ツールを呼んだ回数も 38 問すべてで同じだった
- **A の打ち切り 2 回は、どちらも「初回応答が 15 秒来ない → 再試行すればすぐ返る」**だった（その 2 問は、
  ふだんの所要に 15 秒を足した 18〜20 秒）。初回応答が 8〜15 秒に来た回は A・B とも 0 回。遅れは考え込み
  ではなく、**提供元のまれな停滞**である
- B は後半（災害・拒否・地図文脈）だけが遅かった（中央値：災害 5.0 → 10.7 秒、拒否 1.7 → 4.4 秒）。
  前半の 19 問は A・B とも中央値 3.8 秒で同じ

温度のせいか、流した時間帯のせいかを分けるため、**拒否の 4 問（ツールを呼ばない＝モデル 1 回）を、
0.2 と既定で同じ時間帯に交互に** 5 巡流した（計 40 回・1:37〜1:43・`gemini-3.5-flash-lite`）：

| 温度 | 所要の中央値 | 平均 | 出力トークンの中央値 | 思考トークン |
|---|---|---|---|---|
| 0.2 | 2.26s | 2.23s | 49.5 | 0 |
| 既定（1.0） | 2.03s | 2.15s | 47 | 0 |

同じ問・同じ巡の 20 組で比べても、既定の方が遅かったのは 9 組（差の中央値 −0.05 秒）。
**温度は速さにも答えの長さにも効いていない**。B の後半の遅さは、流した時間帯の提供元の遅さである。
思考トークンはどちらも 0 だった（既定の思考 `minimal` では、この種の問をほぼ考えずに答える）。

### 4.4 ログに出る「署名が無い」という警告は無害

B と C のログに、次の警告が出た（B は 4 問、C は 1 問。どれも合格）：

```
AI SDK Warning (google.generative-ai / gemini-3.5-flash-lite): Replayed 1 `functionCall` part(s) for a Gemini 3 model
without a `thoughtSignature` (tools: `getHazardAlerts`). Injected the documented `skip_thought_signature_validator` …
```

手順ごとに署名の付き方を確かめると、**並列に呼んだツールの 2 つ目以降にだけ署名が無い**
（例：`getHazardAtPoint[署名あり] + getHazardAlerts[なし]`）。温度 0.2 でも既定でも同じ形だった。
これは Google の仕様どおりで、並列のときは最初の呼び出しにだけ署名が付き、検証されるのも最初の呼び出しだけ
（[Thought signatures](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures)）。

- `@ai-sdk/google` は、ID が `gemini-3` で始まるときだけ Gemini 3 として扱い、署名の無い呼び出しに
  検証を飛ばす目印を補って、この警告を出す。警告文は「アプリが署名を落としている」と推測するが、
  ここでは当たらない
- 別名（A）は Gemini 3 と見なされないので、補いも警告も無い。最初の呼び出しには署名があるので
  400 にもならない
- つまり**番号つきの ID に固定すると、並列呼び出しのたびにこの警告が本番のログに出る**。害はない

## 5. 決定

**既定モデルは `gemini-3.5-flash-lite`（番号つきの安定版）に固定し、温度は送らない（＝既定 1.0）。**
組み合わせ B である。

規則（§2）への当てはめ：

1. 関門：A・B は通過、**C は落ちた**（災害 15/17・全体 33/38）。C が最良でないので D は流さない
2. 合格数：38 対 38 で並ぶ
3. 安定性：A は 2（打ち切り 2・再試行 0）、B は 0。差 2 は補足により並び（補足前の文面なら、ここで B）
4. p95：18.2 秒対 12.4 秒（32% 短い）で **B**

ただし §4.3 のとおり、p95 の差は温度から来たものではない（A の 2 回の停滞と、B を流した時間帯の遅さ）。
実質は「品質が同じなら Google の推奨に従う」（段 4）と同じ結論で、**補足の有無にも、どの段で決まるかにも
依らず B になる**。

版の固定（§2.4）について：

- 別名は測定の日（2026-09-26 1:49 JST）も 3.5 を指していた（generateContent の `modelVersion:
  gemini-3.5-flash-lite`）。**固定しても本番のモデルは変わらない。変わるのは温度だけ**である
- 固定の理由に、測定中に分かったことが 1 つ加わる：ID が `gemini-3…` なら SDK が Gemini 3 として扱う（§4.4）
- プレビュー版（`-preview`）も既定にしない。数か月で退役するため（例：3.1 Flash-Lite Preview は
  2026-03-03 公開、05-25 退役）。`tests/ai-client-model.test.ts` が番号つき・非プレビューを見張る
