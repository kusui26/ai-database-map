## 2. #1 駅を替えるとタブが戻る

### 2.1 いま起きていること

東京駅で「所得」タブを選び、検索で新宿駅に切り替えると、タブは**「乗降客数」に戻る**。

### 2.2 根：戻す処理がわざわざ書いてある

`src/components/detail/StationDetailPanel.tsx:335`・`:351-354`

```ts
const [tab, setTab] = useState<DetailTab>('passenger')
// 駅が変わったら乗降タブへ戻す（ただし焦点要求が保留中なら上の効果を優先）
useEffect(() => {
  if (requestedRef.current === null) setTab('passenger')
}, [grp])
```

- 駅（`grp`）が変わるたびに乗降へ戻す。**閉じる**（`grp` → `null`）でも同じ効果が走るので、開き直しても戻る。
- タブは `useState` にしか無い。**リロードで消え、URL にも載らない**（「所得タブを見て」とリンクで送れない）。
- チャットの ⤢ が要求する焦点タブは、別経路の「1 回だけ消費する要求」（`chatStore.requestedCategory`・`:337-349`）で、
  上の効果と `useRef` で譲り合っている。仕組みが 2 本ある。

### 2.3 直し方

| 案 | 中身 | 駅の切替 | リロード | 共有リンク | 戻る/進む |
|---|---|:-:|:-:|:-:|:-:|
| A | 戻す効果を消すだけ | ○ | × | × | × |
| B | A ＋ ブラウザに保存（localStorage） | ○ | ○ | × | × |
| **C（推奨）** | **タブを URL（`?tab`）に載せる ＋ 無いときはブラウザの記憶** | ○ | ○ | ○ | ○ |

**C を推奨**。タブを `grp`・`r` と同じ「URL が正」の状態にする。

- タブの決まり方（上が優先）：① URL の `?tab` → ② **この端末で最後に選んだタブ**（原文の「ブラウザ覚えておいて」）→ ③ 乗降客数。
- 駅を替えても `?tab` は残る（`setGrp` は `grp` しか触らない）＝**同じ項目を見続けられる**。
- **チャットの焦点も同じ経路で書く**（`?tab` を書くだけ）。1 回消費の `requestedCategory` と `useRef` の譲り合いは消える。
- 書き込みは replace（タブの切替を履歴に積むかは §12-2）。既定（乗降）は nuqs の `clearOnDefault` で URL から消える。

**型で塞ぐ**：`DetailTab = Category | 'hazard'`（`src/shared/constants.ts:83`）は `population_forecast` を含むのに、
タブ帯（`DETAIL_TABS`）には無い。これが §4.3 の不具合の根なので、`DetailTab` から `population_forecast` を外し、
カテゴリ → タブの写像（`population_forecast` → `population`）を 1 つの純関数にする。

### 2.4 実装

### 2.5 検証

- 単体：`isDetailTab`（9 タブ・`population_forecast`・空文字・数値・null）、`resolveDetailTab`（URL 優先・記憶の不正値・両方なし）、

### 2.7 実施記録（A1・2026-10-02）

§12-1・§12-2 は推奨どおり（URL＋この端末の記憶／タブは replace）で実装した。§4.3 の不具合と §4.4(a) も同じ PR に入れた。

- **決め方**：`components/detail/detailTab.ts`（`resolveDetailTab`・記憶の読み書き）と `useDetailTab.ts`（`?tab`）。
  駅詳細パネルの「駅が変わったら乗降へ戻す」効果と、`chatStore` の 1 回消費の `requestedCategory` を消した。
- **チャット**：`data-promotions` の焦点を `detailFocus.ts`・`useApplyDetailFocus.ts` で `?tab` に書く。⤢ のチップも同じ道。

計画から変えた点：

1. **乗降客数も URL に明示して書く**（計画は既定値を URL から消すとしていた）。URL に無いときは「この端末の記憶」を

   そのたびに当てると、回答の途中で利用者が替えたタブが戻ってしまう。質問を送るたびに当て直す。

## 3. #2 回答が最後まで見えない

### 3.1 いま起きていること

| 測ったもの | 値 |
|---|---|
| 長めの回答（15 行＋図のチップ）を 3 往復したあとの、スレッドの末尾までの残り | **303 → 1,161 → 2,020px** |
| 駅を選んだ状態での、スレッドの見える高さ（送信前 → 回答待ち → 回答後） | **488 → 602 → 464px** |

### 3.2 根は 3 つ

1. **スクロールの制御が何も無い**。スレッドは `overflow-y-auto` の箱（`ChatPanel.tsx:142`）だけ。
   短い回答でも数往復で枠を超え、以後の回答は**枠の下に出続ける**。
2. **回答の前後で枠の高さが変わる**。回答待ちの間はサジェストを**消し**（`ChatPanel.tsx:181`）、回答後に戻す。
   駅を選んでいるとサジェストは 8 個（4 段）あり、それと「会話をクリア」が戻った瞬間に枠が **138px 縮む**。
   回答の終わりで末尾へ送っても、**直後に末尾の 138px が隠れる**。
3. **図のチップは本文のあとに届く**（`data-map` は本文の後）。本文が出たあとに高さが伸びる。

### 3.3 直し方

| 要素 | 中身 |
|---|---|
| **末尾に追従** | 利用者が末尾にいる間は、中身が伸びるたびに末尾へ送る。上へスクロールしたら**追わない**（読んでいる所を奪わない） |
| **長い回答は頭を見せる** | 質問＋回答が枠より高いときは、末尾ではなく**質問の頭を枠の上端**に合わせる（ハザードのカードは会話の中に出るので背が高い） |
| **送信したら必ず末尾へ** | 送った質問と「考え中」は必ず見せる |
| **枠の高さを変えない** | 回答待ちの間もサジェストを**消さずに無効化**する（押せないが場所は取る） |
| **「↓ 最新の回答」ボタン** | 追従を外れている間に新しい中身が来たら出す |

**部品は既存ライブラリを推奨**：[`use-stick-to-bottom`](https://github.com/samdenty/use-stick-to-bottom)
（MIT・1.1.6・React 19 対応・StackBlitz 製）。中身の伸びの監視、利用者のスクロールで追従を外す判定、`isAtBottom`、
`scrollToBottom`、**追従先を差し替える `targetScrollTop`** を持つ。CLAUDE.md §3「ライブラリ既存ユーティリティを自作より優先」に沿う。
**パッケージの追加なので可否を決めてほしい**（§12-3）。自作でも 50 行ほど（ResizeObserver ＋ 位置の判定）で書ける。

根 2 は「枠の高さを変えない」で潰す。

// questionTop_px が null なら bottom_px。それ以外は max(0, min(bottom_px, questionTop_px - margin_px))

## 5. #4 戻るで UI を戻したい

### 5.1 いま起きていること

`about:blank` → アプリ → 検索で東京 → 新宿 → **ブラウザの戻る**で、**`about:blank`（アプリの外）に出る**。

### 5.2 根：何も積んでいない

| 状態 | 置き場 | 履歴 |
|---|---|---|
| 選択駅 `grp`・半径 `r` | URL（`useMapUrlState.ts`） | **replace**（nuqs の既定） |
| ハザードのレイヤ `hz`・`hzop` | URL | replace |
| おすすめを開いているか `rec`・条件 `rec*` | URL | replace |
| 詳細のタブ | `useState` | **URL に無い** |
| 図（キャンバス／モーダル） | Zustand（`chatStore.promotion`） | **URL に無い** |
| ランキング・散布のダイアログ（FAB） | `useState`（`Fab.tsx:122-123`） | **URL に無い** |

URL に載っているものも**すべて replace** なので、戻るに積まれるものが 1 つも無い。
`useMapUrlState.ts` の冒頭コメント「戻る/進むで状態が復元される」は、実際には成り立っていない。

### 5.3 方針：戻る＝「直前の画面の移動」を取り消す

| 操作 | URL | 履歴 | 理由 |
|---|---|---|---|
| 駅を選ぶ（地図・検索・会話の駅名・順位表の行・AI） | `grp` | **push** | 場所を移る＝移動。戻るで前の駅へ（地図も飛んで戻る・`MapView.tsx:364-379`） |
| 詳細を閉じる | `grp` を消す | **push** | 戻るで開き直せる |
| 図を開く（AI の自動・チップ・FAB） | `fig` ほか（§5.5） | **push** | **原文の核心**：開いたものを戻るで閉じられる |
| 図を閉じる | `fig` を消す | **push** | 戻るで開き直せる |
| おすすめを開く・閉じる | `rec` | **push** | 同上 |
| 半径・タブ・図やおすすめの中の条件 | `r`・`tab`・`fig*`・`rec*` | replace | 同じ画面の中での調整。積むと戻るが調整を 1 つずつ遡るだけになり、アプリから出るのに何十回も押すことになる |
| ハザードのレイヤ（手で切替） | `hz` | replace | 調整に近い |
| システムが自動で変えるもの（警戒モード・不正値の丸め） | — | **必ず replace** | 利用者がしていない操作を戻るに積まない |
| チャットの開閉・現在地・About | URL に載せない | — | 現在地は共有リンクに載せない（`geoStore.ts` の方針）。チャットは既定で開く画面なので積まない |

**「閉じる」を `history.back()` にしない理由**：図を開いたあとに駅を選ぶと（push）、閉じるボタンの `back()` は
**駅の選択を取り消すだけで、図は開いたまま**になる。閉じるも 1 つの移動として push する方が、どんな順序でも壊れない。

**タブは replace を推奨**するが、原文は「UI のイベントは history に積んで」とも読める。決めてほしい（§12-2）。

### 5.4 1 回の回答で積むのは 1 つ

サーバはツールが成功するたびに `data-map` を送り直す（部分成果の先出し）。そのたびに push すると、1 回の回答で履歴が 2〜3 個積まれ、
**戻るを押しても何も変わらない**ことが起きる。

- 送信のたびに「この回答ではまだ積んでいない」に戻し、**最初の適用だけ push、2 回目以降は replace**。
- nuqs 2.9.0 は同じ tick の更新を 1 回の URL 更新に束ね、**束の中に push が 1 つでもあれば全体を push にする**
  （`node_modules/nuqs/dist/debounce-*.js` で確認）。駅の選択・焦点のタブ・ハザードのレイヤは 1 つの履歴になる。

### 5.5 図も URL へ

図を URL に載せないと、戻る・進む・リロードで開き直せない。

- パラメータは `rec*` と同じ流儀（読める・既定は書かない）：`fig`（`ranking`/`scatter`）・`figM`（指標）・`figX`/`figY`・`figO`（順）・

### 6.2 根

1. **ランキング・散布に市区町村・範囲の条件が無い**。`listStations` は `municipality`・`bbox`・`near` を持つ
   （`tool-specs.ts:229-268`・SQL `list_stations`）のに、`rankStations` / `compareGrowth` は都道府県・会社・路線・種別だけ
   （SQL `rank_by_column`・`scatter_points` も同じ）。AI は県や会社で**代用する**しかない。
   - **「○km 範囲」（探す範囲）を入れる場所が無い**。ランキングにある距離の引数は `radiusM`（**各駅の周りを何 km で集計するか**）だけなので、
     AI は「5km範囲」をそこに入れる。半径に依らない指標（最寄地価）では何も変わらず、半径のある指標では**指標そのものが変わる**（§6.1.1 の 3km）。
   - **距離を知らないまま距離を語る**。道具は起点からの距離を返さないので、「5km圏内ではありません」と根拠なく書く（新宿三丁目は 4,871m で圏内）。
2. **路線・会社の表記ゆれ**。データの正式名は「東横線」（「東急東横線」ではない）、会社は「東急電鉄」（旧社名「東京急行電鉄」ではない）。
   東京メトロは「4号線丸ノ内線」「5号線東西線」、都営は会社名が「東京都」で「1号線浅草線」、小田急の本線は「小田原線」、
   JR の中央線は「中央線」（「中央線快速」「中央本線」ではない）（`/api/routes` で確認）。
   **利用者の言い方では 0 件**になり、AI は当てずっぽうの再試行を繰り返す。さらに「東西線」とだけ書くと、
   **札幌・仙台・京都の東西線（49 駅）に当たり、東京メトロの東西線（23 駅）は入らない**——0 件より気づきにくい。
   - **名前を正しく解決しても、駅の集合が違う**（B1 のあとで判明・§6.8）。データの路線は**法令上の線路の名前**で、
     利用者の言う路線（運行系統）ではない。「山手線」は 17 駅しかなく、東京・上野・秋葉原など 13 駅は東海道線・東北線の側にある。
3. **エリアの性格を 1 回で返す道具が無い**。`getStationDetail` は 1 カテゴリずつで、「どんなエリア？」には乗降だけで答え、残りを一般知識で埋める。
4. **地図の文脈が「選択駅」しか無い**。「このあたり」「地図に出している範囲」は伝わらない（`/api/chat` の入力は `selectedGrp` と `radiusM` だけ）。
5. **エリアを単位にした集計が無い**（#8）。どの道具も「駅（点）を並べる」まで。

### 6.3 GIS の定石との対応

§9.1 の調査で、GIS・商圏分析・住まい探しのツールはどれも
**「エリアを決める → エリアで集計する → 定型レポート・塗り分け・順位を出す」** の繰り返しだと分かった。
本アプリは「エリアを決める」が都道府県・会社・路線までで、**「エリアで集計する」と「塗り分け」が無い**。#5 と #8 はこの欠けの表と裏である。

⚠ **駅の値を市区町村で足してはいけない**。隣の駅の円は重なっているので**二重に数える**。中央値（地価）や率（増減率）はそもそも足せない。
エリアの値は**メッシュから面積按分で計算し直す**（既存の人口・事業所と同じ作法）。

### 6.5 共通 API が先（CLAUDE.md §2）

### 6.7 実施記録（B1・2026-10-07）

    「東西線」× 大阪府 → JR東西線）。残れば候補
    （呼び直しにそのまま使える `operators`・`routes`、駅の数・都道府県）を返す

### 6.8 B1 で見えた課題：データの「路線」は、利用者の言う路線ではない（2026-10-08）

B1 で名前は正式名に解決できるようになった。ところが本物のデータで確かめると、**解決した先の駅の集合が、利用者の思う路線と違う**。
データの路線（国土数値情報 S12）は**法令上の線路の名前**で、利用者が言う路線（**運行系統**）とは別物だからである。
「データの山手線は 17 駅です」と断るのは、利用者から見れば「データを整備しろ」でしかない。**データの持ち方で直す**。

#### 6.8.1 何が起きるか（実データ・2026-10-08）

| 利用者の言う路線 | 駅数 | データ（法令上の路線）で集計すると |
|---|--:|---|
| 山手線 | 30 | 「山手線」は **17 駅**（品川〜渋谷〜新宿〜池袋〜田端）。東京・有楽町・新橋・浜松町・田町・高輪ゲートウェイ・西日暮里・日暮里・鶯谷・上野・御徒町・秋葉原・神田の **13 駅は東海道線・東北線の側**にある |
| 中央線（快速・東京〜高尾） | 24 | 「中央線」は**東京駅を含まず**、神田〜名古屋の 111 駅（信濃町・千駄ヶ谷など各駅停車だけの駅も含む） |
| 京浜東北線（大宮〜横浜） | 36 | 同じ名前の路線が無い。一番近い「東北線」でも 22 駅しか拾えず、余分が 123 駅 |
| 副都心線（和光市〜渋谷） | 16 | 「13号線副都心線」は 11 駅。和光市〜小竹向原の 5 駅は法令上「有楽町線」 |

- **駅は全部ある**。山手線の 30 駅はどれもデータの駅（grp）として存在する（東京駅は東海道線・東北線・総武線・京葉線などの駅として）。
  欠けているのは「どの駅がどの運行系統か」という**束ね方**だけ。
- **山手線だけではない**。駅データ.jp の営業中の 601 路線（利用者の呼び方の路線）を法令上の路線 1 本と突き合わせると、駅が一致するのは
  375（62%）。94（16%）は余分な駅が混ざり、**132（22%）は駅が欠ける**（1 割を超えて欠けるのが 81、3 割超が 39）。
  種別では路面電車が 45 路線中 27 と多く、地下鉄は 42 路線中 5 と少ない（地下鉄は番号を外せば法令上の名前と同じことが多い）。
  欠けるのは、環状運転（山手線・名城線・伊予鉄道環状線）、直通運転（副都心線・目黒線・相鉄・JR直通線）、
  複数の線路にまたがる JR の系統（京浜東北線・埼京線・横須賀線・中央・総武線）、路面電車の系統（熊本市電 A 系統・広電 2 号線）。
- **B1（#172）は名前の表で一部だけしのいでいる**：「中央線快速」は中央線全体へ広げて断り、「京浜東北線」などは正式な路線を候補で返し、
  「山手線」は聞き返して、JR を選ぶと 17 駅で答える。L3 でこれらを置き換える。

#### 6.8.2 3 つの論点と結論（2026-10-08 に推奨どおり決定・§12-13・15〜19）

| 論点 | 結論 |
|---|---|
| ① 名前ごとの既定（「山手線」＝JR 東日本など） | **足さない**。同じ名前の路線は**地図の表示範囲**で決め、決まらないときだけ聞き返す（§6.8.6） |
| ② 見た目を整える（「5号線東西線」「（全国・東京都・上位）」など） | **独立の PR は作らない**。③で路線名が利用者の呼び方（「東京メトロ東西線」「都営浅草線」）になり、図の題・選択肢・AI の本文がそれに替わる。会社は駅データ.jp の通称で出す（§6.8.7） |
| ③ 路線を運行系統のデータで持ち直す | **やる（L1〜L4）**。原典は**駅データ.jp**。法令上の路線（S12）は駅の帰属として裏に残し、「路線」の正にはしない（§6.8.3〜§6.8.5） |

#### 6.8.6 同じ名前の路線をどう決めるか（論点①）

- 運行系統にしても、名前だけでは決まらない路線は残る：「山手線」＝JR山手線（30 駅）・神戸市営地下鉄山手線（8 駅）、
  「東西線」＝東京メトロ・札幌・仙台・京都・JR、「中央線」＝JR中央線(快速)・大阪メトロ中央線、「新宿線」＝都営・西武（どちらも東京）。
- **名前ごとの既定は足さない**。表に入れて安全なのは事実上「山手線」だけで、ほかは地域で意味が変わる（大阪の人の「中央線」は大阪メトロ）。
  1 行の例外のために仕組みを足し、地域を見ないまま、ほかの地域の人に黙って違う路線を出すことになる。
- **地図の表示範囲で決める**：チャットの送信時に地図の範囲（丸めた bbox）を同送し、範囲の中に駅のある候補が 1 本ならそれに決めて
  `nameNotes` で断る。地図の初期表示は東京駅中心・ズーム 9（首都圏が入る）なので、首都圏の人には何もしなくても
  「山手線 → JR山手線」「東西線 → 東京メトロ東西線」「中央線 → JR中央線」に決まり、大阪を見ている人には「中央線 → 大阪メトロ中央線」に決まる。
  範囲に 2 本ある（新宿線）・範囲が広すぎる（全国）ときだけ聞き返す。明示の都道府県・会社はこれより強い。
- これは B3（地図の文脈）の**前半**にあたる。名前を決めるのに要るのは範囲の同送だけで、B2（範囲の条件）を待たなくてよいので、
  **L3 で入れる**。「このあたり」の質問（B3 の本体）は B2 のあと。

#### 6.8.7 見た目（論点②）

- 路線名は L で利用者の呼び方になるので、「5号線東西線」「1号線(御堂筋線)」「1号線」（横浜市・千葉モノレール）は、
  **選択肢・図の題・AI の本文に出なくなる**。
- 会社は、駅データ.jp の事業者名（「JR東日本」「東京メトロ」「東京都交通局」「Osaka Metro」。略称の列には「相鉄」「南海」もある）で出す。S12 の会社名
  （「東日本旅客鉄道」「東京地下鉄」「東京都」）は鍵として残す（対応表は L1）。都営の会社名が「東京都」で、
  図の題「（全国・東京都・上位）」が都道府県と紛れる問題もこれで消える。
- 駅名の区別（「大塚（東日本旅客鉄道）」）は DB の関数で作っているので、L4 で事業者の通称に替えるか、別に直す。
- 正式名は捨てない：選択肢のホバーと `nameNotes` に残す（鉄道の専門家には法令上の名前も要る）。

#### 6.8.8 実施記録（L1・2026-10-08）

- **結果**：営業中の 601 路線・駅レコード 10,620 のうち **10,617（99.97%）をアプリの駅に結んだ**（駅名の完全一致 10,523・鍵の一致 94・

  （直しの表を当てたあとの数え直し。§6.8.1 の 22% とほぼ同じ）。

計画から変えたこと・実装で分かったこと：

1. **候補の選び方を「会社名 → 駅名の完全一致 → 近さ」にした**（計画は完全一致が先）。完全一致を先にすると、島原鉄道の「諫早」が

### 6.10 実施記録（B3・2026-10-09）

「このあたりで地価が上がっている駅は？」に、地図に表示中の範囲で答える。L3 で送信に同送するようになった地図の範囲は、

## 8. #9 AI が聞き取って絞る

### 8.1 いまの答え

例の質問をそのまま投げると、**ツールを 1 つも呼ばず**、「条件の組み合わせ…（通勤時間・地価・将来の人口動向など）によって変わります。
画面下の『おすすめ』ボタンから…比較できます」と返して終わる。聞き返さず、**扱えない通勤時間を考慮点として挙げている**。

### 8.2 根

- **W6 を見送ったまま**（2026-09-16・`260912_gui_chat_protocol.md` §13.7）。チャットはボタンへ案内するだけで、条件を渡す手段が無い。
  見送り時に決めた**再開の条件は「チャットでおすすめを聞かれている事実が出たとき」**——このフィードバックがその事実である。
- おすすめ画面の 6 軸（将来人口・実績人口・地価トレンド・地価水準・乗降回復・乗降水準）では、例の条件を表せない。

| 例の条件 | 何に当たるか | いま | 足すもの |
|---|---|:-:|---|
| 大手町と横浜に通勤 | 2 つの勤務地への所要時間 | × | C6 |
| 世帯年収 1,500 万 | 予算（買える価格帯） | △ 地価公示だけ | C4 |
| 子ども 2 人 | 子育て世帯の多さ・保育・学校 | × | C1・C2 |
| 家を買う | 資産性・災害 | ○ | おすすめの 6 軸＋災害 |

⚠ 年収から買える価格を**計算して断定しない**（プロンプトの「助言の断定をしない」に当たる）。予算は本人に聞く。

### 8.3 設計：聞き取り → おすすめ画面へ条件ごと引き渡す（W6 の軽い版）

1. **聞く**：複数の要因をまとめた推薦の問いには、**最大 3 問・1 回に 1 問・選択肢つき**で聞く
   （例：①通勤で許せる時間 ②予算と、戸建てかマンションか ③重視する順〈資産性・利便・子育て・災害〉）。文中に答えがあるものは聞かない。
2. **写す**：答えを**おすすめの条件（`RecommendCriteria`）に写すのはドメインの純関数**。LLM に重みの数値を作らせない
   （例：子育て重視 → ファミリー（持続性）、資産性重視 → 資産性重視、災害を避けたい → 足切り）。
3. **開く**：新しい道具 `recommendStations`（共通 API `/api/recommend` の薄い包み）が、おすすめ画面を**その条件で開く**昇格
   （`shared/promotion.ts` に `recommend` を足す。GUI Chat Protocol は変えない）を返す。
   画面は W1〜W5 のまま（方法・重み・除外・敏感度・限界・出典）。**チャットは自分で順位を作らない**（`260912_gui_chat_protocol.md` §13.4 の規範）。
   道具が LLM に返すのは、使った条件・候補の駅数・上位数駅の名前・限界だけにする（順位の説明は画面に任せる）。
4. **言う**：本文では**使った条件と、見ていない条件**（通勤時間・予算の適合・学校の質）をはっきり書く。

**選択肢のボタン**：AI の質問に選択肢を添えるため、サーバが `data-replies`（選択肢の配列）を送り、画面は入力欄の上にボタンで出す。
押すと**その文言を利用者の発話として送る**——サーバは会話を本文だけで再構成している（`route.ts` の入力スキーマ）ので、この形なら壊れない。

### 8.4 通勤（大手町・横浜）の扱い

C6 が入るまでは**通勤時間を扱えない**。路線の所属（`station_routes`）での近似も効かない。

- 大手町を通る路線（丸ノ内・東西・千代田・半蔵門・三田）と横浜駅を通る路線（東海道・横須賀・根岸・東横・京急・相鉄・みなとみらい・ブルーライン）に
  **共通のものは無い**。路線の所属だけで「両方へ乗り換えなしで行ける駅」を探すと **0 件**になる。
- 一方、実際には**直通運転**で両方へ乗り換えなしで行ける駅がある。都営三田線は 2023-03-18 から東急目黒線・新横浜線を経て相鉄線へ直通しており
  （[東京都交通局](https://www.kotsu.metro.tokyo.jp/pickup_information/news/subway/2022/sub_p_2022121610731_h.html)）、相鉄本線の駅は横浜駅にも直通する。
  `station_routes` は直通運転を表せないので、これも拾えない。

だから C6 までは、聞き取りで**候補のエリアや路線を利用者に挙げてもらう**のが誠実である。

### 8.5 制約

- 会話の合計は **4,000 字まで**（`route.ts` の `MAX_CONVERSATION_CHARS`）。3 問の聞き取りは 1,000〜1,500 字の見込み。長い会話のあとでは超えうる。
- 無料枠は **1 日 500 リクエスト**（モデルの呼び出し回数）を全利用者で分け合う。聞き取り 1 回で 5〜7 回ほど使う
  （質問のターンは 1 回ずつ、最後のターンはツールの段数ぶん）。
- 評価は 1 問 1 答しか無い。**複数ターンの評価**（台本どおりに答え、最後のターンの道具と条件を判定）を足す。

## 9. #6 進化の方向 — GIS の定石・前提なしの利用テスト・対話だけで分析

### 9.1 GIS で一般的な分析と、本アプリの対応（2026-10-01 調査）

jSTAT MAP（総務省統計局）・RESAS・不動産情報ライブラリ・ArcGIS Business Analyst・QGIS・MarketAnalyzer（技研商事）・
不動産ポータルの街ランキングを調べた。どれも中核は **「エリアを決める → エリアで集計する → 定型レポート・塗り分け・順位を出す」** だった。

| 分析の型 | 答える問い | 本アプリ |
|---|---|:-:|
| ① 半径の集計（バッファ） | 駅から○m 以内に何人・何社？ | ○（6 半径。中心は駅だけ） |
| ② 到達圏（徒歩・車・電車） | 電車で 30 分で届く範囲は？ | × |
| ③ 商圏モデル（ハフ） | 競合を考えた来店確率は？ | × |
| ④ エリアの概要・比較 | どんな地域か、他と比べて？ | △（駅のカテゴリごと。エリアは無い） |
| ⑤ 主題図（塗り分け） | エリアの**中のどこが**高い？ | ×（駅の印は 2 値だけ） |
| ⑥ ホットスポット | 高い値が固まっている所は？ | ×（散布の k-means は空間を見ない） |
| ⑦ アクセシビリティ | 最寄りの病院・保育所まで何 m？ | △（バス停・避難場所のみ） |
| ⑧ 重ね合わせ | 浸水想定区域に何人住んでいる？ | △（地点の判定のみ。人口との重ねは無い） |
| ⑨ 時系列・将来推計 | 20 年でどう変わった？2050 年は？ | ○（人口 1995–2020・推計〜2070・地価・乗降） |
| ⑩ 適地選定・スコアリング | 条件に最も合う駅は？ | ○（おすすめ） |
| ⑪ 沿線分析 | この路線の沿線人口は？ | △（路線で絞った順位・散布だけ） |
| ⑫ 駅勢圏・利用者推計 | 新駅で何人乗る？ | △（半径の値のみ） |

**「もっと基本的な部分」**＝足りないのは、エリアを**決める**（市区町村・沿線・範囲・到達圏）、エリアで**集計する**、
エリアの**概要と比較**、エリアの中を**塗り分ける**、の 4 つで、§6 の B1〜B5 がそのまま当たる。
次に重ね合わせ（C3）・施設へのアクセス（C2）・到達圏（C6）。日本で効くエリアの単位は
**会話の語彙としての「市区町村＋沿線・駅勢圏」と、計算の土台としての「メッシュ」**、住まい探しではこれに町丁目・学区・通勤圏が加わる。

参考：対話 AI 向けの「○分圏」の部品は外部に既にある（駅すぱあと API の MCP サーバー「範囲探索」・2026-09-03・複数の起点から共通して行ける駅を返す・有料）。

### 9.2 対話だけでいろいろな分析ができるための原則

1. **どの道具も同じエリアの条件を受ける**（B2）。道具ごとに絞り方が違うと、AI は代用して間違える（§6.1.1 の竹橋・立川、§6.1.2 の横浜市）。
2. **名前はサーバが解決する**（B1）。正式名を当てさせない。
3. **1 回で要点が返る道具を置く**（B4・B5）。上限 6 ステップと応答時間の中で、5 回の呼び出しを連ねさせない。
4. **曖昧なら聞く**（D1）。推測で絞らない。
5. **道具は「見ていないこと」も返す**。AI はそれを本文に書く。
6. **能力を足すたびに評価を足す**（ゴールデン・複数ターン）。

### 9.3 前提なしの利用テスト（R2）

| 項目 | 中身 |
|---|---|
| いつ | Phase A のあと（既知の不満で時間を使わせない）。B と並行 |
| 誰に | 3 つの用途（鉄道の輸送計画・出店・住まい探し）から各 2〜3 人。アプリを知らない人 |
| 渡すもの | **目的だけ**（例「家を探している。候補の街を 3 つに絞ってください」）。操作や用語は教えない |
| 進め方 | 本番の URL・PC と携帯・画面録画（同意の上）・思考発話・30〜45 分 |
| 見ること | ①自然に出るエリアの言い方（市・区・路線・「○○駅周辺」・「徒歩○分」・学区・「○分で通える」）②問いの型（どこ？／どれくらい？／どっち？）の比率 ③名前が挙がった足りないデータ ④行き詰まり・言い直し・チャットの失敗（サーバの失敗ログと突き合わせる）⑤最初の役に立つ答えまでの時間 |
| 出すもの | 所見の文書 → B・C・D の優先度の見直し |

①は B1・B2 が受け付ける語彙と単位の優先度を、③は C の順を決める材料になる。

## 11. やらないこと・線引き

- **LLM に数値・順位・重み・性格づけを作らせない**。すべてドメイン（共通 API）が決め、LLM は説明する。
- **駅の値を足してエリアの値にしない**（§6.3）。
- **治安を「安全」「危険」とラベルにしない**。件数・人口あたりの事実と、範囲・罪種の偏りだけを出す。
- **年収から買える価格を断定しない**（予算は本人に聞く）。
- **学区を駅で断定しない**（学区は住所で決まる）。学校の質は扱わない（全国データが無い）。
- **推薦の「正解」を主張しない**（`260912_gui_chat_protocol.md` §13.4 の規範のまま）。
- **「商用不可」「再配布不可」のデータを公開の API に載せない**（無料の公開アプリが非商用に当たるかは解釈が分かれるため、安全側）。
- **法令上の路線のまま、利用者の言う路線として答えない**（山手線を 17 駅で答えない。運行系統の駅の集合で答える・§6.8）。
  「データの山手線は 17 駅です」のような断り書きで済ませない。
- **駅データ.jp の原データをリポジトリに入れない**（`data/` に置く。DB と API には加工した対応だけを載せる）。
- 物件・個人の情報は扱わない。
