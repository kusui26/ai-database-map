## 0. サマリ（結論先出し）

**いまの説明は、どこでも「データの名前」が主語になっている**（「駅周辺のデータ（乗降客数、人口、地価…）について質問してください」）。
利用者が知りたいのは「これで何ができるか」なのに、それを書いた場所が無い。説明の言葉も場所ごとにばらばらで、同じ源が無い。

**直し方は 3 つだけ**：

1. **説明の型をそろえる**——どこでも「何のアプリか（1 行）→ 何ができるか（やりたいこと 4 つ・例の質問つき）→ どう始めるか（1 行）」の順
2. **説明を 1 つの源にする**——`src/shared/guide.ts`（型つきの定義）と共通 API `GET /api/guide`。説明用ページ・最初の画面・
   AI の答え・MCP が同じ源を読む（CLAUDE.md §2。言葉がずれない）
3. **出し先を 4 つに**——説明用ページ（新設 `/about`）・最初の画面（チャットの空の状態と携帯の初回）・AI の答え（「何ができる？」）・
   MCP の `instructions`

**②（任意の場所と半径）**は段階に分ける。いますぐ直すべきは **AI の正直さ**——住所を聞かれると、黙って同じ名前の駅に
読み替えて答えている（§2.2）。地図で地点を選べるようにするのは次の段、地点の周りの人口などを数えるのは
データの作り足しが要るので**別の計画**にする（§7）。

| PR | 中身 | Gemini |
|---|---|---|
| **PR-1** | 説明の源（`guide.ts`・`/api/guide`）・説明用ページ `/about`・About の冒頭・検索や SNS の説明文 | 0 |
| **PR-2** | 最初の画面（1 行＋やりたいこと 4 つ・携帯の初回の案内） | 約 10 回（例の質問の答えを確かめる） |
| **PR-3** | AI の「何ができる？」（ガイドを返す道具）・住所の問いの断り（②-1）・MCP の `instructions` | 約 350 回（全問の A/B） |
| **PR-4** | ②-2：地図で地点を選ぶ → 地点のカード（災害・近くの駅） | 約 30 回 |
| 別の計画 | ②-3：地点の周りを数える（任意の半径）・②-4：住所で探す | — |

決めてほしいことは §10（推奨つき 7 つ）。

## 1. 依頼とユーザーの声

> ① AI Database Mapアプリのことを何も知らないユーザーがアクセスすると、何をするためのアプリなのかがパッとわからないと思ったので、
> このアプリを使えば何を達成できるかわかると良いなと思いました
> 個人の住宅購入に限っていえば、駅ベースで最初は進めて、最後は購入予定周辺の情報を知りたくなるので、任意の場所と半径で
> 周辺データが見れるとさらに使い勝手がよくなる気がします

この計画での読み方：

| | 声 | この計画で |
|---|---|---|
| ① | 何をするためのアプリか、ぱっと分からない。**何を達成できるか**が分かるとよい | 本題（§4〜§6・PR-1〜PR-3） |
| ② | 住宅購入は駅から始め、**最後は購入予定の場所の周り**を知りたくなる。任意の場所と半径で見たい | 段階に分ける（§7・PR-3 の一部と PR-4・残りは別の計画） |

## 2. いまの状態（2026-11-28 に確かめた）

main（60d2e07・本番と同じ）のビルドを手元で起動し、Playwright（1440×900・390×844）で最初の画面を開いた。AI には 3 問を聞いた。

### 2.1 説明が出る場所と、いまの言葉

| 場所 | いまの言葉 | 利用者にとって |
|---|---|---|
| ブラウザの題（`title`） | 「AI Database Map — 駅×半径のオープンデータ地図」 | 「駅×半径」「オープンデータ」は作る側の言葉 |
| 検索・SNS の説明（`description`・OG） | 「オープンデータ（乗降客数・人口・地価・バス・事業所…）を駅×半径で集約し、地図とAIで誰でも使えるようにするWebアプリ。」 | 何に使えるかが無い |
| 画面の左上 | PC：「AI Database Map ⓘ」／**携帯：丸印と ⓘ だけ（名前も出ない）** | 携帯では何のアプリか、手がかりが無い |
| チャットの最初（PC は開いている・携帯は閉じている） | 「駅周辺のデータ（乗降客数、人口、地価、バス停数、事業所数、従業者数）について質問してください。」と例の質問 4 つ（東京駅の人口推移・亀有駅の浸水・神奈川県の乗降の増加・品川駅） | **データの名前から考えさせている**。年齢・将来・災害・売上が抜けていて、言える範囲とも合わない |
| 入力欄 | 「質問を入力…（例：新宿駅の地価は？）」 | — |
| 道具のボタン | 現在地・ランキング・散布図・エリア（**携帯は記号だけ**）。上に 500m〜20km（**何の距離か書いていない**） | 押すと何が出るか分からない |
| About（ⓘ） | 題「このアプリ・データ出典」。1 段落「公的オープンデータ（…）を駅からの半径で集約し、地図とAIで誰でも扱えるようにする実験的な Web アプリです…」と、出典の一覧 | 説明はデータの言葉。ほとんどが出典の一覧 |
| `/ai`（Claude で使う） | 導入の手順 | 開発に近い人向け（このままでよい） |
| AI の役割（システムプロンプトの 1 文） | 「…半径圏で集約されたオープンデータ（…）を、地図とチャートで案内します。」 | 「何ができる？」に答える材料が無い |
| MCP | `instructions` が無い | Claude・ChatGPT が最初に読む「このサーバの使い方」が空 |
| README | 「オープンデータ（…）を駅×半径で集約し…」と、想定（輸送計画・出店・住宅購入） | 作る人向け（任意で合わせる） |

**共通の問題**：どこも主語が「データ」で、「あなたは何ができるか」が無い。挙げるデータも場所ごとに違う（バス停・所得・売上・年齢・
災害が入ったり抜けたり）。**同じ源が無い**ので、データを足すたびにずれる。

### 2.2 AI に聞いた（Gemini・main のビルド）

| 問い | AI の答え（要約） | 問題 |
|---|---|---|
| このアプリで何ができますか？ | 道具を呼ばず「日本全国の駅周辺のオープンデータ（乗降客数・人口・所得・地価…）を、地図とチャートで確認・比較できるツールです…どのようなデータや地域をご覧になりますか？」 | データの名前の羅列。**何も見せずに聞き返す**（2026-10-19 と同じ形） |
| 家を買う予定の場所の周りがどんな所か知りたい | 道具を呼ばず「対象となる駅名（または市区町村名・**住所など**）を教えていただけますでしょうか？」 | **扱えない住所を求めている** |
| 横浜市港北区日吉本町3丁目の周り1kmの人口は？ | 「日吉本町」で駅を探し、日吉本町駅の周り（1km）のプロフィールで「日吉本町駅の周辺1km圏の人口は52,671人（2020年）です」 | **住所の地点を、黙って駅の周りに読み替えた**。答えの文に「駅の周りの値で、住所の地点の値ではない」が無い |

### 2.3 地点（②）について、いまできること・できないこと

| | 画面 | AI・MCP |
|---|---|---|

| **地点の周りの人口・年齢・地価などの集計** | × | ×（DB は駅ごとの値と区域の値だけ。メッシュは手元のファイルにしか無い） |

| 地図の好きな場所を押す | ×（押せるのは駅とクラスタだけ） | — |

## 4. 目指す姿 — 3 秒で「何ができるか」が分かる

### 4.1 説明の型（どこでも同じ順）

```
① 何のアプリか（1 行）
② 何ができるか（やりたいこと 4 つ。それぞれ例の質問 1 つと「分かること」1 行）
③ どう始めるか（1 行）
（説明用ページと AI の答えだけ）④ できないこと（3 行まで）
```

- **主語は利用者**（「〜を選ぶ」「〜に備える」）。データの名前は「分かること」の中に入れる
- 画面の文字は増やさない（2026-11 からの方針：画面に常に出る注意書きの壁・「見ていないこと」の一覧・長い出典の一覧を置かない。
  値と結論を先に）。最初の画面は ① と ② だけ

### 4.2 ひとこと（① の文案）

| 案 | 文 | 向き |
|---|---|---|
| **A（推奨）** | **住まい選び・お店探し・災害への備えに。全国の駅のまわりを、データと AI で調べられます。** | 「何を達成できるか」が先（声 ① に正面から答える） |
| B | 駅のまわりを、データと AI で調べる地図 | 何をするアプリか（短い。261019 の U-5 の案） |
| C | 気になる街の人口・地価・災害リスクが、駅ごとに分かる | 分かることが先 |

- 推奨は A。狭い所（携帯の上の帯・`title`）には後半だけの短い形「全国の駅のまわりを、データと AI で調べる」を使う
- 「駅×半径」「オープンデータ」は既定の画面では使わない（データの説明の中では使ってよい）

### 4.3 やりたいこと 4 つ（② の文案）

| やりたいこと | 例の質問（押すとそのまま聞く） | 分かること（1 行） | 主に使う共通 API |
|---|---|---|---|
| **住む街を選ぶ** | 武蔵小杉に住むならどう？ | 人口の増減と将来・年齢・地価・災害リスク・県内での位置 | 駅周辺のプロフィール |
| **お店の場所を探す** | 渋谷駅のまわりで働く人と売上は？ | 乗降客数・働く人の数・推計の売上（小売・飲食・生活/娯楽）・事業所 | 駅の詳細（売上・従業者） |
| **災害に備える** | 亀有駅は浸水しますか？ | 浸水・土砂などの想定・いまの警報・近くの避難場所・逃げる方向 | 地点のハザード・警報・避難先 |
| **街のこれからを知る** | 東急東横線の沿線の人口は、2050年までにどうなる？ | 将来の人口と年齢（生産年齢人口・高齢化率）・市区町村や沿線の全体 | エリアの要約 |

- 4 つは README の想定（住宅購入・出店・輸送計画）と、いちばん聞かれる災害から選んだ。**これ以上増やさない**
  （261019 §6.2 の原則。5 つ目は「次の一手」で出す）
- 「比べる」（武蔵小杉と自由が丘）は「住む街を選ぶ」の中で扱う（例の質問の 2 つ目として説明用ページにだけ出す）
- 例の質問は、**PR-2 で本番の Gemini に流し、答えが 1 回で図まで出るものだけ**を採る（上の 4 つは案）
- 代替：261019 の 4 つ（住む街の候補を探す・街を知る・2 つの街を比べる・災害を確かめる）。住まいに寄せた形。§10 の D-2

### 4.4 できないこと（④ の文案・3 行まで）

- **住所や地図の好きな地点の「周りの人口」など**：いまは駅のまわりだけ（地点の災害リスクは見られる）
- **治安・学校・保育園・お店の評判、家賃や物件の値段**：データに無い（地価は公示地価）
- **将来の断定**：将来の人口は推計（国の推計を駅のまわりに割り振ったもの）

### 4.5 ③ どう始めるか（1 行）

「駅名を入れるか、下の例を押すだけ。AI が地図と図で答えます。」

## 5. 同じ源 — 使い方ガイドを共通 API に

### 5.1 置き場所と形

```
src/shared/guide.ts           ← 説明の単一の真実（Zod で型つき・データとして持つ。カタログと同じ扱い）
  tagline（長い形・短い形）  jobs[]（id・名前・例の質問・分かること・アイコン名）  howToStart  limits[]
        │
        ├─ GET /api/guide                 → 説明用ページ・About・最初の画面（共通 API）
        ├─ AI の道具 getAppGuide の返り値 → 「何ができる？」の答え（返り値に答え方 answerGuide）
        ├─ MCP の instructions（先頭 512 文字で完結）・（任意）resource guide://app
        └─ メタ情報（title・description・OG）
```

- **画面に説明の文を直書きしない**（今の `ChatPanel.tsx` の 1 文・`SuggestionChips.tsx` の例の質問・`AboutDialog.tsx` の段落・
  `layout.tsx` の説明文を、ガイドから読むものへ置き換える）
- `jobs[].id` は短い英字（`live`・`shop`・`disaster`・`future`）。URL（§6.1 の `?try=`）と評価で使う
- 「分かること」に書くデータは、**カタログのカテゴリにあるものだけ**（テストで確かめる。無いものを書かない）

### 5.2 同期テスト（言葉がずれないように）

- 説明用ページ・最初の画面・AI の返り値・MCP の `instructions` が、ガイドと**同じ文字列**を使っている
- 例の質問はどれも、評価の問に入っている（答えが出ることを評価で見続ける）
- ガイドの `limits` と、AI の答え方（「住所は扱えない」など）が食い違わない

- サーバで描く静的なページ（検索と SNS に出る・軽い）。携帯で 2 画面以内
- スクリーンショットは最初は載せない（古くなりやすい・重い）。載せるなら PR-1 の後に 1 枚ずつ（§10 の D-3）

### 6.2 About（ⓘ）

- 冒頭の段落を「ひとこと（A）＋やりたいこと 4 つの名前（1 行）＋『詳しく →』（`/about`）」に替える
- 出典の一覧（駅の指標・エリアの値・災害）はそのまま。題は「このアプリ・データ出典」のまま

### 6.3 最初の画面

- 入力欄の例も「どう始めるか」に合わせる（「駅名か、聞きたいことを入力…」。今は「質問を入力…（例：新宿駅の地価は？）」）

**携帯（チャットが閉じている）**：

- **最初の 1 回だけ**、地図の下に小さな案内（ひとことの短い形＋やりたいこと 4 つのボタン・× で閉じる）。閉じたら出さない
  （ブラウザに覚える・覚えられなくても壊れない）
- AI のボタン（✦）に「AI に聞く」の文字（入らなければ `aria-label` と、初回の案内の中で）
- 半径の切り替え（500m〜20km）に「駅からの範囲」の説明（`title`・読み上げ用。画面の文字は増やさない）

### 6.4 AI チャットの答え

「このアプリで何ができますか？」「はじめてです」「何を聞けばいい？」に、ガイドから答える。

**仕組み（2 案）**

|---|---|---|---|
| **道具（推奨）** | 道具 `getAppGuide` を 1 本足す。返り値はガイドと答え方（answerGuide） | 聞かれたときだけ読む。画面・MCP と同じ源。答え方を返り値で縛れる（B4・B5 で効いた形） | 道具の説明は**全部の問いに見える**（B5d：説明の 1 語で無関係な問が崩れた）→ 説明は短く、ほかの道具の名を書かない。全問の A/B |

## 7. ② 任意の場所と半径 — 住宅購入の最後の段

### 7.1 利用者の流れ

駅で比べる（いまできる）→ 候補の駅を決める（いまできる）→ **物件の場所の周りを知る（ここが無い）**

最後の段で知りたいのは、たぶん「その場所の災害リスク」「近くの駅と距離」「周りの人の数や年齢・地価」。前の 2 つは、データは
もう持っている（§2.3）。足りないのは**地点を選ぶ入口**と、**地点の周りを数える仕組み**。

### 7.2 段階

| 段 | 中身 | 規模 | データ・DB | Gemini |
|---|---|---|---|---|
| **②-1 正直さ** | 住所らしい問い（「丁目」「番地」「◯番◯号」）を見分け、その問いにだけ「住所の地点の値は持っていない。駅の周り（駅から N km）の値で答えるなら、そう断る」を足す（`asksAboutAddress`。2026-11 の「この区」の守り〔#204〕と同じ作り）。AI に住所を求めさせない。ガイドの「できないこと」にも書く | S | なし | 住所の問い＋無関係の問（PR-3 の A/B に含める） |
| **②-2 地点を選ぶ** | 地図を長押し（携帯）・右クリック（PC）で地点を選ぶ → **地点のカード**：その地点の災害リスク（今の地点のハザード）・近くの駅と距離（今の `near`）・「この駅の周りを見る」。AI にも「選んだ地点」を地図の文脈として渡す（選択中の駅と同じ置き場所） | M | なし | 地点の問 約 30 回 |
| **②-3 地点の周りを数える** | 「地点から N m」をエリアの要約の種類に足す（**駅から N m と同じ見せ方・同じ按分**）。人口・年齢・将来（250m）、事業所・従業者（500m）、地価公示の地点、バス停 | L | メッシュを DB に（下の見積もり）・本番への投入の了承 | エリアの問の A/B |
| **②-4 住所で探す** | 町丁目の代表点を DB に入れ、住所（町丁目まで）を地点にする。**住所を外のサービスに送らない** | M | 町丁目の代表点（下の候補） | 少し |

**②-3 の見積もり**（2026-11-28 に手元のファイルで数えた）：250m の国勢調査は 1,163,757 セル、将来推計（R6）は 1,162,630 セル、
500m の経済センサスは 324,923 セル。セルの形は DB に持たず、**メッシュコードの範囲で引く**（円に掛かるセルを計算で列挙し、
コードで引いて重なりの割合で足す）。列を絞れば（人口 2 年・年齢 4 区分・将来の総数と年齢・従業者・事業所で 20 列ほど）
**100〜200MB**。本番の DB は 511MB（Pro・8GB）なので入る。半径 20km でも掛かるセルは 2 万ほどで、1 回で引ける。
乗降客数（駅の値）・所得・売上（駅の円で作った値）は、地点では作らない（「最寄り駅の値」として出すかは別に決める）。

**②-4 の候補**（どちらも利用規約と、代表点の座標が入っているかを**要確認**）：

- 国土交通省「位置参照情報」（大字・町丁目レベル・[製品仕様](https://nlftp.mlit.go.jp/isj/product_spec_ohzachochomoku_v1_2.pdf)）
- デジタル庁「アドレス・ベース・レジストリ」（[利用規約](https://www.digital.go.jp/policies/base_registry_address_tos)：公共データ利用規約 PDL1.0・出典の記載が要る）
- 国土地理院の住所検索 API は**勧めない**（利用者の住所＝購入予定の場所が外のサービスに出る）

### 7.3 推奨

- **②-1 は早く**（PR-3）：今の答えは、住所を駅に黙って読み替えている（§2.2）。数がもっともらしいので誤解を生む
- **②-2 は PR-4**：データを作り足さずに、住宅購入の最後の段の半分（災害と近くの駅）に届く
- **②-3・②-4 は別の計画**：データの設計・大きさの試し・本番への投入があるので、この計画とは分ける。②-2 で地点を選ぶ入口が
  できてから、同じカードに「周りの人口など」を足す形にする

## 9. 検証
