# memo
このファイルは、AI-Database-Map リポジトリで作業するときに Claude Code へ指針を提供するものです。

## プロジェクト概要

- **AI Database Map**: オープンデータ（乗降客数、人口、地価等）を可視化したAIネイティブなWebアプリ
- **目的**: オープンデータを誰でも分かりやすく使えるWebアプリ
- **活用想定**: 鉄道会社の輸送計画、店舗出店の商圏分析、個人の住宅購入　等
- **目標**: 個人開発した「Station Area Database Map」をAIネイティブなアプリに進化させること

Step1: 個人開発した「Station Area Database Map」のデータセットを更新して、アプリを公開すること
Step2: Step1で開発したアプリにLLMを連携して、AIネイティブなアプリにすること
Step1の実装時点で、Step2のLLMとの連携を見据えて、最適なアーキテクチャ、ロジック、コードの実装を進めること。

## architecture
1. Technology Stack
    - Infrastructure & Hosting: Vercel (Hobby Plan)
    - Language: TypeScript
    - Framework: Next.js (App Router) + React
    - Map Rendering : MapLibre GL JS
    - Map Tiles / Base Map: MapTiler
    - AI / LLM: Google Gemini 2.5 Flash
    - Database: Supabase
    - Spatial Extension: PostgreSQL + PostGIS

2. System Architecture & Responsibilities
    
    [A] Frontend Layer (Next.js / React / MapLibre)

    [B] Backend / API Layer (Next.js API Routes on Vercel)

    [C] Database Layer (Supabase / PostgreSQL / PostGIS)

    [D] AI Layer (Gemini 2.5 Flash)

3. Core Protocol: "GUI Chat Protocol (Map Edition)"
AI（バックエンド）とフロントエンドが通信するための標準インターフェース。AIエージェントは、最終的にこの型（Type）に合致するレスポンスをフロントエンドに返すようにAPIを実装すること。

development/ai_friendly.md
人間用UIとAI用APIのロジックを分離しない
よくある失敗は、

UI専用ロジック
AI / API専用ロジック
が別実装に分かれてしまうこと。AIと人間で「操作の入り口」を二重に作ると、片方だけ仕様が古くなったり挙動がズレたりして、バグの温床になる。

理想は、人間向けUIも、AIが叩くのと同じAPIを使うこと。 UIはそのAPIを直接、または薄くラップした関数を経由して呼び出す。こうすれば操作の入り口が一本に共通化され、AIと人間がまったく同じロジックを通る。

人間向けUI ─┐
            ├─→ 共通API（またはそのラッパ関数）─→ Domain Logic
AI / MCP ───┘
ポイント:


AIと人間で 別々のAPIを作らない（共通化する）。これが結果的にコードを健全に保つ
UIから直接DBやドメインロジックを叩かず、必ずこの共通APIを経由させる
共通APIを unit test で固めておくと、人間・AI どちらの経路も同時に品質が保証され、安心してリファクタリングできる

spec/AI_NATIVE_BUSINESS_APP_ARCHITECTURE.md

反転

従来のSaaSアプリケーションはUI中心である。

   ┌──────────────────────────────────────┐
   │                UI                    │   ← プロダクト
   ├──────────────────────────────────────┤
   │         Business logic               │   ← UIの背後
   ├──────────────────────────────────────┤
   │             Database                 │
   └──────────────────────────────────────┘

UIが特権的な位置にある。APIが仮に存在するとしても、それは後から考えられた副次的なものであり、連携パートナーのための二級のアクセス手段にすぎない。

AIネイティブなトポロジーは、これを反転させる。

          [ LLM ]                 [  UI / View  ]
              \                       /
               \                     /
                \                   /
                 ─────── API ──────
                          │
                  Business logic
                          │
                      Database
                   (file system)

APIこそがプロダクトである。2つのクライアント、つまり構造化UIとLLMが、対等な存在としてそれを呼び出す。ビジネスロジックとそのデータだけが、アプリケーションにおける唯一の信頼できる部分であり、両方のクライアントは、同じ基盤モジュールの単なるプレゼンテーションにすぎない。

これは「AIアシスタント付きのアプリ」でも、「ツールを持ったAI」でもない。これは、人間がそれを操作するための2つの同等に正当な方法、すなわちクリックすることと尋ねることを備えた、単一のドメインモジュールである。

3つのレイヤー
1. ドメインモジュール

ビジネスロジックとそのデータである。元帳であれば、複式簿記の不変条件、追記専用の仕訳帳、期首残高、貸借対照表の導出がこれにあたる。ドメインモジュールは不変条件、つまりどのクライアントが呼び出しているかにかかわらず成立しなければならないルールを所有する。

2. API

両方のクライアントが呼び出す、単一の型付き契約である。MulmoClaudeの参照実装では、これはドメインプラグインごとに1つのRESTエンドポイントであり、actionディスクリミネーターを持つ（POST /api/<plugin> に {action, ...args} を渡す）。LLMはMCP経由でそれを呼び出し、GUIは直接それを呼び出す。同じ形、同じハンドラー、同じ結果である。

契約が正確に1つだけであるため、手動のクリックとLLMのツール呼び出しは同じサービスレイヤーを通り、同一の状態変更を生み出す。「UIでできること」と「AIでできること」の間にズレは生じない。

3. 2つのプレゼンテーション
構造化UI — ユーザーが見たいもののための、標準的で固定スキーマのインターフェースである。貸借対照表は貸借対照表らしく見え、仕訳帳は仕訳帳らしく見える。これはビジネスロジックを持たない薄いレイヤーである。APIを通じて読み取り、APIを通じて書き込む。
LLM — 同じAPIを読み取り、同じ操作を呼び出し、状態について推論できる会話型インターフェースである。LLMは、ツールスキーマと、APIのレスポンスに埋め込まれたアクションごとの応答メッセージを通じて、そのドメインについて教えられる。

Git 操作
ユーザーの明示的な許可なしに、git commit、push、その他の git 操作を絶対に実行しない
変更を加える前に、必ず git branch または git status で現在のブランチを確認する
ブランチが想定と異なる場合は、どのブランチを使うかを必ずユーザーに確認する
実装作業を始める前に、必ずフィーチャーブランチを作成する
git commit、git push、git merge、git rebase などを実行する前に、必ず確認する
git add . または git add <directory> は絶対に使用しない — ファイルは必ず個別に追加する
未追跡ファイルは絶対に削除しない
main に直接 push しない — 必ずフィーチャーブランチを作成し、PR を開く
PR をマージする際は、必ず merge commit（--merge）を使用する — squash merge は絶対に使用しない
git rebase は絶対に使用しない
git push --force は絶対に使用しない
コミットメッセージには必ず次のプレフィックスを使用する: feat:, fix:, refactor:, docs:, chore:
'create a PR' または 'PR、マージ' と依頼された場合、これは PR をマージすることではなく、プルリクエストを作成することとして解釈しなければならない
PR を作成する前に、正しいデフォルトブランチ / ターゲットブランチを必ず確認する
読み取り専用操作（git status, git diff, git log）は自由に実行してよい

変更範囲のルール
明示的に依頼された変更のみを行う — 機能、ツール、パッケージ、コンテンツを自律的に追加してはならない
追加で何かが必要に見える場合は、まず確認する
指示がない限り、PR コメント、コミットメッセージ、ドキュメントは簡潔に保つ

デバッグ方針
修正を試みる前に、必ず根本原因を診断する
クイックフィックス的な対応（値のハードコード、JSON ワークアラウンド）は絶対に行わない
リグレッションを調査する際は、必ず git の履歴 / diff を確認する
デバッグに飛びつく前に、ユーザーが何を求めているかを必ず理解する

import スタイル
npm パッケージには必ずトップレベルの import を使用する — 常に必要なパッケージに対して await import() は絶対に使用しない
Dynamic import() は、常にロードされるわけではない条件付き / 任意依存関係にのみ使用してよい
具体的で正当な理由がない限り、モジュールを再エクスポートしてはならない

コーディングスタイル

哲学: 人間が理解しやすいコードを書く

人間の文脈把握力と記憶力には限界がある。これを念頭に置いてコードを書くこと:

コンパクトな関数: 人間が一目で完全に理解できる、小さく焦点の合った関数に分割する
明確な命名: 関数名と変数名はストーリーを語るものでなければならない。初心者でも流れを理解できるようにする
最小限のスコープ: 認知負荷を下げるため、変数スコープはできるだけ小さく保つ
読みやすい流れ: コードは物語のように読めなければならない
ルール
関数は必ず 20 行未満に保つ。必要に応じて小さな関数に分割する
let より const を必ず優先する。var は絶対に使用しない
for ループより、関数型アプローチ（forEach, map, filter, reduce）を必ず優先する
.then() チェーンより async/await を必ず優先する
明示的な型定義を必ず使用する。any は絶対に使用しない
マジックナンバーは絶対に使用しない。必ず名前付き定数を使用する
該当する場合は、変数名に単位を含めることが望ましい（例: timeout_ms, distance_km）
DRY 原則（Don't Repeat Yourself）に必ず従う
失敗する可能性がある処理には必ず try/catch を追加する
ネットワークリクエスト（fetch、API 呼び出し）は、必ず AbortController によるタイムアウト処理を含める
文脈（URL、ファイルパスなど）を含む、意味のあるエラーメッセージを必ず提供する

TypeScript ベストプラクティス
as による型キャストは絶対に使用しない。代わりに必ず型ガードを使用する（例: const isXxx = (x: unknown): x is Type => { ... }）
独自実装の代わりに、必ずライブラリの既存ユーティリティ関数を使用する（例: graphai の isObject）
Zod schema から型を導出するには、必ず z.infer<typeof schema> を使用する。重複するローカル型を定義してはならない
文字列を構築する際は、let + += ではなく、必ず const を使った array + push() + join() パターンを使用する
再利用性とテスト容易性のため、純粋なデータ変換関数は専用ファイルに分離することが望ましい
"new/legacy" ではなく、説明的なフォーマット名を必ず使用する（例: "object format" と "text format"）
